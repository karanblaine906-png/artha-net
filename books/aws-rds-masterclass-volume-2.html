Chapter 8 — Advanced SQL and Analytics

8.1 Mental model: SQL is declarative

SQL specifies what result is required; the optimizer selects how to produce it. Logical processing roughly follows FROM/JOIN → WHERE → GROUP BY → HAVING → window evaluation → SELECT → ORDER BY → LIMIT (actual query syntax order differs). A window function does not collapse rows like GROUP BY. A CTE (WITH) names a query subexpression; in modern PostgreSQL some non-recursive CTEs may be inlined. Do not assume a CTE is always materialized or always faster.

8.2 Reproducible order dataset

Save the following as 01_schema.sql and execute with psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f 01_schema.sql.

BEGIN;
CREATE TABLE IF NOT EXISTS customers (
  customer_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL UNIQUE,
  full_name text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE IF NOT EXISTS products (
  product_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  sku text NOT NULL UNIQUE,
  title text NOT NULL,
  price_cents bigint NOT NULL CHECK (price_cents >= 0),
  stock_on_hand integer NOT NULL CHECK (stock_on_hand >= 0)
);
CREATE TABLE IF NOT EXISTS orders (
  order_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customers(customer_id),
  status text NOT NULL CHECK (status IN ('pending','paid','cancelled')),
  idempotency_key uuid NOT NULL UNIQUE,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE IF NOT EXISTS order_items (
  order_id bigint NOT NULL REFERENCES orders(order_id) ON DELETE RESTRICT,
  product_id bigint NOT NULL REFERENCES products(product_id),
  quantity integer NOT NULL CHECK (quantity > 0),
  unit_price_cents bigint NOT NULL CHECK (unit_price_cents >= 0),
  PRIMARY KEY (order_id, product_id)
);
INSERT INTO customers(email,full_name) VALUES
('ada@example.test','Ada'),('grace@example.test','Grace'),('linus@example.test','Linus')
ON CONFLICT(email) DO NOTHING;
INSERT INTO products(sku,title,price_cents,stock_on_hand) VALUES
('BK-001','Database Book',2999,100),('KB-002','Keyboard',5999,25),('MS-003','Mouse',1999,40)
ON CONFLICT(sku) DO NOTHING;
COMMIT;

Line-by-line design notes: BEGIN and COMMIT make DDL and seed operations atomic; IDENTITY delegates key allocation; UNIQUE creates a supporting uniqueness index; timestamptz stores instants (displayed in session timezone); CHECK rejects invalid states; foreign keys enforce referential integrity; ON DELETE RESTRICT avoids silent item loss; (order_id,product_id) enforces one line per product per order; ON CONFLICT DO NOTHING allows repeatable seeding without duplicating email/SKU. IF NOT EXISTS does not validate an existing table's structure—use migrations to evolve schemas.

8.3 Joins and cardinality

SELECT c.email, o.order_id, o.status
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.customer_id
ORDER BY c.email, o.order_id;

LEFT JOIN keeps customers with zero orders; matching order columns are NULL. INNER JOIN removes unmatched customers. An accidental many-to-many join multiplies rows: if one customer has 3 orders and 4 addresses, joining both child tables without care can produce 12 rows. Always reason about grain: one row per customer, order, or item?

8.4 Aggregation and FILTER

SELECT o.customer_id,
       count(*) AS order_count,
       count(*) FILTER (WHERE o.status = 'paid') AS paid_orders
FROM orders AS o
GROUP BY o.customer_id
HAVING count(*) >= 1;

WHERE filters input rows before aggregation; HAVING filters groups after aggregation. count(*) counts rows, whereas count(nullable_col) counts non-null values.

8.5 Window functions

SELECT order_id, customer_id, created_at,
       row_number() OVER (PARTITION BY customer_id ORDER BY created_at DESC, order_id DESC) AS newest_rank,
       lag(created_at) OVER (PARTITION BY customer_id ORDER BY created_at, order_id) AS previous_order
FROM orders;

PARTITION BY resets the window for each customer; the order determines row sequence; the order_id tie-breaker makes ordering deterministic. row_number enumerates rows; rank leaves gaps for ties; dense_rank does not. lag accesses the prior row without a self-join.

8.6 CTEs and recursive queries

WITH RECURSIVE numbers(n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1 FROM numbers WHERE n < 5
)
SELECT n FROM numbers ORDER BY n;

Expected rows: 1, 2, 3, 4, 5. Recursive queries need a termination condition; cyclic graph traversal may require cycle detection.

8.7 Safe upserts and RETURNING

INSERT INTO products(sku,title,price_cents,stock_on_hand)
VALUES ('BK-001','Database Book (2nd ed.)',3499,100)
ON CONFLICT(sku) DO UPDATE SET
 title = EXCLUDED.title, price_cents = EXCLUDED.price_cents
RETURNING product_id, sku, price_cents;

EXCLUDED refers to proposed incoming values; RETURNING avoids a second lookup. Beware that upsert semantics do not replace a full business transaction when stock and payments span multiple rows.

8.8 Pagination: OFFSET vs keyset

-- Offset becomes progressively expensive and is unstable under concurrent inserts.
SELECT order_id, created_at FROM orders
ORDER BY created_at DESC, order_id DESC LIMIT 20 OFFSET 20000;
-- Keyset: supply the last seen tuple from previous page.
SELECT order_id, created_at FROM orders
WHERE (created_at, order_id) < (TIMESTAMPTZ '2026-10-01 00:00:00+00', 900)
ORDER BY created_at DESC, order_id DESC LIMIT 20;

For keyset performance, create an index matching (created_at DESC, order_id DESC). OFFSET still has valid uses for small admin datasets.

8.9 JSONB, arrays, and boundaries

CREATE TABLE IF NOT EXISTS product_attributes (
  product_id bigint PRIMARY KEY REFERENCES products(product_id),
  attrs jsonb NOT NULL DEFAULT '{}'::jsonb
);
INSERT INTO product_attributes(product_id,attrs)
SELECT product_id, '{"color":"black","layout":"US"}'::jsonb
FROM products WHERE sku='KB-002'
ON CONFLICT(product_id) DO UPDATE SET attrs=EXCLUDED.attrs;
SELECT product_id FROM product_attributes WHERE attrs @> '{"color":"black"}'::jsonb;

Use JSONB for flexible attributes, not as an excuse to avoid constraints or normalized relationships. Consider a GIN index for frequent containment searches; verify workload selectivity first.

Lab 8 — analytics practice

  1. Seed two paid and one pending orders with unique UUIDs (see INSERT INTO orders ... syntax).
  2. Report revenue as sum(quantity * unit_price_cents) only for paid orders.
  3. Find customers with no orders via LEFT JOIN ... WHERE o.order_id IS NULL or NOT EXISTS.
  4. Return latest order per customer with row_number() ... WHERE newest_rank=1 in an outer query.
  5. Run EXPLAIN (ANALYZE, BUFFERS) on a SELECT, not on a destructive DML statement in production.

Troubleshooting: SQL

  • Duplicate result rows: inspect join cardinality and key uniqueness; DISTINCT may conceal a modeling bug.
  • Wrong revenue: ensure status filter, historical unit price, currency representation, and returns/refunds semantics.
  • Unexpected NULL: check outer joins and three-valued logic (NULL = NULL is unknown; use IS NULL).
  • Pagination gaps: use stable ordering, keyset cursor, and define concurrency consistency guarantees.

Senior interview Q&A

Q: Why store money as integer cents instead of float? A: Binary floating-point cannot represent many decimal amounts exactly; integers or numeric(p,s) avoid rounding surprises. Define currency and rounding rules explicitly.

Q: When is a CTE slower than a subquery? A: Materialization can block predicate pushdown, but modern PostgreSQL may inline eligible CTEs. Examine the actual plan and version rather than generalizing.

Q: Why do window functions matter for API backends? A: They efficiently express rankings, deduplication, running totals, and latest-per-group retrieval while preserving detail rows.

Chapter 9 — Relational Schema Design

9.1 Start from invariants, not tables

A senior engineer writes business invariants first: an email is unique within a tenant; an order belongs to exactly one customer; item quantities are positive; order prices are historical snapshots; payment retries must not create duplicate charges; deletion must respect legal retention. Convert each invariant into constraints, transaction boundaries, and tests.

9.2 Entities, relationships, and cardinality

erDiagram
  CUSTOMERS ||--o{ ORDERS : places
  ORDERS ||--|{ ORDER_ITEMS : contains
  PRODUCTS ||--o{ ORDER_ITEMS : referenced_by
  ORDERS ||--o{ PAYMENTS : attempts
  CUSTOMERS { bigint customer_id PK
              text email UK }
  ORDERS { bigint order_id PK
           bigint customer_id FK
           uuid idempotency_key UK }
  ORDER_ITEMS { bigint order_id PK,FK
                bigint product_id PK,FK }

An order can have many items; a product can appear in many orders; the intersection table resolves many-to-many. A conceptual ERD cannot itself guarantee every order has an item—enforce this in the transaction/service or with appropriate advanced database constraints.

9.3 Normal forms

  • 1NF: columns contain values treated as atomic for the modeled domain; avoid comma-separated product IDs.
  • 2NF: with a composite candidate key, non-key attributes depend on the whole key (not just order_id or product_id).
  • 3NF: non-key attributes should not depend transitively on a key through another non-key attribute.
  • BCNF: every determinant of a nontrivial functional dependency is a superkey (stronger than 3NF). Normalization limits update anomalies; purposeful denormalization can improve read performance but creates consistency obligations.

9.4 Keys and data types

Surrogate bigint IDENTITY keys are compact and easy to index; UUIDs help with distributed creation and public identifiers, but random UUID insertion may fragment B-trees and add storage overhead. Use timestamptz for event instants; date for calendar dates; numeric for exact fractional money; text for unconstrained strings; varchar(n) only for meaningful length limits. Always define the semantic meaning of NULL.

9.5 Constraints and referential actions

CREATE TABLE IF NOT EXISTS payments (
  payment_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  order_id bigint NOT NULL REFERENCES orders(order_id) ON DELETE RESTRICT,
  provider_request_id text NOT NULL UNIQUE,
  amount_cents bigint NOT NULL CHECK(amount_cents > 0),
  state text NOT NULL CHECK(state IN ('initiated','captured','failed')),
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_payments_order_created ON payments(order_id, created_at DESC);

A payment provider request ID is an idempotency boundary. ON DELETE CASCADE is appropriate only when child data truly must be deleted with parent data. For financial records, restrictive deletion and explicit retention policies are often safer.

9.6 Multi-tenancy

Database-per-tenant: strongest logical separation and customizable maintenance, expensive at high tenant count. Schema-per-tenant: moderate separation, operational complexity and migration fan-out. Shared schema + tenant_id: efficient, requires consistent tenant scoping and often row-level security (RLS). RLS is defense-in-depth, not a replacement for application authorization; pooled sessions must reset tenant context safely.

-- Illustrative pattern for a new multi-tenant table:
CREATE TABLE IF NOT EXISTS tenant_notes (
  tenant_id uuid NOT NULL,
  note_id bigint GENERATED ALWAYS AS IDENTITY,
  body text NOT NULL,
  PRIMARY KEY(tenant_id, note_id)
);
CREATE INDEX IF NOT EXISTS idx_tenant_notes ON tenant_notes(tenant_id, note_id);

9.7 Partitioning and lifecycle

Partition large time-series tables when pruning, retention, and maintenance benefits justify complexity. Partitioning does not automatically make all queries faster; unique constraints on partitioned tables have restrictions. Design partitions around actual predicates and retention. For hot transactional tables, start with good indexing and archiving before introducing partition maintenance.

Lab 9 — schema design review

Design subscriptions, invoices, invoice_lines, and payment_attempts. Specify keys, FKs, uniqueness, nullable fields, cascade behavior, audit columns, and retention. Write tests that attempt duplicate provider IDs, negative quantities, and orphan rows; confirm constraints reject each.

Troubleshooting: modeling

  • Missing FK indexes: PostgreSQL does not automatically index referencing columns; deletion/update of referenced rows may scan children.
  • Large table rewrites: assess DDL lock level and version-dependent behavior before adding defaults or changing types.
  • Hot tenant: evaluate tenant-specific query plans, skewed distributions, partitioning or isolation strategies.

Senior interview Q&A

Q: When would you denormalize? A: After measuring a read bottleneck, defining update ownership, consistency rules, backfill, reconciliation, and rollback.

Q: Why not use a UUID as every clustered key? A: PostgreSQL heap storage is not clustered by primary key automatically; index size/locality and insertion patterns still matter. Pick keys based on access patterns, privacy, and distribution needs.

Q: What makes schema design production-ready? A: Constraints, lifecycle, migration strategy, indexing, ownership, security, observability, and tested failure handling.

Chapter 10 — Indexing, Statistics, and Query Optimization

10.1 Why an index works

A B-tree maintains sorted search keys pointing to table rows. Instead of reading every heap page, PostgreSQL can descend the tree, find matching tuple identifiers, then fetch visible rows from heap pages. For small tables, sequential scans may be cheaper. Indexes consume disk, WAL, cache, and write amplification; they are not free.

flowchart TB
  R[Root page] --> A[Internal page: lower keys]
  R --> B[Internal page: higher keys]
  A --> L1[Leaf: key + tuple pointer]
  A --> L2[Leaf: key + tuple pointer]
  B --> L3[Leaf: key + tuple pointer]
  L2 --> H[(Heap page)]

10.2 Index types

Index Typical fit Important limitation
B-tree equality, ranges, sorting less suitable for arbitrary substring patterns
GIN JSONB containment, arrays, full-text heavier writes and maintenance
GiST geometry, ranges, exclusion operator-class-specific behavior
BRIN huge physically correlated append-only data lossy, may recheck many rows
Hash equality-only niche usually B-tree is more flexible

10.3 Composite and covering indexes

CREATE INDEX IF NOT EXISTS idx_orders_customer_time
ON orders(customer_id, created_at DESC, order_id DESC);
CREATE INDEX IF NOT EXISTS idx_orders_paid_customer
ON orders(customer_id, created_at DESC)
WHERE status = 'paid';
CREATE INDEX IF NOT EXISTS idx_products_sku_include
ON products(sku) INCLUDE(title,price_cents);

Explanation: the composite index starts with customer_id, then orders by timestamp and ID; a query filtering one customer and sorting newest-first can benefit. The partial index stores only paid orders, but a parameterized plan may not always prove a parameter implies the partial predicate. INCLUDE adds payload columns without making them search keys; index-only scans also depend on visibility-map state.

10.4 Query plans

EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT order_id, created_at FROM orders
WHERE customer_id = 1 ORDER BY created_at DESC, order_id DESC LIMIT 20;

Illustrative output (small datasets may prefer Seq Scan):

Limit  (cost=0.15..8.20 rows=20 width=16) (actual time=0.02..0.03 rows=3 loops=1)
  -> Index Scan using idx_orders_customer_time on public.orders
       Index Cond: (customer_id = 1)
Planning Time: 0.3 ms
Execution Time: 0.1 ms

cost is planner-relative estimated work, not milliseconds; actual time is measured milliseconds; rows shows estimated and actual cardinality; loops indicates repeated execution; BUFFERS shows shared/local/temp block accesses. A huge estimate mismatch suggests stale statistics, correlation, skew, or missing extended statistics.

10.5 Query tuning workflow

  1. Capture endpoint latency p50/p95/p99 and throughput, not just SQL timing.
  2. Identify costly SQL via pg_stat_statements where available/enabled (RDS parameter group and extension prerequisites vary).
  3. Record exact parameter shapes and EXPLAIN (ANALYZE, BUFFERS) on representative non-destructive queries.
  4. Check row estimate vs actual, joins, sorts, temp spills, loops, buffer reads, and network/lock waits.
  5. Rewrite predicate or schema, or add a targeted index; test on production-like cardinality.
  6. Compare before/after under concurrent load; account for insert/update cost and maintenance.
  7. Roll out with monitoring and a rollback plan.

10.6 Statistics and autovacuum

ANALYZE collects statistics used by planner. Autovacuum reclaims reusable dead tuples, helps prevent transaction-ID wraparound, and may analyze tables. Vacuum is not simply a disk-shrinking operation: regular VACUUM typically makes space reusable, while VACUUM FULL rewrites and takes an exclusive lock. On RDS, monitor storage growth and long-running transactions that prevent cleanup.

SELECT relname, n_live_tup, n_dead_tup, last_autoanalyze, last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;
ANALYZE orders;

10.7 Sargability and pitfalls

Bad: WHERE lower(email)='ada@example.test' without a matching expression index. Options: store normalized email, create a suitable expression index, or use case-insensitive types with carefully chosen semantics. Bad: WHERE created_at::date = CURRENT_DATE if it prevents an ordinary timestamp range scan. Better:

WHERE created_at >= CURRENT_DATE::timestamptz
  AND created_at < (CURRENT_DATE + 1)::timestamptz

Timezone semantics must match your business requirement.

Lab 10 — benchmark fairly

Create 100k+ synthetic orders on a disposable database, ANALYZE, capture baseline plan, add the composite index, rerun with warm and cold cache considerations. Record rows, buffers, execution time, write overhead, and index size via pg_relation_size. Do not benchmark only a 3-row table and claim a production improvement.

Troubleshooting: slow queries

  • Sequential scan: may be optimal; check table size, selectivity, statistics, and predicate.
  • Sort spilled to disk: inspect temp I/O and work memory; raising work_mem globally can multiply memory usage across concurrent sorts.
  • Nested loop explosion: inspect misestimated join cardinality and indexes; avoid blindly disabling join methods.
  • Index not used: consider parameter types, function wrappers, selectivity, partial-index implication, and stale stats.

Senior interview Q&A

Q: Why is EXPLAIN ANALYZE risky for UPDATE/DELETE? A: It actually executes the statement. On a disposable environment, use a transaction and ROLLBACK when safe; side effects outside the transaction may still exist.

Q: Does an index guarantee an index scan? A: No. Planner chooses based on estimated cost and data distribution.

Q: Why can adding an index worsen performance? A: It increases write/WAL/maintenance work and may alter planner choices; each index needs a measured use case.

Chapter 11 — Transactions, Isolation, MVCC, and Locking

11.1 ACID in an application

Atomicity: either all inventory/order writes commit or none do. Consistency: database constraints plus application invariants hold. Isolation: concurrency anomalies are controlled at the chosen level. Durability: committed data survives within the system's durability model; distinguish database commit from cross-region disaster recovery guarantees.

11.2 MVCC internals

PostgreSQL stores row versions with transaction metadata. A reader's snapshot determines which versions are visible. Writers create new tuple versions on UPDATE; dead versions are eventually reclaimed by VACUUM. MVCC reduces reader/writer interference but does not eliminate write locks, unique-index conflicts, deadlocks, or serialization failures.

sequenceDiagram
  participant A as Session A
  participant DB as PostgreSQL
  participant B as Session B
  A->>DB: BEGIN; read stock=1
  B->>DB: BEGIN; read stock=1
  A->>DB: UPDATE stock=0; COMMIT
  B->>DB: UPDATE stock=0 with predicate stock>=1
  DB-->>B: 0 rows updated (predicate rechecked)
  B->>DB: ROLLBACK

11.3 Isolation levels in PostgreSQL

Level Dirty reads Non-repeatable reads Phantom / serialization behavior
Read Committed (default) prevented possible new matching rows may appear in later statements
Repeatable Read prevented prevented PostgreSQL snapshot isolation prevents ordinary phantoms; write skew can remain
Serializable prevented prevented serial-equivalent result; serialization failures require retry

PostgreSQL accepts READ UNCOMMITTED but treats it as READ COMMITTED. Do not assume identical behavior across MySQL, SQL Server, or Oracle.

11.4 Inventory-safe update

BEGIN;
UPDATE products
SET stock_on_hand = stock_on_hand - 1
WHERE product_id = 1 AND stock_on_hand >= 1
RETURNING stock_on_hand;
-- If zero rows returned, ROLLBACK and report out-of-stock.
-- Otherwise INSERT order + item and COMMIT in the same transaction.
COMMIT;

The conditional update atomically enforces stock >= 0. A naïve read-then-write outside a transaction can oversell. The example does not include payment processing; external payments need idempotency and reconciliation rather than pretending one DB transaction covers a third-party API.

11.5 Row locks and deadlocks

BEGIN;
SELECT product_id, stock_on_hand FROM products
WHERE product_id IN (1,2) ORDER BY product_id FOR UPDATE;
-- Update both products in consistent order.
COMMIT;

A deadlock occurs when sessions form a cycle of lock waits; PostgreSQL detects it and aborts one transaction. Prevent with consistent lock ordering, short transactions, indexes, and no network calls while holding locks. Handle SQLSTATE 40P01 with bounded retry and jitter. Serialization failure SQLSTATE 40001 also requires retrying the entire transaction.

11.6 Session diagnostics

SELECT pid, usename, state, wait_event_type, wait_event,
       now()-xact_start AS transaction_age, left(query,120) AS query
FROM pg_stat_activity
WHERE datname=current_database()
ORDER BY xact_start NULLS LAST;
SELECT blocked.pid AS blocked_pid, pg_blocking_pids(blocked.pid) AS blockers
FROM pg_stat_activity AS blocked
WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0;

Requires appropriate privileges to view details of other sessions. In production, capture evidence and assess business impact before terminating backends. A long idle in transaction session can retain snapshots and block cleanup.

11.7 Idempotency and the outbox pattern

A retryable POST /orders should accept an idempotency key and persist a unique record. To publish events reliably, insert an outbox_events row inside the same database transaction as the order; a separate worker publishes and marks it processed. Delivery is often at least once; consumers must be idempotent. Avoid claiming exactly-once semantics across arbitrary distributed systems.

Lab 11 — two-terminal concurrency

Terminal A: BEGIN; UPDATE products SET stock_on_hand=stock_on_hand-1 WHERE product_id=1 AND stock_on_hand>0; (do not commit yet). Terminal B: run the same update and observe waiting using pg_stat_activity. Commit A and observe B resume. Repeat with stock=1 and verify B updates zero rows. Reset test data on a disposable database.

Troubleshooting: transactions

  • Lock timeout: locate blocker, long transaction, and missing index; avoid raising timeouts blindly.
  • Deadlock: read database logs, identify lock order inversion, add consistent ordering and retry.
  • Serialization failure: retry full unit of work, not only the failed SQL statement.
  • Too many idle transactions: ensure commit/rollback on all exception paths; configure timeouts carefully.

Senior interview Q&A

Q: Is Repeatable Read always serializable? A: No. Snapshot isolation may allow write skew; Serializable adds conflict detection and can abort transactions.

Q: What is the safe approach to retries? A: Use idempotent operations, bounded exponential backoff/jitter, and full-transaction retries for retryable SQLSTATEs.

Q: Why not hold a DB transaction while charging a card? A: External latency and uncertainty hold locks and consume connections; use explicit state transitions, provider idempotency keys, outbox, and reconciliation.

from .models import Customer
from .schemas import CustomerIn, CustomerOut

@app.get("/health/live")
def live():
    return {"status": "alive"}

@app.get("/customers/{customer_id}", response_model=CustomerOut)
def get_customer(customer_id: int, db: Session = Depends(get_session)):
    obj = db.get(Customer, customer_id)
    if obj is None:
        raise HTTPException(status_code=404, detail="Customer not found")
    return CustomerOut(customer_id=obj.customer_id, email=obj.email,
                       full_name=obj.full_name)

@app.post("/customers", response_model=CustomerOut, status_code=201)
def create_customer(payload: CustomerIn, db: Session = Depends(get_session)):
    obj = Customer(email=payload.email, full_name=payload.full_name)
    db.add(obj)
    try:
        db.commit()
        db.refresh(obj)
    except IntegrityError:
        db.rollback()

    except SQLAlchemyError:
        db.rollback()
        raise HTTPException(status_code=503, detail="Database unavailable")

                       full_name=obj.full_name)

13.5 Repository and service

package com.example.shop;
import java.util.Optional;
import org.springframework.data.jpa.repository.JpaRepository;
public interface CustomerRepository extends JpaRepository<Customer, Long> {
  Optional<Customer> findByEmail(String email);
}

package com.example.shop;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class CustomerService {
  private final CustomerRepository repository;
  public CustomerService(CustomerRepository repository) { this.repository = repository; }
  @Transactional
  public Customer create(String email, String fullName) {
    return repository.save(new Customer(email, fullName));
  }
  @Transactional(readOnly = true)
  public Customer get(long id) {
    return repository.findById(id).orElseThrow(
      () -> new IllegalArgumentException("Customer not found"));
  }
}

@Transactional starts/joins a transaction via Spring proxy interception. Beware self-invocation: calling another @Transactional method within the same instance may bypass proxy behavior. readOnly=true is an optimization hint, not a security enforcement. Map exceptions to proper HTTP status codes in a controller advice; catch unique-constraint violations, not all data access exceptions as conflicts.

import express from 'express';
import { pool } from './db';

const app = express();
app.use(express.json({ limit: '32kb' }));

app.get('/health/live', (_req, res) => res.json({ status: 'alive' }));

app.get('/customers/:id', async (req, res) => {
  const id = Number(req.params.id);
  if (!Number.isSafeInteger(id) || id <= 0) {
    res.status(400).json({ error: 'Invalid ID' }); return;
  }
  try {
    const result = await pool.query(
      'SELECT customer_id,email,full_name FROM customers WHERE customer_id=$1', [id]);
    if (result.rowCount === 0) {
      res.status(404).json({ error: 'Not found' }); return;
    }
    res.json(result.rows[0]);
  } catch (err) {
    console.error('Database query failed');
    res.status(503).json({ error: 'Service temporarily unavailable' });
  }
});

app.post('/customers', async (req, res) => {
  const { email, full_name } = req.body ?? {};
  if (typeof email !== 'string' || typeof full_name !== 'string' ||
      email.length > 320 || !email || !full_name || full_name.length > 200) {
    res.status(400).json({ error: 'Invalid customer' }); return;
  }
  try {
    const result = await pool.query(
      `INSERT INTO customers(email,full_name) VALUES($1,$2)
       RETURNING customer_id,email,full_name`, [email, full_name]);
    res.status(201).json(result.rows[0]);
  } catch (err: any) {
    if (err?.code === '23505') {
      res.status(409).json({ error: 'Duplicate email' }); return;
    }
    console.error('Database insert failed');
    res.status(503).json({ error: 'Service temporarily unavailable' });
  }
});

process.on('SIGTERM', () => {

});

14.5 Correct transaction usage

const client = await pool.connect();
try {
  await client.query('BEGIN');
  const stock = await client.query(
    `UPDATE products SET stock_on_hand=stock_on_hand-$1
     WHERE product_id=$2 AND stock_on_hand >= $1
     RETURNING stock_on_hand`, [qty, productId]);
  if (stock.rowCount !== 1) throw new Error('Out of stock');
  // Insert order and order_items using this SAME client.
  await client.query('COMMIT');
} catch (err) {
  await client.query('ROLLBACK');
  throw err;
} finally {
  client.release();
}

This is a method-body excerpt: qty and productId must be defined. Never use pool.query() for statements that belong to a checked-out client's transaction. For retryable failures (40001, 40P01), repeat the whole transaction after a bounded delay and ensure idempotency.

Chapter 15 — Migrations, Testing, Pooling, and Production Delivery

15.1 Expand–migrate–contract

Breaking schema changes are a deployment coordination problem. Old and new app versions may coexist during rolling deploys. Safe pattern:

  1. Expand: add nullable display_name, index concurrently where appropriate, or new compatible table.
  2. Deploy dual-write/read-compatible application with feature flags and observability.
  3. Backfill in bounded batches; track progress and verify counts/hashes.
  4. Switch reads after data parity is proven; monitor errors and latency.
  5. Contract old columns in a later release after all old instances and consumers are retired.
flowchart LR
  A[Schema v1] --> B[Expand: additive migration]
  B --> C[Deploy compatible code]
  C --> D[Backfill + verify]
  D --> E[Switch readers]
  E --> F[Contract later]

15.2 Lock-aware DDL

-- Execute outside an explicit transaction block:
CREATE INDEX CONCURRENTLY idx_orders_status_time
ON orders(status, created_at DESC);

CONCURRENTLY reduces blocking of writes but is slower and can leave an invalid index if interrupted. Check pg_index.indisvalid and follow cleanup guidance. Some migration tools wrap DDL in a transaction by default; configure the migration step accordingly. Avoid blanket ALTER TABLE changes without evaluating locks, table size, defaults, and PostgreSQL version.

15.5 Connection budget and Little's Law

Let average connection hold time be W seconds and throughput be λ DB transactions/sec. Approximate concurrently busy connections L ≈ λW. Example: 250 transactions/sec × 0.04 sec = 10 busy connections on average. Plan for burstiness, long tails, failover, transactions, background jobs, and deploy overlap. This is a sizing starting point, not a guaranteed pool size.

Budget example: DB max_connections=200 (illustrative, engine/instance dependent); reserve 40 for admin/background/maintenance; 8 application pods × 2 worker processes × pool max 8 = 128 potential app connections, leaving 32 spare. During rolling deploys 16 pods could temporarily double demand; cap rollout surge or use suitable proxy/pool strategy. RDS Proxy can reduce connection churn for supported engines/configurations, but session pinning and transaction behavior may limit multiplexing.

15.6 Timeout hierarchy

  • API deadline should be greater than DB statement timeout plus network margin but bounded by user experience SLO.
  • Connection acquisition timeout limits waiting for a pool slot.
  • Connection establishment timeout limits TCP/TLS/auth establishment.
  • statement_timeout bounds SQL runtime; lock_timeout bounds waiting on locks; idle_in_transaction_session_timeout can clean up abandoned transactions.
  • Retry budgets must fit overall request deadlines and avoid retry storms.
-- Session-local example, not a blanket production setting:
SET statement_timeout = '3s';
SET lock_timeout = '500ms';
SELECT 1;

  • Failover breaks transactions: clients must reconnect; in-flight transactions may need safe retry; do not assume connection pool retries are enough.

Q: Why is a migration's down script not necessarily a rollback? A: Data transformations and destructive changes may be irreversible; recovery may require restore, forward-fix, or reconciliation.

Q: How do you size connection pools? A: Measure hold time, throughput, CPU, wait queues, instance capacity, and total replicas; model deploy surges and background workloads.

Q: What makes a deployment zero downtime? A: Compatibility across old/new code, lock-aware schema changes, safe traffic shifting, observability, and recovery—not just a rolling deployment flag.

Outbox schema

CREATE TABLE IF NOT EXISTS outbox_events (
  event_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  aggregate_type text NOT NULL,
  aggregate_id bigint NOT NULL,
  event_type text NOT NULL,
  payload jsonb NOT NULL,
  published_at timestamptz,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS idx_outbox_unpublished
ON outbox_events(created_at, event_id) WHERE published_at IS NULL;

Critical edge case: a worker may publish successfully then crash before recording published_at; duplicates are possible. Consumers must deduplicate by stable event ID. For concurrent workers, consider FOR UPDATE SKIP LOCKED with bounded batches and appropriate transactions; do not hold row locks while performing slow external network calls without evaluating throughput and failure behavior.

Acceptance criteria

  1. Concurrent attempts to purchase the last item cannot both succeed.
  2. Replaying an idempotency key returns the original result (or an explicit in-progress state) without duplicate orders.
  3. Duplicate provider/payment callbacks do not duplicate state transitions.
  4. Every committed order produces a durable outbox row.
  5. Simulated DB outage returns bounded errors without hanging all workers.
  6. p95 API latency and error rates are measured at 10, 50, and 100 concurrent clients; record hardware and data volume.
  7. Migration from schema v1 to v2 succeeds with old/new application versions overlapping.
  8. Demonstrate restore rehearsal on a disposable database; document RTO/RPO measured in your environment.

Troubleshooting Playbooks

Playbook A — API latency jumps from 80 ms to 2 seconds

Symptoms: p95 increases, connection wait queue grows, CPU may remain low. Investigate: request tracing → pool acquisition time → DB query duration → pg_stat_activity waits → pg_stat_statements → EXPLAIN (ANALYZE, BUFFERS) on representative SELECT → RDS CloudWatch storage/CPU/network. Possible causes: locks, I/O, temp spills, connection exhaustion, DNS/TLS handshakes, slow downstream service. Mitigate: reduce traffic/concurrency, cancel offending query with authorization, restore index/plan, or roll back change. Verify: p95, error rate, queue depth, and DB health recover.

Playbook B — remaining connection slots are reserved

Investigate: SHOW max_connections; SELECT state,count(*) FROM pg_stat_activity GROUP BY state; Compare app replicas × workers × pool maximum, cron jobs, and deploy surge. Mitigate: stop leak/scale down safely, tune pools, shorten transactions; use supported proxy where useful. Prevent: pool acquisition metrics and connection-budget tests.

Playbook C — Deadlocks after a feature launch

Investigate: SQLSTATE 40P01, lock graphs in DB logs, update order across tables. Mitigate: bounded full-transaction retry; ensure consistent lock order and short transactions. Prevent: concurrency tests and no network calls inside critical transaction.

Playbook D — Query regression after data growth

Investigate: EXPLAIN estimated vs actual rows, table/index bloat, skew, stale statistics, missing predicate-aligned index. Mitigate: targeted index, query rewrite, ANALYZE, partition/archiving if justified. Prevent: realistic performance datasets and plan regression checks.

Playbook E — RDS connectivity fails

Investigate in order: DNS resolution → route/VPC/subnet → security group/NACL → port reachability → TLS CA/hostname → auth/IAM token lifetime → engine availability → max connections. nc -vz host 5432 checks TCP only, not TLS/auth. psql 'host=... dbname=... user=... sslmode=verify-full sslrootcert=...' tests full connection. Do not make a production DB publicly accessible as a quick fix.

Playbook F — ORM returns too many SQL statements

Investigate: SQL query count per request, lazy-loaded relations, join cardinality, pagination. Mitigate: DTO projections, batching, explicit eager loading appropriate to cardinality; benchmark memory and SQL count. Prevent: query-count assertions in integration tests.

Playbook G — Migration blocked during deploy

Investigate: active sessions, blockers, DDL lock type, transaction age. Mitigate: cancel/retry, split migration, create indexes concurrently, batch backfill. Prevent: rehearsal against production-like volume and lock-timeout budget.

Playbook H — TLS connection errors after certificate rotation

Investigate: trust-store contents, CA bundle age, client driver behavior, hostname verification, RDS certificate validity. Mitigate: distribute current trusted CA bundle and redeploy clients; never set sslmode=disable or disable verification to suppress the error. Prevent: certificate-expiration inventory and planned rotation tests.

Senior Engineering Interview Bank

The following scenarios require architecture reasoning, failure handling, and tradeoffs—not memorized definitions.

  1. Design an order system for 10k requests/sec. Start with real read/write mix, burst profile, order consistency, partitioning/tenant boundaries, connection limits, caching, and eventual scaling; never promise one RDS instance can handle unspecified workload.
  2. Explain PostgreSQL MVCC. Snapshot visibility, row versions, vacuum, long-running transactions, and write contention.
  3. Explain lost updates and prevention. Conditional UPDATE, row locks, optimistic version columns, or Serializable with retry.
  4. Choose Read Committed vs Serializable. Default often sufficient with atomic constraints; use Serializable for complex cross-row invariants, accepting retry overhead.
  5. Diagnose high CPU but low IOPS. Inspect expensive queries, sort/hash operations, parallelism, and application traffic.
  6. Diagnose high IOPS but low CPU. Look for random reads, cache misses, index design, large scans, and storage latency.
  7. What does a connection pool solve? Connection reuse and bounded concurrency; not query inefficiency or transaction correctness.
  8. Why can RDS Proxy pin sessions? Session-specific state or behaviors may require dedicated backend connection, limiting multiplexing.
  9. How do you handle a failover mid-transaction? Treat transaction outcome as uncertain until reconciled, reconnect, and retry only with idempotency.
  10. Why not store passwords in code? Source leakage, rotation difficulty, and excessive credential spread; use scoped secret management.
  11. How do you prove an index helps? Representative plans, buffer usage, latency distributions, and write-cost measurements.
  12. Explain index-only scan limitations. Visibility map and heap visibility checks can still require heap access.
  13. What is an N+1 query? One initial query plus N relation queries; solve with fetch planning/projections.
  14. How do you safely rename a column? Expand/dual-write/backfill/switch/contract over separate releases.
  15. What is an idempotency key? Stable identity for retryable logical request; enforce uniqueness and return consistent prior outcome.
  16. Why does OFFSET 100000 hurt? Database may still walk/discard skipped rows; keyset cursor can avoid large skips.
  17. How do you debug a deadlock? Gather lock graph and statements; standardize lock order and bounded retry.
  18. How do you prevent SQL injection? Bound parameters for values, allowlisted identifiers, least-privilege DB roles.
  19. Explain RDS vs Aurora. Both managed relational services; Aurora uses a different distributed storage architecture and engine compatibility; choose based on workload and cost.
  20. What makes a senior engineer's incident response strong? Impact assessment, evidence, safe mitigation, clear communication, validation, postmortem and prevention.
  21. When would you use JSONB? Flexible sparse attributes with controlled validation and access patterns, not core relational keys by default.
  22. Why is count(*) expensive on large tables? MVCC visibility means exact count may require scanning tuples/index entries; estimates may be sufficient for dashboards.
  23. How do you handle schema drift? Versioned migrations, CI checks, schema diff review, no manual untracked DDL.
  24. What is the outbox pattern? Persist business state and event intent in one DB transaction, publish asynchronously with deduplication.
  25. How do you decide pool size for 20 pods? Budget total connections including workers and surge, measure wait/hold times, and load-test.
  26. How does @Transactional work? Spring proxy and transaction manager; beware self-invocation and propagation.
  27. What is SQLAlchemy's identity map? Session caches one mapped object identity per DB row in its unit of work.
  28. Why must node-postgres transactions use one client? Transactions are connection-scoped; pool queries may use different backends.
  29. What does EXPLAIN cost mean? Relative planner estimates, not direct time units.
  30. How do you verify a backup? Restore to isolated instance, run integrity/application tests, measure restore duration and recovery point.

Glossary and Index

Glossary

  • ACID: atomicity, consistency, isolation, durability.
  • B-tree: balanced ordered index structure.
  • BRIN: block-range index useful for physically correlated large data.
  • CTE: common table expression using WITH.
  • DDL: data definition language (CREATE/ALTER/DROP).
  • DML: data manipulation language (SELECT/INSERT/UPDATE/DELETE).
  • Deadlock: cycle of transactions waiting on each other's locks.
  • DTO: data transfer object used at API boundaries.
  • GIN: generalized inverted index, e.g., for JSONB.
  • Idempotency: repeat request has the same logical effect as one request.
  • Index-only scan: index scan that can avoid many heap fetches when visibility permits.
  • Isolation: rules controlling concurrent transaction observations.
  • MVCC: multi-version concurrency control.
  • N+1: ORM access pattern issuing N extra relation queries.
  • Outbox: table storing event intent atomically with business changes.
  • PITR: point-in-time recovery.
  • RDS Proxy: managed database proxy supporting pooling for eligible engines/configurations.
  • RPO: recovery point objective, tolerated data loss window.
  • RTO: recovery time objective, target restoration duration.
  • SQLSTATE: standardized machine-readable database error code.
  • Sargability: predicate structure allowing efficient index access.
  • WAL: write-ahead log used for durability and recovery.
