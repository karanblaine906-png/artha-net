Learning outcomes

Build repeatable, testable and secure RDS environments; instrument application/database behavior; distinguish symptoms from causes; safely migrate schemas; plan and rehearse maintenance; automate guarded operations; and defend architecture choices during senior interviews.

  CI --> Approval{Approval and policy gates}
  Approval --> CD[CD: IaC deploy and migration job]

Chapter 31 — AWS CLI and boto3 automation

Mental model

AWS CLI and boto3 call the RDS control-plane API to create, modify, describe, snapshot and delete DB resources. SQL clients such as psql and psycopg talk to the database data plane. rds:DescribeDBInstances IAM permission does not grant SELECT in PostgreSQL; IAM database authentication is a separate feature requiring configuration and database permissions.

Prerequisites and safe identity

aws --version
aws sts get-caller-identity
aws configure list
export AWS_REGION=ap-south-1
export DB_ID=rds5-training-pg
aws rds describe-db-instances --region "$AWS_REGION" \
  --query 'DBInstances[].{ID:DBInstanceIdentifier,State:DBInstanceStatus,Engine:Engine,MultiAZ:MultiAZ}' --output table

Line by line: sts get-caller-identity confirms account and principal; configure list reveals credential/region sources; DB_ID isolates the lab resource; describe-db-instances is read-only; --query projects useful fields. Illustrative output: rds5-training-pg | available | postgres | False.

Guarded snapshot workflow

export SNAPSHOT_ID="${DB_ID}-manual-$(date -u +%Y%m%d%H%M%S)"
aws rds create-db-snapshot --db-instance-identifier "$DB_ID" \
  --db-snapshot-identifier "$SNAPSHOT_ID" --region "$AWS_REGION"
aws rds wait db-snapshot-available --db-snapshot-identifier "$SNAPSHOT_ID" --region "$AWS_REGION"
aws rds describe-db-snapshots --db-snapshot-identifier "$SNAPSHOT_ID" \
  --query 'DBSnapshots[0].{Status:Status,Encrypted:Encrypted,SizeGiB:AllocatedStorage}'

create-db-snapshot starts an asynchronous operation; wait polls until completion; the final query validates state. Snapshot creation can affect I/O depending on engine/storage and timing. Snapshot storage is billable. Never equate snapshot completion with a tested restore.

Production-oriented Python script: read-only inventory

#!/usr/bin/env python3
import json
import os
import boto3
from botocore.config import Config
from botocore.exceptions import ClientError, BotoCoreError

region = os.environ.get('AWS_REGION', 'ap-south-1')
client = boto3.client('rds', region_name=region,
                      config=Config(retries={'mode': 'standard', 'max_attempts': 8}))
try:
    for page in client.get_paginator('describe_db_instances').paginate():
        for db in page.get('DBInstances', []):
            print(json.dumps({
                'id': db['DBInstanceIdentifier'],
                'engine': db['Engine'],
                'status': db['DBInstanceStatus'],
                'encrypted': db.get('StorageEncrypted'),
                'multi_az': db.get('MultiAZ'),
                'public': db.get('PubliclyAccessible'),
            }))
except (ClientError, BotoCoreError) as exc:
    raise SystemExit(f'Inventory failed: {exc}')

Config controls retries; paginator avoids truncation; get tolerates optional fields; errors fail visibly rather than claiming success. Use roles/short-lived credentials, never hardcoded access keys.

Lab

  1. Verify principal and region. 2. Run read-only inventory. 3. Snapshot a disposable DB. 4. Wait and inspect encryption. 5. Restore snapshot to a new identifier in an approved isolated network. 6. Connect and verify a sentinel row. 7. Delete test resources only after explicit identifier/account confirmation.

Failure investigation

AccessDenied → inspect IAM/SCP/permission boundary; DBInstanceNotFound → account, region, identifier; InvalidDBInstanceState → pending operations; throttling → bounded exponential backoff; waiter timeout → inspect events and resource state. Never blindly retry non-idempotent create operations with new identifiers.

Chapter 32 — Terraform architecture and reusable modules

Core principles

Terraform builds a dependency graph and reconciles desired infrastructure state. Its state file may contain sensitive metadata; encrypt and restrict remote state. A saved plan must be reviewed in the same workspace and variable context in which it is applied. Drift detection is not database schema migration.

Directory design

infra/
  envs/dev/{main.tf,variables.tf,terraform.tfvars.example}
  envs/prod/{main.tf,variables.tf}
  modules/rds-postgres/{main.tf,variables.tf,outputs.tf}

Keep state isolated per environment/account, not just by branch. Production changes need peer review, policy gates and explicit approvals.

Minimal reusable module (illustrative, not production-complete)

# modules/rds-postgres/variables.tf
variable "identifier" { type = string }
variable "subnet_ids" { type = list(string) }
variable "security_group_ids" { type = list(string) }
variable "kms_key_arn" { type = string }
variable "instance_class" { type = string  default = "db.t4g.micro" }
variable "engine_version" { type = string }
variable "secret_arn" { type = string }

# modules/rds-postgres/main.tf
resource "aws_db_subnet_group" "this" {
  name       = "${var.identifier}-subnets"
  subnet_ids = var.subnet_ids
}
resource "aws_db_instance" "this" {
  identifier                 = var.identifier
  engine                     = "postgres"
  engine_version             = var.engine_version
  instance_class             = var.instance_class
  allocated_storage          = 20
  storage_type               = "gp3"
  db_subnet_group_name       = aws_db_subnet_group.this.name
  vpc_security_group_ids     = var.security_group_ids
  publicly_accessible        = false
  storage_encrypted          = true
  kms_key_id                 = var.kms_key_arn
  username                   = "app_admin"
  manage_master_user_password = true
  backup_retention_period    = 7
  deletion_protection        = true
  skip_final_snapshot        = false
  final_snapshot_identifier  = "${var.identifier}-final"
  apply_immediately          = false
}
output "endpoint" { value = aws_db_instance.this.address }
output "master_secret_arn" {
  value = aws_db_instance.this.master_user_secret[0].secret_arn
}

Review before applying: secret_arn is unused and should be removed or wired into a separate application integration. final_snapshot_identifier must be unique for each actual deletion; a fixed name can cause destroy failure. Engine/class/storage support varies by region/version. manage_master_user_password is supported only for compatible engines and configurations. Protect the generated secret and check whether its lifecycle/cost is acceptable. For a lab, deliberately disable deletion protection only after backup verification and approval.

Root module and commands

provider "aws" { region = "ap-south-1" }
module "postgres" {
  source             = "../../modules/rds-postgres"
  identifier         = "rds5-dev"
  subnet_ids         = var.private_subnet_ids
  security_group_ids = [var.db_sg_id]
  kms_key_arn        = var.kms_key_arn
  engine_version     = var.postgres_version
}

terraform fmt -recursive
terraform init
terraform validate
terraform plan -out=tfplan
terraform show tfplan
terraform apply tfplan
terraform state list

fmt standardizes syntax; init downloads providers and configures backend; validate checks structure; plan previews operations; show is a review gate; apply executes reviewed plan; state list inventories managed objects. Never publish plan/state files because they may include sensitive information.

Remote state and locking

Use an S3 backend with encryption, bucket versioning, restrictive IAM and state locking supported by your Terraform version (S3 lockfile where available). Older DynamoDB-based locking examples exist but are deprecated in newer Terraform versions. Configure the backend outside this snippet and validate behavior for the installed Terraform version. Avoid passing secrets via -var or committed tfvars.

Terraform troubleshooting

InvalidSubnet → wrong VPC/subnet IDs; subnet group lacking distinct AZs → select suitable subnets; InvalidParameterCombination → incompatible instance class/engine/version/storage; unexpected replacement → inspect plan carefully; drift → compare live state with code; locked state → identify the active operator, never force-unlock without coordination. Protect prod with deletion protection, backups and organization policy.

Chapter 33 — CloudFormation and AWS CDK

Choosing tools

CloudFormation uses declarative AWS resources and change sets; CDK synthesizes CloudFormation from code; Terraform uses provider resources and its own state. Use one clear ownership boundary per resource to avoid conflicting controllers.

CloudFormation starter

AWSTemplateFormatVersion: '2010-09-09'
Description: Minimal private PostgreSQL RDS starter
Parameters:
  DBSubnetGroupName:
    Type: String
  DBSecurityGroupId:
    Type: AWS::EC2::SecurityGroup::Id
  KmsKeyId:
    Type: String
  MasterUsername:
    Type: String
    Default: app_admin
Resources:
  Database:
    Type: AWS::RDS::DBInstance
    DeletionPolicy: Snapshot
    UpdateReplacePolicy: Snapshot
    Properties:
      DBInstanceIdentifier: rds5-cfn-dev
      Engine: postgres
      DBInstanceClass: db.t4g.micro
      AllocatedStorage: '20'
      StorageType: gp3
      StorageEncrypted: true
      KmsKeyId: !Ref KmsKeyId
      DBSubnetGroupName: !Ref DBSubnetGroupName
      VPCSecurityGroups: [!Ref DBSecurityGroupId]
      PubliclyAccessible: false
      MasterUsername: !Ref MasterUsername
      ManageMasterUserPassword: true
      BackupRetentionPeriod: 7
      DeletionProtection: true
Outputs:
  Endpoint:
    Value: !GetAtt Database.Endpoint.Address

DeletionPolicy protects data during stack deletion through a snapshot (check actual resource behavior); UpdateReplacePolicy addresses replacement. ManageMasterUserPassword avoids embedding a static secret. Parameterize names/classes/versions for real use and inspect change sets.

CDK TypeScript sketch

import * as cdk from 'aws-cdk-lib';
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import * as rds from 'aws-cdk-lib/aws-rds';
import { Construct } from 'constructs';
export class DatabaseStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props: cdk.StackProps & {vpc: ec2.IVpc}) {
    super(scope, id, props);
    new rds.DatabaseInstance(this, 'Postgres', {
      engine: rds.DatabaseInstanceEngine.postgres({
        version: rds.PostgresEngineVersion.VER_16
      }),
      vpc: props.vpc,
      vpcSubnets: {subnetType: ec2.SubnetType.PRIVATE_ISOLATED},
      credentials: rds.Credentials.fromGeneratedSecret('app_admin'),
      storageEncrypted: true,
      deletionProtection: true,
      removalPolicy: cdk.RemovalPolicy.SNAPSHOT,
    });
  }
}

Version-sensitive: CDK constants, supported PostgreSQL versions and constructs vary with the installed CDK release. Verify the code against that release. This sketch assumes a VPC with isolated subnets; app connectivity, security groups, KMS, backup and alarms still need configuration.

Lab and troubleshooting

Run cfn-lint on templates, aws cloudformation validate-template, create a change set and inspect replacements before execution. For CDK: npm ci, npx cdk synth, npx cdk diff, then gated deploy. If a stack rolls back, inspect stack events, resource events and CloudTrail; never repeatedly delete and recreate production databases to fix templates.

Chapter 34 — CI/CD, schema migrations and zero-downtime releases

Why database releases are different

App rollback can be seconds; schema rollback may destroy data or block writes. Prefer expand → migrate/backfill → switch → contract. Deploy backward-compatible schema first, release app code that supports both shapes, backfill in small idempotent batches, monitor, then remove old columns only after all readers and rollback windows have passed.

Example safe migration

-- Phase A: expand, low-risk metadata change (verify version/locking)
ALTER TABLE customers ADD COLUMN display_name text;
-- Phase B: backfill incrementally in an application worker, not one huge transaction
-- Phase C: add constraints only after validation and application rollout
ALTER TABLE customers ADD CONSTRAINT display_name_present
  CHECK (display_name IS NOT NULL) NOT VALID;
ALTER TABLE customers VALIDATE CONSTRAINT display_name_present;

A NOT VALID check avoids scanning existing rows during initial creation, but still enforces new/updated rows; validation can consume I/O and locks. An application must populate the field before enabling the check for new writes. Do not run this unchanged if legacy writers cannot provide display_name.

Alembic migration command

alembic revision --autogenerate -m "add customer display name"
alembic upgrade head
alembic current

Autogeneration is a draft: manually inspect type changes, data loss, indexes, locks and downgrade safety. Run migrations once as a dedicated job with bounded timeout and deployment coordination; do not let every application replica race to migrate.

GitHub Actions illustrative pipeline

name: database-release
on:
  workflow_dispatch:
  pull_request:
jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: python -m pip install -r requirements-dev.txt
      - run: pytest -q
      - run: alembic check

Pin actions to trusted commit SHAs in regulated/production environments, add SAST and dependency scanning, and keep the example read-only on pull requests. For deployment, use OIDC federation to a narrowly scoped AWS role and a private-network migration runner (CodeBuild in VPC, ECS task, or approved runner). Never expose RDS publicly just to let a hosted CI runner connect.

Release gates

Schema compatibility tests; EXPLAIN plans; estimated lock duration; backup/restore confidence; pre-deploy baseline; migration timeout; on-call ownership; feature flags; canary; rollback strategy; post-deploy error/latency metrics. For large tables consider concurrent index creation where supported, with its special transaction restrictions.

Troubleshooting

Migration waiting → pg_stat_activity/lock graph; app errors after deploy → incompatible SQL/ORM model; high WAL/replica lag → large backfill; deploy blocked by long transaction → inspect blockers and terminate only with incident approval. Do not auto-rollback destructive migrations.

Chapter 35 — CloudWatch, Database Insights and observability

Three telemetry layers

Infrastructure: CPUUtilization, FreeableMemory, FreeStorageSpace, ReadIOPS/WriteIOPS, ReadLatency/WriteLatency, DiskQueueDepth, DatabaseConnections. Engine: pg_stat_activity, pg_stat_statements, wait events, autovacuum, locks, replication. Application: p50/p95/p99 request latency, errors, pool saturation, query counts, traces. Correlate by time, deployment, AZ and workload; a high CPU graph alone does not prove the database is the bottleneck.

CLI metrics inspection

aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS --metric-name CPUUtilization \
  --dimensions Name=DBInstanceIdentifier,Value="$DB_ID" \
  --statistics Average Maximum --period 300 \
  --start-time 2026-10-15T00:00:00Z --end-time 2026-10-15T01:00:00Z

The timestamps are examples, replace with a relevant incident window. Metrics can be delayed and datapoints may be missing. For automated dashboards use get-metric-data with aligned windows and pagination.

PostgreSQL diagnostic SQL

SELECT now(), state, wait_event_type, wait_event, count(*)
FROM pg_stat_activity GROUP BY 1,2,3,4 ORDER BY 5 DESC;
SELECT datname, numbackends, xact_commit, xact_rollback,
       blks_read, blks_hit, deadlocks
FROM pg_stat_database ORDER BY datname;
SELECT pid, usename, state, now()-xact_start AS transaction_age,
       wait_event_type, wait_event, left(query, 160) AS query_excerpt
FROM pg_stat_activity WHERE xact_start IS NOT NULL
ORDER BY transaction_age DESC;

pg_stat_activity exposes active backend state; long-lived idle-in-transaction sessions are especially risky. pg_stat_database counters are cumulative since reset, so compute rates/deltas, not just raw totals. Query text may contain sensitive values: restrict logging and access.

Database Insights and legacy tooling

AWS has evolved RDS observability features, including Database Insights and Performance Insights transition timelines. Before enabling a paid observability tier or relying on a legacy console page, verify current engine support, retention, IAM, and charges in official documentation. Enhanced Monitoring is distinct from CloudWatch basic metrics and from database query instrumentation.

Alarm design

Use SLO-linked thresholds, multiple evaluation periods and composite signals. Example: sustained low FreeStorageSpace + growth trend + write errors is stronger than a single storage datapoint. Page for user impact; ticket for gradual capacity drift. Configure SNS routing, runbook URL and ownership. Test alarm delivery end-to-end.

Lab

  1. Generate a controlled read workload. 2. Capture baseline metrics. 3. Add a deliberately inefficient query in test. 4. Compare EXPLAIN, latency, DB CPU and waits. 5. Create an alarm with an intentionally safe test threshold. 6. Restore threshold and document what actually triggered.

Chapter 36 — Performance diagnostics and incident response

Diagnostic order

  1. Confirm user impact and onset. 2. Check deployment/change timeline. 3. Compare request latency with pool wait and SQL duration. 4. Check DB status, failover events, connections, CPU, memory, I/O latency, queue depth. 5. Inspect engine waits, blockers and top SQL. 6. Apply lowest-risk mitigation. 7. Verify recovery and write a blameless postmortem.

EXPLAIN lab

CREATE TABLE orders_perf (
 id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
 customer_id bigint NOT NULL,
 created_at timestamptz NOT NULL DEFAULT now(),
 amount numeric(12,2) NOT NULL
);
INSERT INTO orders_perf(customer_id,created_at,amount)
SELECT (random()*10000)::bigint,
       now() - (random()*interval '365 days'),
       (random()*1000)::numeric(12,2)
FROM generate_series(1,100000);
ANALYZE orders_perf;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders_perf WHERE customer_id=123
ORDER BY created_at DESC LIMIT 20;
CREATE INDEX CONCURRENTLY idx_orders_customer_created
ON orders_perf(customer_id,created_at DESC);
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders_perf WHERE customer_id=123
ORDER BY created_at DESC LIMIT 20;

Lab caution: CREATE INDEX CONCURRENTLY must run outside an explicit transaction block. It reduces write blocking but takes time/resources and may leave an invalid index if interrupted. EXPLAIN ANALYZE executes the query; use caution for DML. Compare actual time, rows, buffers, sort and index usage rather than assuming every index helps.

Blocking analysis

SELECT blocked.pid AS blocked_pid, blocking.pid AS blocking_pid,
       blocked.wait_event_type, blocked.wait_event,
       now()-blocking.xact_start AS blocker_age,
       left(blocking.query,120) AS blocker_query
FROM pg_stat_activity blocked
JOIN LATERAL unnest(pg_blocking_pids(blocked.pid)) AS blocker_pid(pid) ON true
JOIN pg_stat_activity blocking ON blocking.pid=blocker_pid.pid;

pg_blocking_pids exposes blockers. Terminating sessions can roll back transactions and cause app errors; first identify owner, impact and safe alternative.

Incident playbooks

Connections exhausted: check pool sizes × replicas, idle sessions, leak patterns, max_connections, RDS Proxy pinning; reduce concurrency and fix leaks before raising connection limits. CPU high: inspect top SQL and wait mix; optimize query or scale based on evidence. I/O high: check scans, checkpoints, WAL, maintenance, gp3 baseline/allocated IOPS; do not conflate IOPS with latency. Storage low: examine table/index growth, WAL retention, replication slots, temporary files and backups; consider storage autoscaling limits. Replication lag: assess primary write volume, replica CPU/I/O and long queries; stale reads must be handled at application level.

Example incident record

Impact: checkout p99 increased from 180 ms to 3.2 s (illustrative). Hypothesis: index regression after migration. Evidence: query plan changed to sequential scan; buffers read and CPU rose; connection pool waiting increased secondarily. Mitigation: safe index addition, throttle writes during build, verify plan, monitor replica lag. Prevention: query-plan review, regression load test, alert on pool wait.

Chapter 37 — Upgrades, maintenance and patching

Separate change types

Minor engine patch, major engine upgrade, instance class resize, storage change, parameter group modification, certificate rotation and OS maintenance have different downtime/rollback implications. Maintenance window does not mean zero downtime. apply_immediately can schedule an interruption now. Test exact engine upgrade paths and extension compatibility.

Upgrade preflight

Inventory engine versions, extension versions, parameter groups, option groups, client drivers, replication topology, backup retention, PITR, storage headroom, long-running transactions, compatibility, failover configuration and rollback requirements. Rehearse restore or blue/green where supported. Record RTO/RPO and cutover decision owners.

CLI review

aws rds describe-db-instances --db-instance-identifier "$DB_ID" \
  --query 'DBInstances[0].{Version:EngineVersion,Status:DBInstanceStatus,Pending:PendingModifiedValues,Window:PreferredMaintenanceWindow}'
aws rds describe-pending-maintenance-actions --filters Name=db-instance-id,Values="$DB_ID"
aws rds describe-events --source-type db-instance --source-identifier "$DB_ID" --duration 1440

PendingModifiedValues reveals queued changes; maintenance actions and events help reconstruct activity. Review supported versions with describe-db-engine-versions and engine release notes.

Parameter management

Use custom DB parameter groups for controlled tuning; distinguish dynamic parameters from static parameters requiring restart. Store changes in code; measure before/after; avoid copying values between instance classes. Example: increasing work_mem can multiply memory use per sort/hash operation and per concurrent query, potentially causing OOM.

Upgrade runbook

T-7d compatibility and restore test → T-1d stakeholder notification and freeze → T-1h backups and baseline → change window with on-call/rollback owner → validate connections, writes, read paths, replicas and latency → monitor 24h → post-change review. A restored pre-upgrade snapshot may imply lost post-snapshot writes; treat rollback as a data-recovery decision, not a button.

Chapter 38 — Automated operations and event-driven runbooks

Event-driven design

RDS events / CloudWatch alarms → EventBridge or SNS → guarded Lambda/Step Functions workflow → approval gate (for destructive actions) → AWS API → verification → ticket and audit log. Use idempotency keys, concurrency controls, retries with backoff, dead-letter handling, and rate limits.

Lambda read-only triage example

import json
import os
import boto3

rds = boto3.client('rds')

def lambda_handler(event, context):
    db_id = os.environ['DB_INSTANCE_ID']
    response = rds.describe_db_instances(DBInstanceIdentifier=db_id)
    db = response['DBInstances'][0]
    report = {
        'db': db_id,
        'status': db['DBInstanceStatus'],
        'multi_az': db.get('MultiAZ', False),
        'pending': db.get('PendingModifiedValues', {}),
        'event_type': event.get('detail-type', 'unknown'),
    }
    print(json.dumps(report, default=str))
    return report

Keep environment configuration trusted, IAM restricted to the target ARN where supported, and redact secrets. The Lambda is read-only: it does not trigger failover or modify storage. Production workflows should correlate alert IDs, enrich with recent metrics/events and suppress duplicates.

Dangerous automation anti-patterns

Auto-rebooting on every CPU spike; terminating all slow queries; deleting snapshots by age without retention/legal review; modifying security groups to 0.0.0.0/0; scaling without cost guardrails; auto-failing over during an ambiguous network event. Prefer safe diagnostics first and explicit approval for impactful changes.

Lab

Create a test CloudWatch alarm → SNS subscription or EventBridge rule → Lambda with read-only DescribeDBInstances permission → emit structured log → validate delivery and duplicate handling → disable test rule. Document what happens when Lambda fails or AWS API throttles.

Chapter 39 — Cost optimization and governance

Cost components

DB instance-hours (class, deployment type), provisioned storage, extra provisioned IOPS/throughput where applicable, backup/snapshot storage beyond free allowances, cross-region data transfer, RDS Proxy, Secrets Manager, monitoring tiers, logs and networking (NAT gateways, endpoints). Aurora and RDS PostgreSQL pricing models differ. Never assume a single universal free tier or fixed price: inspect the region-specific AWS pricing calculator and account offers.

Optimization method

  1. Attribute spend by environment/team/product tags. 2. Measure CPU, memory, IOPS, latency, connections, read/write patterns and growth. 3. Right-size test environments and choose suitable instance families. 4. Schedule nonproduction stop/start where allowed (RDS automatically restarts stopped instances after a limited period). 5. Remove orphan snapshots only after retention approval. 6. Compare storage types and backup retention. 7. Evaluate Reserved DB Instances for stable usage; assess term/payment and eligible engines. 8. Revalidate resilience requirements before downsizing.

Cost worksheet

Monthly estimate = compute + storage + extra IOPS/throughput
                 + backup/snapshot + monitoring + proxy
                 + cross-region transfer + networking + tax

Example hypothetical, not an AWS quote: compute $180, storage $45, backups $12, monitoring $18, networking $25 = $280/month. Validate real prices in AWS Pricing Calculator. Include Multi-AZ/replicas, idle environments and restore tests in TCO.

Governance controls

Mandatory tags; AWS Budgets and anomaly detection; SCP restrictions on public RDS where appropriate; approved KMS keys; deletion protection; backup policies; drift scans; periodic IAM review; data classification; documented ownership; break-glass access; cost and security exceptions with expiry dates.

Senior trade-off

Senior Software Engineer interview questions and model answers

Q1. How does an RDS control-plane API differ from SQL? AWS RDS APIs manage cloud resources; SQL operates on engine data and roles. They have different permissions, audit trails and failure domains.

Q2. Why should Terraform state be protected? It records infrastructure identifiers and may include sensitive attributes. Encrypt, restrict, version and lock it; never commit state or plan artifacts.

Q3. How would you prevent accidental production deletion? RDS deletion protection, backup policies, approval gates, resource-specific IAM/SCP, IaC policy checks and rehearsed restore procedures.

Q4. Why can a terraform apply be unsafe even when syntax validates? Provider changes can replace resources, drift can alter effects, and runtime constraints/costs are not guaranteed by syntax validation.

Q5. When would you choose CloudFormation/CDK instead of Terraform? Existing AWS-native stack ownership, organization skillset, policy tooling and change-set workflow may favor them; Terraform helps with provider ecosystems and modules. Avoid dual ownership.

Q6. How do you migrate a populated table without downtime? Expand schema compatibly, deploy dual-compatible app, backfill in batches, validate, cut over reads/writes and contract after rollback window.

Q7. Why not run migrations on every app startup? Replica races, locks, uncontrolled rollout timing and permission sprawl. Use a single gated migration job.

Q8. What makes an index build risky? I/O/CPU load, WAL generation, lock behavior, replica lag, disk consumption and failure cleanup; evaluate concurrently where supported.

Q9. What is the difference between CPU saturation and lock contention? CPU saturation spends cycles executing work; lock contention waits on holders. Wait events and blocked-session graphs distinguish them.

Q10. Why is connection count not equal to useful concurrency? Idle/blocked backends consume slots and memory; application pools can queue; DB throughput may fall under excessive active concurrency.

Q11. Which RDS metrics would you use for slow queries? Correlate application latency with query timings, engine waits, CPU, I/O latency, queue depth, memory and connection saturation.

Q12. Why are CloudWatch metric averages insufficient? Averages hide bursts and tail latency. Compare maxima, percentiles where applicable, distributions and request-level traces.

Q13. What is pg_stat_statements useful for? Aggregated query statistics identify high-total-time or frequent SQL; extension enablement and permissions must be configured appropriately.

Q14. How would you debug a deadlock? Inspect engine deadlock logs, conflicting transaction order, lock modes and application retry semantics; establish consistent lock order and short transactions.

Q15. Why can raising work_mem be dangerous? Memory use multiplies across operations and concurrent sessions; overcommit can destabilize the database.

Q16. How do you plan a major PostgreSQL upgrade? Check supported paths/extensions/drivers, restore/rollback strategy, rehearsal, cutover, replication, downtime, monitoring and data-loss tradeoffs.

Q17. What is a safe rollback after destructive migration? Often there is no trivial rollback; use forward repair or carefully planned restore with reconciliation of post-backup writes.

Q18. Why shouldn't Lambda automatically reboot RDS on CPU alarms? CPU may be caused by legitimate work or lock/IO symptoms; reboot risks downtime and hides evidence.

Q19. What does idempotency mean for automation? Repeated execution should not create unintended duplicate side effects; use stable resource identifiers, guards and state checks.

Q20. How would you secure CI access to AWS? Short-lived OIDC role assumption, minimal permissions, protected environments, approval gates, audit logs and no static cloud keys.

Q21. Why is a publicly accessible RDS endpoint risky? It expands network exposure; use private subnets, tight SGs and controlled administrative access.

Q22. What is RDS Proxy good for? It can help manage bursts and reuse database connections, but transaction/session pinning and query cost can limit benefits.

Q23. How do you distinguish read replica lag from slow primary queries? Inspect replica lag metrics, replication state, primary WAL volume, replica resource pressure and workload routing.

Q24. How do you verify PITR readiness? Restore to a new isolated instance at a selected timestamp, validate consistency and measure recovery time, rather than relying only on retention settings.

Q25. What is RTO versus RPO? RTO is acceptable recovery duration; RPO is acceptable data-loss window. Both require measured exercises.

Q26. How do you optimize RDS cost without risking availability? Use utilization trends, workload benchmarks and budget models; preserve HA, backups, security and latency SLOs.

Q27. What causes sudden cost increases? Scale-up, replica growth, extra storage/IOPS, snapshot retention, cross-region transfer, paid observability or network costs.

Q28. What would you include in an RDS operational readiness review? Ownership, IAM, network, encryption, backups, RTO/RPO, runbooks, SLOs, alarms, maintenance, cost, change management and restore evidence.

Q29. How do you design a failover test? Define blast radius and approvals, baseline error/latency, execute supported test mechanism, measure recovery, validate writes and rollback/follow-up.

Q30. How do you present a production incident in an interview? State impact, detection, timeline, hypotheses, evidence, mitigation, validation, root causes, prevention and measurable outcomes without inventing results.

Scenario-based practical interview drills

Scenario A: API p99 rises after deployment

Collect deploy timestamps, request traces, pool wait, DB connections, query plans and wait events. Compare pre/post SQL shapes. Mitigate via feature flag or safe query fix; avoid blind instance resize. Verify p99 and error rate.

Scenario B: Storage drops rapidly

Inspect table/index growth, WAL/replication slots, temp files, logs and maintenance; review storage autoscaling/max threshold and growth forecast. Stop runaway workload if necessary; coordinate expansion and recovery.

Scenario C: Terraform wants to replace production RDS

Stop pipeline. Inspect attribute diff, provider/module changes, state drift and lifecycle settings. Never apply until data safety, replacement need and recovery plan are approved.

Scenario D: Migration blocks checkout

Identify blockers via pg_blocking_pids, check lock timeout and transaction age; cancel migration safely if possible. Redesign with staged schema and smaller backfill batches; rerun in controlled window.

Scenario E: A new instance is cheaper but slower

Compare representative workload p95/p99, CPU, memory, storage I/O, network, failover behavior and reserved pricing. Quantify total cost of latency and operational risk.

Glossary

  • ACID: Atomicity, consistency, isolation, durability.
  • ARN: Amazon Resource Name.
  • Backfill: Populate new schema fields for existing rows.
  • Change set: Preview of proposed CloudFormation stack changes.
  • Control plane: AWS APIs for resource management.
  • Data plane: SQL protocol and database reads/writes.
  • Drift: Difference between IaC state/configuration and live infrastructure.
  • Enhanced Monitoring: RDS OS-level monitoring feature.
  • IaC: Infrastructure as Code.
  • Idempotency: Safe repeated execution without duplicate unintended effects.
  • KMS: AWS Key Management Service.
  • MVCC: Multi-Version Concurrency Control.
  • OIDC: OpenID Connect federation for short-lived identity.
  • PITR: Point-in-time recovery.
  • p99: 99th percentile of a latency distribution.
  • RDS Proxy: Managed database connection proxy service.
  • RPO: Recovery Point Objective.
  • RTO: Recovery Time Objective.
  • SLO: Service Level Objective.
  • WAL: Write-ahead log in PostgreSQL.
