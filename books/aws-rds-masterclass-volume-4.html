Chapter 22 — Storage architecture, gp3/io1/io2, IOPS and latency

Concepts and internal mechanisms

An RDS database is not merely an EC2 VM plus a disk. RDS manages the DB instance lifecycle and storage integration. For traditional RDS engines, storage is provisioned independently from instance compute and typically backed by managed block-storage technologies. Aurora uses a fundamentally different distributed cluster storage design, covered later.

Four critical metrics: IOPS = completed I/O operations per second; throughput = bytes transferred per second; latency = time to complete an operation; queue depth = outstanding operations. These are related but not interchangeable. 8 KiB random reads at 10,000 IOPS yield approximately 78 MiB/s of payload, whereas large sequential I/O may hit throughput ceilings before IOPS ceilings. Real workload behavior also depends on cache hits, page size, WAL flushes, concurrency and engine internals.

Storage classes: gp3 is general-purpose SSD with independently provisionable performance subject to AWS-specific limits and configuration rules; io1/io2 are provisioned-IOPS SSD options for workloads requiring more predictable I/O performance, with io2 Block Express support dependent on deployment and engine. Never assume a particular IOPS-to-GiB ratio or maximum without checking the engine/region/storage configuration. Storage autoscaling increases allocated storage when thresholds are met; it does not reduce storage and is not a cure for runaway writes.

Inside a commit: client issues COMMIT → engine generates WAL/redo records → durable logging requirements are met → transaction can be acknowledged. Data pages may be flushed later. In a Multi-AZ instance deployment, the durability path also depends on the synchronous standby mechanism. Distinguish application-perceived commit latency from disk-level write latency.

Lab: record a baseline before changing anything. Use aws rds describe-db-instances --db-instance-identifier "$DB_ID" --query 'DBInstances[0].{Storage:StorageType,GiB:AllocatedStorage,IOPS:Iops,Throughput:StorageThroughput,AZ:AvailabilityZone}'. Compare CloudWatch ReadIOPS, WriteIOPS, ReadLatency, WriteLatency, ReadThroughput, WriteThroughput, DiskQueueDepth, FreeStorageSpace and FreeableMemory. Correlate with PostgreSQL pg_stat_database, pg_stat_bgwriter/pg_stat_checkpointer (version dependent), pg_stat_wal, and pg_stat_statements when enabled.

Decision rule: If latency is high but IOPS low, investigate lock waits, query plans, connection saturation and application latency before purchasing more IOPS. If latency and queue depth rise together under sustained storage load, test a suitable storage/performance upgrade after checking workload and cost.

Chapter 23 — Multi-AZ DB instances and Multi-AZ DB clusters

Concepts and internal mechanisms

Multi-AZ DB instance: one writer in one AZ and a synchronously replicated standby in another AZ. The standby is not a normal read endpoint. RDS detects qualifying failures and performs a managed failover. Applications should connect via the DB endpoint hostname and must reconnect/retry appropriately after DNS and connection transitions.

Multi-AZ DB cluster: supported RDS engines/configurations use a writer and two readable standby instances across three AZs, with different replication/failover mechanics and reader access from a classic Multi-AZ DB instance. It is not the same as Aurora, even though both have writer/reader concepts. Confirm engine version, region, limitations and pricing.

What HA is not: Multi-AZ does not guarantee zero downtime, zero lost transactions under every conceivable failure, protection against accidental DROP TABLE, immunity to regional failure, or an automatic solution to application retry logic.

Application sequence: (1) open connection with reasonable timeouts, (2) begin transaction, (3) issue SQL, (4) commit, (5) on network error or failover, discard broken connection and retry only when operation is safe. For non-idempotent payments, use an idempotency key and verify committed state before replaying.

Failure timeline: detection → promotion/role transition → DNS/endpoint changes → client DNS refresh and reconnection → application recovery. The total user-visible outage includes every stage. Do not promise a fixed failover duration; measure it.

CLI inspection: aws rds describe-db-instances --db-instance-identifier "$DB_ID" --query 'DBInstances[0].{MultiAZ:MultiAZ,Endpoint:Endpoint.Address,AZ:AvailabilityZone,SecondaryAZ:SecondaryAvailabilityZone,Status:DBInstanceStatus}'.

Safe nonproduction test: aws rds reboot-db-instance --db-instance-identifier "$DB_ID" --force-failover applies to supported Multi-AZ DB instance configurations. Do not assume it applies to Multi-AZ DB clusters or Aurora; use the deployment-specific failover API. Run only with change approval, telemetry and a recovery plan.

Verification: continuously issue a read and an idempotent write from the application, record request errors, connection recovery time, DB event notifications and DNS behavior. Verify committed records after recovery.

Chapter 24 — Read replicas and replication internals

Concepts and internal mechanisms

Core distinction: High availability and read scaling are different requirements. A read replica may serve reads and support a promotion strategy, but standard asynchronous read replication introduces lag and does not provide strong read-after-write guarantees on replica reads.

Physical versus logical replication: PostgreSQL physical replication replays WAL and preserves physical database state; logical replication streams selected data changes using publication/subscription semantics, with different DDL and conflict considerations. RDS read replica implementation varies by engine and deployment. MySQL uses engine-specific binary log replication approaches. Aurora readers consume the shared Aurora cluster storage architecture rather than being identical to conventional RDS read replicas.

Why lag happens: primary write throughput exceeds replica replay capacity; long-running queries on a replica; network interruption; storage pressure; large transactions; CPU saturation; vacuum and replay conflicts. ReplicaLag is a useful signal but is not a complete proof of transaction-level freshness.

Read routing: write requests and consistency-sensitive reads go to the writer; analytics/search and eventually consistent reads may use replicas. For a user who just updated a profile, route the immediate read to the writer or implement a consistency-aware strategy.

Lab: create a test replica through the console or an engine-supported aws rds create-db-instance-read-replica --db-instance-identifier "$REPLICA_ID" --source-db-instance-identifier "$DB_ID" with appropriate subnet, encryption, region and configuration. Wait for available, then compare a marker inserted on the primary with its visibility on the replica. Inspect aws rds describe-db-instances --db-instance-identifier "$REPLICA_ID" --query 'DBInstances[0].{Status:DBInstanceStatus,Source:ReadReplicaSourceDBInstanceIdentifier,Endpoint:Endpoint.Address}'.

Promotion: aws rds promote-read-replica --db-instance-identifier "$REPLICA_ID" is a disruptive topology change, not an automatic failback plan. Validate replica catch-up, application write routing, data reconciliation and old-writer fencing. Cross-region read replicas have added network, compliance and recovery concerns.

Chapter 25 — Automated backups, snapshots and PITR

Concepts and internal mechanisms

Automated backups support recovery to a point within the configured retention window by combining backups with transaction logs as supported by the engine. Manual snapshots are explicitly retained until deleted and capture a restorable database state. PITR creates a new DB instance/cluster at the selected recoverable point; it does not rewind the original in place.

RPO versus backup frequency: A nightly snapshot alone may imply substantial data loss. PITR can provide a much smaller recoverable gap within the available log/restore constraints, but LatestRestorableTime and engine behavior govern the actual latest point. Always inspect rather than assume zero RPO.

CLI: aws rds describe-db-instances --db-instance-identifier "$DB_ID" --query 'DBInstances[0].{Retention:BackupRetentionPeriod,LatestRestorableTime:LatestRestorableTime,Encrypted:StorageEncrypted}'; aws rds create-db-snapshot --db-instance-identifier "$DB_ID" --db-snapshot-identifier "$SNAPSHOT_ID"; aws rds describe-db-snapshots --db-snapshot-identifier "$SNAPSHOT_ID".

PITR drill: inject an unmistakable test row at T1, record time T2, intentionally delete it at T3 in a nonproduction DB, then restore to a valid point between T1 and T3 using aws rds restore-db-instance-to-point-in-time --source-db-instance-identifier "$DB_ID" --target-db-instance-identifier "$RESTORE_ID" --restore-time '2026-10-01T10:05:00Z' (example timestamp; substitute a real time inside the retention window). Restore may require explicit networking, security and parameter settings. Wait until available, connect to the new endpoint and verify the row.

Snapshot restore: aws rds restore-db-instance-from-db-snapshot --db-instance-identifier "$RESTORE_ID" --db-snapshot-identifier "$SNAPSHOT_ID" --db-instance-class db.t3.medium is illustrative; verify supported classes, encryption/KMS access and other required settings.

Critical runbook: create isolated restore → verify schema/data counts and app smoke tests → reconcile post-restore transactions → choose cutover and rollback approach → update secrets/endpoints → monitor. Backup success is not recovery success. Run regular restore drills, verify backup access across accounts and preserve immutable/offline protections where appropriate.

Chapter 26 — DR strategy, cross-region replication and RTO/RPO

Concepts and internal mechanisms

RTO is maximum acceptable time to restore service. RPO is maximum acceptable data loss measured in time. They are business targets, not properties you get merely by checking Multi-AZ.

Example: last recoverable committed transaction at 13:56, disaster at 14:00, recovered service at 14:42. Observed RPO = 4 minutes and RTO = 42 minutes. Compare with contractual objectives such as RPO ≤ 5 minutes and RTO ≤ 60 minutes; use actual incident measurements, not vendor averages.

DR patterns: backup-and-restore (lower ongoing cost, longer RTO); pilot light (core data/infra warm); warm standby (reduced recovery time, ongoing cost); active-active (complex consistency/conflict management and higher operational cost). Cross-region read replica or Aurora Global Database may reduce recovery times for suitable engines but still require promotion, write fencing, DNS, credentials, networking, application readiness and data-loss assessment.

Region failure checklist: determine blast radius → declare incident → freeze conflicting writes → establish replica freshness or last restorable point → promote/restore target → verify data and security → route application traffic → smoke test → reconcile pending transactions → announce status → document new primary and failback strategy.

Data correctness: If an old writer becomes reachable after a region failover, prevent split-brain writes. Payment/order systems should use durable request IDs and downstream reconciliation. Avoid claiming asynchronous cross-region replication has zero RPO.

Security: replicate or reconstruct required secrets, KMS permissions, IAM policies, parameter groups, network controls, observability and backup retention. A restored encrypted snapshot requires appropriate KMS key access. Test cross-account/cross-region copy requirements in advance.

Exercise: draw the dependency graph for API, DB, Secrets Manager, DNS, queue, object storage and identity. Assign RTO/RPO per dependency, then run a tabletop scenario where the primary region is unavailable and one replica is 90 seconds behind.

Chapter 27 — Vertical/read scaling and capacity planning

Concepts and internal mechanisms

Vertical scaling changes DB instance class to add CPU/memory/network capacity, potentially with a maintenance interruption or failover depending on configuration. Read scaling adds read capacity through replicas or reader instances where supported; it does not increase writer throughput or solve hot-row contention. Sharding can distribute writes but creates complex query, transaction and operational tradeoffs.

Capacity model: Estimate peak requests/s × SQL statements/request × average execution time, then apply concurrency/queueing reasoning. Little's Law: L = λW, where L is average in-flight work, λ is throughput and W is mean response time in consistent units. Example: 800 DB operations/s × 0.025 s = 20 concurrent in-flight operations on average, not necessarily 20 DB connections. Pool sizing must account for think time, blocking, multiple services and resource limits.

Performance priorities: measure query plans and indexes first; eliminate N+1 queries; batch writes carefully; avoid long transactions; right-size connection pools; add caching with explicit consistency semantics; then evaluate class/storage/read scaling. Oversized connection pools often increase memory pressure and contention.

Planning worksheet: capture peak QPS/TPS, p50/p95/p99 SQL latency, CPU, freeable memory, connections, WAL generation, IOPS, storage growth per day, replication lag, lock waits, and backup restore time. Model 30/90/365-day growth and test 2× peak workload.

CLI resize example: aws rds modify-db-instance --db-instance-identifier "$DB_ID" --db-instance-class db.m6i.large --apply-immediately (class illustrative, may not be supported for selected engine/region; can cause disruption). Prefer a reviewed change window and tested rollback strategy. Note that downsizing storage is not a normal RDS operation.

Chapter 28 — Amazon Aurora and Aurora Serverless

Concepts and internal mechanisms

Aurora is a MySQL/PostgreSQL-compatible managed relational database family with a distributed, fault-tolerant storage layer. Its compute instances connect to a cluster storage volume replicated across multiple AZs; Aurora reader instances share the cluster storage rather than maintaining completely separate conventional DB volumes. Storage-level replication is not the same thing as SQL transaction replication to a normal RDS read replica.

Endpoints: cluster/writer endpoint routes to the current writer; reader endpoint balances connections across available readers, but does not guarantee per-query load balancing or read-your-writes; instance endpoints address individual instances; custom endpoints can target selected groups. DNS changes and pooled connections require failover-aware behavior.

Aurora Serverless v2: adjusts compute capacity within configured minimum/maximum ACU ranges, subject to supported engine versions and deployment configurations. It is not an automatic guarantee of unlimited scaling, no cold-start effects, or zero cost when idle. Inspect scaling, connection limits, workload variability and pricing.

Aurora Global Database: provides cross-region architecture for supported Aurora configurations, with asynchronous replication to secondary regions and defined switchover/failover operations. Understand planned switchover versus unplanned failover and data-loss implications.

Selection matrix: conventional RDS PostgreSQL is attractive for familiar PostgreSQL behavior and straightforward operations; RDS Multi-AZ DB cluster may offer HA plus readable standbys on supported engines; Aurora is attractive when its storage architecture, failover/read scaling, features or Global Database meet requirements; Serverless v2 can help variable demand. Benchmark your workload and validate extension/engine compatibility, pricing and migration complexity.

Inspection: aws rds describe-db-clusters --db-cluster-identifier "$CLUSTER_ID" --query 'DBClusters[0].{Engine:Engine,Writer:Endpoint,Reader:ReaderEndpoint,Members:DBClusterMembers,StorageEncrypted:StorageEncrypted}'.

Common misconception: Aurora storage resilience does not replace backups, application idempotency, monitoring or DR testing.

Chapter 29 — Production failure simulations and runbooks

Lab prerequisites and safety

Use a dedicated sandbox AWS account and a disposable PostgreSQL RDS instance. Choose a region and engine version supported by your account. Use private subnets, restrictive security groups, IAM least privilege, encryption, deletion protection where appropriate, a budget alarm and tagged resources. Set environment variables AWS_REGION, DB_ID, REPLICA_ID, SNAPSHOT_ID, RESTORE_ID, CLUSTER_ID only after confirming actual identifiers. Commands beginning with aws rds run from a workstation or CI runner with configured AWS CLI credentials; SQL runs inside psql against the intended database. Do not paste placeholder names or timestamps unchanged.

Lab A — Observe Multi-AZ failover

  1. Confirm instance Multi-AZ status and application endpoint.
  2. Generate a low-rate synthetic transaction with an idempotency key every second and record UTC timestamps.
  3. Enable app logs for connection errors, reconnects, commit ambiguity and response latency.
  4. With change approval, force failover only on a compatible nonproduction Multi-AZ DB instance.
  5. Observe DB events, CloudWatch and app traces. Reconnect using the endpoint hostname, not a pinned IP.
  6. Query unique keys after recovery to detect lost/duplicate operations.
  7. Calculate observed downtime and recovery steps; record uncertainty around in-flight commits.

Representative output (illustrative, not actual AWS output):

2026-10-01T10:00:00Z write key=ha-001 status=committed latency_ms=18
2026-10-01T10:00:17Z write key=ha-018 status=connection_lost
2026-10-01T10:01:03Z reconnect status=success
2026-10-01T10:01:04Z write key=ha-019 status=committed latency_ms=25

Interpretation: connection_lost does not establish whether an in-flight transaction committed. Query by idempotency key before retrying.

Lab B — Read-after-write consistency

  1. Create a primary table: CREATE TABLE replication_probe(id uuid PRIMARY KEY, created_at timestamptz NOT NULL DEFAULT clock_timestamp());.
  2. Connect separately to primary and replica using psql.
  3. Insert a UUID into the primary and poll for it on the replica with UTC timestamps.
  4. Under a controlled write load, plot distribution of visibility delay and CloudWatch ReplicaLag.
  5. Document why a dashboard's aggregate lag metric is not a per-request freshness guarantee.

Lab C — PITR after accidental delete

  1. Enable and confirm automated backup retention.
  2. Insert test records, record UTC time and LatestRestorableTime.
  3. Delete test rows on a disposable instance only.
  4. Restore to a new instance at a valid point before the deletion.
  5. Check restored counts, constraints and application reads; log elapsed recovery time and estimated data loss.
  6. Tear down the restored resources after saving evidence.

Lab D — Storage latency investigation

  1. Capture SQL p95, CPU, memory, IOPS, latency, queue depth and active sessions.
  2. Run EXPLAIN (ANALYZE, BUFFERS) SELECT ... on a safe representative query, not unbounded on production.
  3. Compare index plan versus sequential scan, rows estimated versus actual, and shared buffer hits/reads.
  4. Inspect long transactions and lock waits before changing provisioned IOPS.
  5. Change one variable in a controlled load test and record whether user-visible latency improved.

Incident runbook — writer unavailable

Trigger: elevated 5xx, DB connection failures, DB instance status transition.
Triage: determine AZ/region scope, endpoint DNS, security group changes, DB events, connection pool state, app deploy changes.
Contain: stop unsafe retries and duplicate payment/order processing.
Recovery: use managed failover where applicable; restore/promote only according to approved topology and RPO plan.
Verify: unique business keys, critical read/write flows, latency and downstream reconciliation.
Aftercare: preserve timeline, quantify RTO/RPO, record root cause and corrective actions.

Incident runbook — replication lag

Trigger: ReplicaLag exceeds freshness budget.
Triage: write volume, large transactions, replica CPU/storage pressure, long-running read queries, network, engine logs.
Mitigate: route consistency-sensitive reads to writer; reduce heavy replica workload; increase capacity only if measured bottleneck.
Verify: lag returns below SLO and end-to-end data freshness tests pass.

Incident runbook — storage full

Trigger: FreeStorageSpace falls rapidly, writes fail or storage autoscaling limit approaches.
Triage: table/index growth, temporary files, transaction log retention, replication slots, unexpected bulk ingestion.
Mitigate: stop runaway workload, preserve data, evaluate storage modification, fix retention/queries with engine-safe methods.
Verify: writes resume, free space stabilizes, backups remain viable. Avoid dangerous manual deletion of engine-managed files.

Chapter 30 — Capstone: production-grade order service

Business requirements

An order API processes 250 writes/s peak and 1,500 reads/s peak. Target p99 read latency < 150 ms, business RTO 30 minutes, RPO 5 minutes for regional disaster, and no duplicate charge/order processing. All values are hypothetical design inputs, not RDS guarantees.

Proposed architecture

flowchart TB
    U[Clients] --> ALB[ALB]
    ALB --> APP[Stateless API in two AZs]
    APP --> PROXY[RDS Proxy / connection pool]
    PROXY --> W[(RDS writer)]
    W --> HA[(Multi-AZ standby or cluster standbys)]
    APP --> READ[Consistency-aware read router]
    READ --> REP[(Read replica)]
    W --> BK[Automated backups + PITR]
    BK --> DR[Cross-region restore plan]
    W --> OBS[CloudWatch + DB telemetry]
    APP --> OBS

Architecture decisions

  • Private DB subnet group spanning required AZs; security groups permit DB port only from authorized application tier.
  • TLS, secrets rotation, least-privilege SQL roles, encrypted storage and audit controls.
  • Writer handles payments, orders and read-after-write; replica handles tolerant catalog/reporting queries.
  • Idempotency key unique index protects retries; outbox pattern decouples DB commit from asynchronous events.
  • Tested backup/PITR and cross-region recovery process; RTO/RPO validated with drills.
  • IaC and immutable application releases; database migrations follow expand–migrate–contract.

Example SQL

CREATE TABLE orders (
  id uuid PRIMARY KEY,
  idempotency_key text NOT NULL UNIQUE,
  customer_id uuid NOT NULL,
  total_cents bigint NOT NULL CHECK (total_cents >= 0),
  status text NOT NULL CHECK (status IN ('pending','paid','cancelled')),
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX orders_customer_created_idx ON orders(customer_id, created_at DESC);

Explanation: UUID primary key provides stable order identity; unique idempotency key prevents duplicate logical requests; bigint stores money in minor units; CHECK constraints reject invalid states/negative totals; composite index supports customer order history in descending date order. Constraints alone do not guarantee payment gateway idempotency; coordinate with the provider and transaction boundary.

Acceptance tests

  1. App can write and read via TLS, without public DB access.
  2. Multi-AZ failover test recovers within measured application SLO or produces a documented gap.
  3. Read routing meets freshness contract; replica lag alarms fire under injected lag.
  4. PITR restore produces correct records and measured recovery time.
  5. DR tabletop demonstrates region-loss decision path, promotion/restore and split-brain prevention.
  6. Load test captures p95/p99 latency and capacity bottlenecks; estimate monthly cost with current regional prices.

Senior interview — scenario questions with model answers

Q1. Multi-AZ enabled: why did clients still see 90 seconds of errors?
A. HA requires detection, promotion, endpoint resolution, pool reconnection and application retry. Measure each stage; investigate DNS caching and stale connections.

Q2. Can you send all SELECT statements to replicas?
A. No. Transactions and read-after-write operations often require the writer; replicas can lag. Classify consistency needs per query.

Q3. Does synchronous replication mean zero data loss in every disaster?
A. No universal guarantee. Clarify failure model, commit acknowledgment, region scope, application behavior and backup/DR boundaries.

Q4. ReplicaLag is low but users see stale data. Why?
A. Metric aggregation, request timing, caching, wrong endpoint, transaction snapshots or application routing can all cause stale observations.

Q5. How do you choose gp3 versus io2?
A. Benchmark real I/O profile and latency, check AWS support/limits, evaluate predictability, cost and headroom. Don't optimize solely for peak IOPS.

Q6. What is the difference between snapshot and PITR?
A. Snapshot restores to the captured point; PITR reconstructs a new DB at a selected recoverable point using backups/logs within retention limits.

Q7. You have RTO 15 min and RPO 1 min across regions. What next?
A. Assess data criticality and failure modes, benchmark suitable cross-region replication, define promotion/fencing, test network/app dependencies, measure achieved RTO/RPO and identify gaps.

Q8. How can you prevent duplicate charges after failover?
A. Use stable idempotency keys, unique DB constraints, payment-provider idempotency and reconciliation. Do not blindly replay ambiguous commits.

Q9. Why can more read replicas increase complexity?
A. They introduce lag, routing, monitoring, cost, capacity and promotion/failback concerns; they do not scale writes.

Q10. What is your first action when WriteLatency spikes?
A. Correlate query waits, I/O, WAL flushes, CPU, lock contention, traffic and deployments before modifying storage.

Q11. What happens when you restore PITR?
A. A new DB endpoint is created. You must verify data, security, connection strings and cutover; the original is not automatically replaced.

Q12. Is Aurora always faster than RDS PostgreSQL?
A. No. Performance depends on workload, configuration, SQL, storage behavior, network and engine features. Benchmark representative transactions.

Q13. Can a reader endpoint guarantee load balancing per query?
A. No. It distributes connection placement under documented behavior; long-lived pooled connections may skew distribution.

Q14. How would you estimate database concurrency?
A. Use measured arrival rate and response time (Little's Law), then account for waiting, transaction scope, connection pooling and service count.

Q15. How do you prove a backup strategy works?
A. Repeated restore drills, application integrity checks, access/key verification, measured RTO/RPO and evidence retention.

Glossary

ACU: Aurora Capacity Unit. AZ: Availability Zone. Commit ambiguity: inability to tell whether a transaction committed after a lost connection. DNS TTL: duration DNS responses may be cached. HA: High availability. IOPS: I/O operations per second. PITR: Point-in-time recovery. Read replica: asynchronously updated read-oriented copy in conventional RDS configurations. RPO: maximum tolerable data loss. RTO: maximum tolerable restoration time. WAL: write-ahead log. Writer fencing: preventing an old writer from accepting conflicting writes after failover.
