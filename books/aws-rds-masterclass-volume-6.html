Chapter 41 — PostgreSQL performance and internals

How PostgreSQL executes a request

flowchart LR
 A[Client / pool] --> B[PostgreSQL backend]
 B --> C[Parser / rewrite]
 C --> D[Planner: cardinality and cost]
 D --> E[Executor]
 E --> F[Shared buffers]
 F --> G[OS page cache / RDS storage]
 E --> H[WAL records]
 H --> I[Durable WAL flush]

PostgreSQL uses a process-per-connection architecture. A statement is parsed, rewritten, optimized using statistics, and executed. The planner considers row-count estimates, access paths, join algorithms, and cost parameters. EXPLAIN shows the chosen plan; EXPLAIN (ANALYZE, BUFFERS) executes the statement and measures actual work. Never use ANALYZE on a destructive DML statement in production unless you intend its effects; wrap a test in a transaction and roll back when safe.

MVCC: updates usually create new tuple versions. Old versions persist until they are no longer needed and vacuum can reclaim their space. Long-lived transactions and replication slots can prevent cleanup, creating bloat and transaction ID risk. Visibility maps help index-only scans; HOT updates can reduce index churn when indexed columns remain unchanged and page space permits. WAL records changes for crash recovery and replication; commit durability depends on flush semantics and configuration. RDS restricts some superuser-level settings.

Statistics and planner: ANALYZE updates statistics; extended statistics can capture correlations; bad estimates can choose nested loops over hash joins or vice versa. Tune query shape and indexes before blindly increasing memory.

Lab 41A — Diagnose a slow query

CREATE SCHEMA IF NOT EXISTS training;
CREATE TABLE IF NOT EXISTS training.orders (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id bigint NOT NULL,
  customer_id bigint NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  status text NOT NULL CHECK (status IN ('pending','paid','cancelled')),
  total numeric(12,2) NOT NULL CHECK (total >= 0)
);
INSERT INTO training.orders (tenant_id, customer_id, created_at, status, total)
SELECT 1 + (g % 20), 1 + (g % 1000), now() - (g || ' minutes')::interval,
       CASE WHEN g % 3 = 0 THEN 'paid' ELSE 'pending' END, (g % 900)::numeric
FROM generate_series(1,100000) AS g;
ANALYZE training.orders;
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at, total FROM training.orders
WHERE tenant_id = 4 AND status = 'paid'
ORDER BY created_at DESC LIMIT 30;
CREATE INDEX CONCURRENTLY orders_tenant_status_created_idx
ON training.orders (tenant_id, status, created_at DESC) INCLUDE (total);
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, created_at, total FROM training.orders
WHERE tenant_id = 4 AND status = 'paid'
ORDER BY created_at DESC LIMIT 30;

Where: psql connected to a disposable RDS PostgreSQL instance. CREATE INDEX CONCURRENTLY cannot run inside an explicit transaction block; it may leave an invalid index on failure. Expected: the second plan may use the composite index and avoid sorting, depending on data distribution. Verify: inspect actual time, rows, loops, shared hits/reads, planning time, and whether estimates match reality. Cleanup: DROP SCHEMA training CASCADE; only in the lab database.

Line-by-line reasoning: tenant_id is the leading equality key; status is the next equality key; created_at DESC supports ordered retrieval; INCLUDE (total) can help covering scans, but heap visibility still matters. The LIMIT favors an ordered index scan. An index is not free: writes, WAL, disk and vacuum work increase.

Lab 41B — Inspect production-safe diagnostics

SELECT pid, usename, application_name, state, wait_event_type, wait_event,
       now() - query_start AS query_age, left(query,160) AS sample
FROM pg_stat_activity WHERE datname = current_database()
ORDER BY query_start NULLS LAST LIMIT 30;
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 20;
SELECT indexrelname, idx_scan, idx_tup_read, idx_tup_fetch
FROM pg_stat_user_indexes ORDER BY idx_scan ASC LIMIT 30;

pg_stat_activity identifies current sessions and waits, not historical root cause. Dead tuple counts are estimates. Low index scan counts do not alone justify dropping an index (unique constraints, rare critical queries and time-window bias matter). For pg_stat_statements, check parameter group/preload requirements and supported extension privileges before enabling.

Deep-dive: vacuum, memory and connection saturation

shared_buffers caches pages; work_mem is per sort/hash operation, potentially many times per query and session; maintenance_work_mem supports maintenance. High max_connections multiplies backend memory and context switching. Avoid treating RDS instance RAM as one freely assignable cache. Investigate checkpoints, WAL volume, temp files, autovacuum progress, idle in transaction, and replication slot retention. Escalation: when approaching transaction ID wraparound, prioritize vacuum blockers and AWS-supported recovery guidance rather than indiscriminately disabling autovacuum.

Chapter 42 — MySQL performance and internals

InnoDB execution model

flowchart LR
 A[Application] --> B[MySQL parser/optimizer]
 B --> C[InnoDB buffer pool]
 C --> D[Clustered primary-key B-tree]
 C --> E[Secondary indexes]
 C --> F[Redo log]
 C --> G[Undo / MVCC]
 D --> H[RDS storage]

InnoDB stores table rows in the clustered primary-key B-tree; secondary index leaves contain primary-key values. A wide or random primary key affects storage, secondary indexes and page locality. The buffer pool caches data/index pages; redo supports crash recovery; undo supports rollback and consistent reads. Binlogs serve replication/CDC when configured. MySQL's default InnoDB isolation is commonly REPEATABLE READ; PostgreSQL defaults to READ COMMITTED—do not assume identical gap locking or snapshot semantics.

Lab 42A — Index selection and plans

CREATE DATABASE IF NOT EXISTS training;
USE training;
CREATE TABLE invoices (
 id BIGINT PRIMARY KEY AUTO_INCREMENT,
 tenant_id BIGINT NOT NULL,
 issued_at DATETIME NOT NULL,
 status VARCHAR(20) NOT NULL,
 amount DECIMAL(12,2) NOT NULL,
 INDEX idx_tenant_status_date (tenant_id,status,issued_at)
) ENGINE=InnoDB;
EXPLAIN FORMAT=JSON SELECT id, issued_at, amount
FROM invoices WHERE tenant_id=7 AND status='open'
ORDER BY issued_at DESC LIMIT 50;
SHOW GLOBAL STATUS LIKE 'Threads_connected';
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_reads';
SHOW ENGINE INNODB STATUS\G

Where: MySQL client connected to a disposable RDS MySQL instance. Expected: JSON plan indicates access path and estimated rows; without data, optimizer behavior is not representative. Load anonymized data, collect timings and compare plans before claiming an optimization. Observe: performance_schema and Performance Insights/Database Insights availability depends on engine version and AWS offering. Inspect information_schema.innodb_trx and performance_schema.data_lock_waits when supported. Cleanup: DROP DATABASE training; only after verifying the target.

Tuning methodology

Establish p50/p95/p99 latency and throughput; check slow query logs and digest aggregates; capture EXPLAIN ANALYZE on versions supporting it; inspect row estimates and access paths; fix predicates, indexes, N+1 queries and excessive result sizes; re-measure with concurrency. innodb_buffer_pool_size changes are workload-specific and RDS parameter groups may require reboot. Watch redo/binlog growth, checkpoint pressure, buffer pool hit/miss context, disk queueing, CPU and connections. Avoid tuning solely to an arbitrary hit ratio.

Chapter 43 — Locks, deadlocks, isolation and concurrency

Transaction anomaly map

  • Dirty read: observe uncommitted data; PostgreSQL treats READ UNCOMMITTED as READ COMMITTED.
  • Nonrepeatable read: same row read twice differs across statements.
  • Phantom: predicate result changes between reads; exact guarantees differ by engine and isolation.
  • Write skew: transactions each read a shared invariant then update different rows; serializable semantics or explicit coordination may be needed.
  • Deadlock: a wait-for cycle; engine detects and aborts one participant. Retrying the entire idempotent transaction is usually correct.
sequenceDiagram
 participant T1 as Transaction A
 participant DB as Database
 participant T2 as Transaction B
 T1->>DB: Lock account 1
 T2->>DB: Lock account 2
 T1->>DB: Request account 2 (wait)
 T2->>DB: Request account 1 (cycle)
 DB-->>T2: Abort one transaction
 T1->>DB: Continue / commit

Lab 43A — Reproduce a PostgreSQL deadlock (two psql terminals)

-- Setup once
CREATE TABLE training.accounts(id integer PRIMARY KEY, balance integer NOT NULL);
INSERT INTO training.accounts VALUES (1,100),(2,100);
-- Terminal A
BEGIN; UPDATE training.accounts SET balance=balance-10 WHERE id=1;
-- Terminal B
BEGIN; UPDATE training.accounts SET balance=balance+10 WHERE id=2;
-- Terminal A: run and wait
UPDATE training.accounts SET balance=balance+10 WHERE id=2;
-- Terminal B: run and wait
UPDATE training.accounts SET balance=balance-10 WHERE id=1;

Expected: PostgreSQL eventually reports ERROR: deadlock detected to one transaction (SQLSTATE 40P01); the aborted transaction must ROLLBACK. Prevent: always lock accounts in ascending ID order, keep transactions short, use narrow indexes, and retry transient errors with bounded exponential backoff + jitter. A lock_timeout can cap waits but is not a substitute for fixing contention.

Lab 43B — Safe transfer with deterministic locking

BEGIN;
SELECT id, balance FROM training.accounts WHERE id IN (1,2)
ORDER BY id FOR UPDATE;
UPDATE training.accounts SET balance=balance-10 WHERE id=1 AND balance>=10;
-- Check row count in application; abort if zero.
UPDATE training.accounts SET balance=balance+10 WHERE id=2;
COMMIT;

Important: a production money-transfer design needs idempotency keys, ledger entries, constraints, retries and auditing; the example is a concurrency demonstration, not a complete financial ledger. Application code should verify the first update affected one row before the second update.

Application retry pseudocode

for attempt in range(5):
    try:
        with db.transaction():
            process_idempotent_business_operation()
        break
    except (DeadlockDetected, SerializationFailure):
        if attempt == 4:
            raise
        sleep(min(0.1 * 2**attempt, 1.5) + random.uniform(0, 0.1))

Do not retry an operation with external side effects unless the side effects are idempotent or managed with an outbox/saga. Database commit and an HTTP call are not one atomic transaction.

Chapter 44 — Production troubleshooting and incident command

Production incident playbook

1. Detect: confirm SLO breach, scope, error budget and business impact. 2. Stabilize: stop a runaway deployment, scale application concurrency down if it is overwhelming the DB, preserve logs and coordinate changes. 3. Diagnose: distinguish DB CPU, IO, locks, network, authentication, pool starvation and bad plans. 4. Mitigate: safe rollback, targeted cancellation, add capacity or fail over only if justified. 5. Recover: verify writes, queues, replication and user-visible correctness. 6. Learn: blameless postmortem, action owners and regression tests.

 F -->|IO| H[IOPS, queue, checkpoints, temp spill]
 C --> I[Apply reversible mitigation]
 E --> I
 G --> I
 H --> I
 I --> J[Verify SLO and data integrity]

Explanation: sts verifies identity; describe-db-instances shows state and pending modifications; CloudWatch metric query returns sampled connection counts in the specified UTC window (change timestamps to incident window); RDS events reveal recent maintenance/failover signals. Empty datapoints can mean no data, wrong dimensions or window, not zero connections.

PostgreSQL blocker diagnosis

SELECT blocked.pid AS blocked_pid, blocked.wait_event_type,
       pg_blocking_pids(blocked.pid) AS blocker_pids,
       now() - blocked.query_start AS blocked_age,
       left(blocked.query,120) AS blocked_sql
FROM pg_stat_activity blocked
WHERE cardinality(pg_blocking_pids(blocked.pid)) > 0;

Avoid blindly terminating sessions: identify business owner, rollback impact and permission; pg_cancel_backend cancels the current query while pg_terminate_backend ends a session and rolls back its open transaction. Neither fixes the underlying lock ordering or transaction length.

Incident casebook

Symptom Competing hypotheses Evidence Reversible mitigation
Connection timeout SG/NACL/DNS/TLS/pool TCP reachability, endpoint, errors Correct narrow SG rule; fix DNS/pool
CPU 95% hot SQL, bad plan, excess concurrency DB load, top statements, EXPLAIN rollback query change, cap concurrency
Storage pressure WAL retention, bloat, temp files, growth free storage, slots, vacuum stats address retention; increase capacity if safe
Replica lag write spike, long replay, IO bottleneck lag metrics, workload, logs stop read routing to stale replica
Deadlock spike lock-order regression engine deadlock logs, app traces rollback release, deterministic order
Slow after failover reconnect storm, DNS cache, cold cache events, pool metrics, latency backoff/jitter, warm carefully

Senior judgment: an RDS failover is not a generic cure for slow SQL; it can create additional disruption. Collect a timeline of changes and preserve forensic data before destructive remediation.

Chapter 45 — AWS DMS and migration engineering

Migration decision tree

Use native dump/restore for modest downtime and homogeneous engines; native logical/physical replication when compatible and operationally appropriate; AWS DMS for managed full-load plus CDC workflows; schema conversion tooling for heterogeneous schemas. DMS does not automatically solve application SQL incompatibility, stored procedures, sequences, large objects, unsupported data types or cutover consistency.

flowchart LR
 A[Source database] --> B[Assess schema + compatibility]
 B --> C[Create target and network access]
 C --> D[Initial full load]
 A --> E[CDC from source logs]
 E --> F[Catch-up and validate]
 D --> F
 F --> G[Write freeze / cutover]
 G --> H[Switch application]
 H --> I[Reconcile and monitor]

Lab 45A — Migration preflight checklist

  1. Inventory source engine/version, extensions, triggers, routines, collations, character sets, foreign keys, large objects, sequences, peak write throughput and table sizes.
  2. Select migration mechanism and document unsupported objects. Provision private network reachability from replication resources to source and target; least-privilege endpoints and encrypted transport.
  3. For PostgreSQL CDC, plan logical replication prerequisites, slots and WAL retention; for MySQL CDC, binlog format/retention and permissions. AWS DMS source prerequisites are engine-specific and version-sensitive.
  4. Estimate full-load time from data volume and measured throughput; test on a realistic subset.
  5. Define a cutover freeze, application rollback criteria, CDC lag threshold, and final sequence/identity adjustments.
  6. Compare counts, checksums/sample hashes, financial totals, referential integrity and application business invariants; row counts alone are insufficient.
  7. Decide when rollback ceases to be trivial: once new writes occur on the target, reversing direction requires a tested strategy.

Lab 45B — Read-only DMS inspection

aws dms describe-replication-instances --region "$AWS_REGION"   --query 'ReplicationInstances[].{Id:ReplicationInstanceIdentifier,Status:ReplicationInstanceStatus}'
aws dms describe-replication-tasks --region "$AWS_REGION"   --query 'ReplicationTasks[].{Id:ReplicationTaskIdentifier,Status:Status,Stats:ReplicationTaskStats}'

Expected: empty arrays if no DMS resources; otherwise status and task statistics. Newer DMS serverless configurations have separate replication-config APIs; choose the API matching the actual mode. Avoid embedding endpoint passwords in shell history or Terraform state. For a full lab, create source and target disposable databases, seed 100k rows, configure full load + CDC in the AWS console with private networking, update source rows during replication, then compare target data and CDC latency. Delete DMS replication resources afterward to stop charges.

Reconciliation SQL

SELECT count(*) AS row_count, sum(total) AS total_amount,
       min(id) AS min_id, max(id) AS max_id
FROM training.orders;

Run on both sides at a consistent logical checkpoint or after a write freeze. Aggregate equality is useful but not proof of row-level equality; add deterministic per-key hashes and business validation.

Chapter 46 — Microservices data architecture

Ownership and boundaries

Each service owns its schema and business invariants. Avoid services directly joining other services' tables. A single RDS instance may host multiple service-owned databases as an interim trade-off, but failure domains, permissions and noisy neighbors remain shared. Database-per-service improves autonomy while increasing operations and cross-service consistency complexity.

flowchart TD
 A[API Gateway] --> O[Order Service]
 A --> P[Payment Service]
 O --> OD[(Orders RDS)]
 P --> PD[(Payments RDS)]
 O --> X[Transactional Outbox]
 X --> E[Event Bus]
 E --> P
 P --> E2[Payment Completed Event]
 E2 --> O

Reliable outbox pattern

BEGIN;
INSERT INTO orders (id, customer_id, status) VALUES (:id,:customer,'pending');
INSERT INTO outbox (event_id, aggregate_id, event_type, payload)
VALUES (:event_id,:id,'OrderCreated',:json_payload);
COMMIT;

Both records commit atomically in the same database. A background relay publishes outbox rows; delivery may be at least once, so consumers require idempotency (unique event_id receipt table), ordering strategy, retries, poison-message handling and observability. The sample uses named bind parameters: pass them through a driver/ORM, not literal SQL in psql.

Engineering trade-offs

Saga: local transactions plus compensating actions, not an ACID transaction spanning services. CQRS: separate read projections when justified by different access patterns; account for lag. Sharding: hash/range/tenant-based distribution; plan rebalancing and hot-key mitigation. Read replicas: can serve stale reads; route read-after-write to writer or use consistency tokens. Connection budgets: sum max pools across replicas and deployments; use RDS Proxy only when compatible with session behavior. Backpressure: bound concurrency and queue length to avoid database overload.

PostgreSQL RLS lab (use a disposable database; application must not connect as a table owner or a role bypassing RLS):

CREATE TABLE tenant_documents (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id uuid NOT NULL,
  title text NOT NULL
);
ALTER TABLE tenant_documents ENABLE ROW LEVEL SECURITY;
ALTER TABLE tenant_documents FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_scope ON tenant_documents
USING (tenant_id = current_setting('app.tenant_id', true)::uuid)
WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid);
CREATE ROLE app_tenant LOGIN;
GRANT SELECT, INSERT, UPDATE, DELETE ON tenant_documents TO app_tenant;
GRANT USAGE, SELECT ON SEQUENCE tenant_documents_id_seq TO app_tenant;

Security warning: a user-controllable session variable alone is not a trustworthy identity boundary. A trusted server must authenticate tenant membership, set tenant context inside each transaction with SET LOCAL, and prevent arbitrary SQL/role escalation. Validate connection-pool resets; test missing, mismatched and malicious tenant IDs. Prefer an authorization architecture that cannot be bypassed by application-level SQL injection.

Lab 47B — Tenant data leak tests

Create two tenant UUIDs and test (1) tenant A sees only A, (2) A cannot insert B rows, (3) unset tenant context denies access, (4) pooled connections do not retain prior tenant identity, (5) backup/restore and exports preserve tenant scoping. Add an integration test for every query path, including background workers, reports and administrative APIs.

Capacity: partitioning by tenant can help pruning but is not a substitute for authorization; very large tenant counts make per-tenant schema operations costly. Track tenant-level QPS, p95 latency, storage, connections and cost allocations.

Chapter 48 — Security and threat modeling

Threat model (STRIDE)

  • Spoofing: stolen app credentials, compromised IAM role → short-lived credentials, MFA for humans, scoped IAM, rotation.
  • Tampering: SQL injection or privileged writes → parameterized SQL, grants, immutable audit pipelines.
  • Repudiation: insufficient audit evidence → CloudTrail for API control plane; database audit/logging for SQL events where supported.
  • Information disclosure: public endpoints, weak TLS, backups or logs → private subnets, SG least privilege, TLS validation, KMS, redaction.
  • Denial of service: unbounded queries/connections → statement timeouts, pooling, quotas, backpressure.
  • Elevation of privilege: overbroad master credentials, cross-tenant access → separate application roles, RLS/authorization and access review.

Secure Python DB connection (psycopg 3)

import os
import psycopg

conn = psycopg.connect(
    host=os.environ['DB_HOST'],
    dbname=os.environ['DB_NAME'],
    user=os.environ['DB_USER'],
    password=os.environ['DB_PASSWORD'],
    sslmode='verify-full',
    sslrootcert=os.environ['RDS_CA_BUNDLE'],
    connect_timeout=5,
    application_name='orders-api',
)
with conn:
    with conn.cursor() as cur:
        cur.execute('SELECT id FROM orders WHERE tenant_id = %s LIMIT 10',
                    (os.environ['TENANT_ID'],))
        print(cur.fetchall())

Line-by-line: environment variables keep credentials out of source control (but env variables can still leak via diagnostics); verify-full checks CA trust and hostname; connect_timeout bounds establishment; application_name improves traceability; %s binds data values rather than interpolating SQL. In production, retrieve Secrets Manager credentials securely and cache with rotation-aware refresh; use IAM DB auth where supported and appropriate. Use the AWS RDS trust bundle from an authoritative AWS URL, not a random certificate mirror.

Infrastructure security baseline

RDS publicly_accessible=false; DB subnet group spanning suitable AZs; no inbound 0.0.0.0/0 database rule; encryption at rest configured at creation; KMS key policy reviewed; backup retention, deletion protection, patch windows, audit logs and event alarms; Secrets Manager rotation; VPC flow logs where needed. IAM database auth does not grant SQL privileges. KMS key deletion can make encrypted data irrecoverable. Encrypted snapshot sharing/copy behavior and cross-account KMS permissions require specific planning.

Chapter 49 — Disaster recovery and reliability

RTO and RPO

RTO: maximum acceptable recovery duration. RPO: maximum acceptable data loss window. Neither is automatically guaranteed by choosing Multi-AZ or a read replica. Test application reconnection, DNS caching, replica promotion, backup restore, infrastructure recreation and data integrity. Backup retention is not the same as tested recoverability.

 A[Primary Region] --> B[Multi-AZ RDS writer]
 B --> C[Automated backups / PITR]
 B -.async replication.-> D[Secondary Region replica]
 D --> E[Promotion + application routing]
 C --> F[Restore into new DB]

Lab 49A — Recovery rehearsal (disposable instance only)

aws rds describe-db-instances --db-instance-identifier "$DB_ID" --region "$AWS_REGION"
aws rds create-db-snapshot --db-instance-identifier "$DB_ID"   --db-snapshot-identifier "${DB_ID}-dr-drill-20261016" --region "$AWS_REGION"
aws rds wait db-snapshot-available   --db-snapshot-identifier "${DB_ID}-dr-drill-20261016" --region "$AWS_REGION"
aws rds restore-db-instance-from-db-snapshot   --db-instance-identifier "${DB_ID}-dr-restore"   --db-snapshot-identifier "${DB_ID}-dr-drill-20261016"   --db-subnet-group-name your-private-db-subnet-group   --vpc-security-group-ids sg-REPLACE   --no-publicly-accessible --region "$AWS_REGION"

Before execution: ensure snapshot name uniqueness, valid engine/region settings, sufficient quota and budget. Restores create a new instance; verify parameters, networking, TLS, credentials and post-restore settings. A restored snapshot is only as current as snapshot time; PITR restores to a specified point within the supported recovery window. Validation: run read-only row-count and invariant checks, synthetic API requests and failover drills; record measured recovery time and data freshness. Cleanup: delete the drill instance and drill snapshot after confirmation, not the source.

DR runbook template

Declare incident and freeze deployments; assess region/control-plane health; choose restore versus promotion; verify IAM/KMS and network prerequisites; restore or promote; update application configuration and routing; check migrations and consistency; resume writes; monitor error rates and lag; document divergence and failback plan. Regional outage scenarios may impair API availability, so preprovision and test critical recovery assets where feasible.

Migration SQL — migrations/001_init.sql

CREATE TABLE IF NOT EXISTS orders (
 id uuid PRIMARY KEY,
 tenant_id uuid NOT NULL,
 customer_id uuid NOT NULL,
 status text NOT NULL CHECK (status IN ('pending','paid','cancelled')),
 total numeric(12,2) NOT NULL CHECK (total >= 0),
 created_at timestamptz NOT NULL DEFAULT now(),
 idempotency_key text NOT NULL,
 UNIQUE (tenant_id, idempotency_key)
);
CREATE INDEX IF NOT EXISTS orders_tenant_created_idx
 ON orders(tenant_id,created_at DESC);
CREATE TABLE IF NOT EXISTS outbox (
 event_id uuid PRIMARY KEY,
 aggregate_id uuid NOT NULL,
 event_type text NOT NULL,
 payload jsonb NOT NULL,
 published_at timestamptz,

FastAPI minimal API — app/main.py

import os, uuid
from decimal import Decimal
from fastapi import FastAPI, Header, HTTPException
from pydantic import BaseModel, Field
from sqlalchemy import create_engine, text
from sqlalchemy.exc import IntegrityError

app = FastAPI()
engine = create_engine(os.environ['DATABASE_URL'], pool_size=5,
                       max_overflow=2, pool_pre_ping=True, pool_timeout=5)

class NewOrder(BaseModel):
    customer_id: uuid.UUID
    total: Decimal = Field(ge=0, max_digits=12, decimal_places=2)

@app.post('/orders', status_code=201)
def create_order(body: NewOrder, idempotency_key: str = Header(min_length=8, max_length=128)):
    # DEMO ONLY: replace fixed tenant with authenticated principal from verified JWT.
    tenant_id = uuid.UUID(os.environ['DEMO_TENANT_ID'])
    order_id, event_id = uuid.uuid4(), uuid.uuid4()
    with engine.begin() as conn:
        existing = conn.execute(text("""SELECT id FROM orders
            WHERE tenant_id=:tenant AND idempotency_key=:key"""),
            {'tenant':tenant_id,'key':idempotency_key}).scalar_one_or_none()
        if existing:
            return {'order_id':str(existing),'deduplicated':True}
        try:
            conn.execute(text("""INSERT INTO orders
                (id,tenant_id,customer_id,status,total,idempotency_key)
                VALUES (:id,:tenant,:customer,'pending',:total,:key)"""),
                {'id':order_id,'tenant':tenant_id,'customer':body.customer_id,
                 'total':body.total,'key':idempotency_key})
            conn.execute(text("""INSERT INTO outbox
                (event_id,aggregate_id,event_type,payload)
                VALUES (:event,:id,'OrderCreated',CAST(:payload AS jsonb))"""),
                {'event':event_id,'id':order_id,
                 'payload':'{"order_id":"'+str(order_id)+'"}'})
        except IntegrityError:
            # Concurrent same-key inserts need an explicit savepoint or full
            # transaction retry; do not continue in an aborted PostgreSQL txn.
            raise HTTPException(409, 'Concurrent duplicate; retry with same key')
    return {'order_id':str(order_id),'deduplicated':False}

Study plan and evaluation

Weeks 1–2: PostgreSQL/MySQL plans, locks and tuning; collect before/after benchmark evidence. Week 3: diagnose three controlled incidents. Week 4: DMS migration rehearsal and reconciliation. Week 5: service boundaries, outbox and tenant-isolation tests. Week 6: security review and DR restore. Weeks 7–8: capstone integration, load test, architecture review and 100-question oral drill.

Senior pass criteria: reproducible deployments; no public database access; evidence of TLS verification; reliable migrations; measured performance gains; bounded connection count; successful recovery drill; documented incident runbooks; architecture decisions with explicit trade-offs. Never claim hands-on proficiency from reading alone—execute and validate in your own account/lab.
