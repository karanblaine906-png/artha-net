Safety: Run destructive storage, networking, and firewall exercises only in disposable virtual machines with console access and snapshots.

Chapter 1: RHEL Architecture and Installation

Learning objectives and theory

This chapter covers boot chain, firmware, GRUB2, kernel, initramfs, systemd; installation and subscription. Think in layers: user request → user-space process → system call → Linux kernel → hardware or remote service. Observe the actual system state before changing configuration.

Guided laboratory

Lab environment: Two RHEL 9 VMs (rhel-a, rhel-b) with sudo-enabled user; take a snapshot first.

  1. Record a baseline and save evidence.
cat /etc/redhat-release
uname -r
hostnamectl
uptime
free -h
df -hT
ip -br addr
systemctl --failed
journalctl -p err -b --no-pager | tail -30
  1. Choose a component in the chapter scope. Inspect its configuration, runtime state, and logs.
  2. Reproduce a controlled failure in a disposable VM, identify the symptom, recover, and document verification.

Troubleshooting workflow

  1. Define expected behavior and observed behavior, including timestamps.
  2. Separate resource saturation, misconfiguration, access control, dependencies, and connectivity.
  3. Correlate process/service state with journal and relevant subsystem evidence.
  4. Make the smallest reversible change, validate the result, and document rollback.

Interview questions

Q1. What would you inspect first when a production issue involves rhel architecture and installation?
A: State the symptom and blast radius, collect read-only evidence, identify the affected layer, then test one hypothesis at a time.

Q2. How do you distinguish root cause from a correlated symptom?
A: Compare timeline, dependencies, metrics, logs, and a repeatable test; avoid treating a single error line as proof.

Q3. What makes a change production-safe?
A: Baseline, peer review, backups, rollback plan, maintenance window where needed, and post-change checks.

Deep-dive appendix: Load average vs CPU utilization

Linux load average is the exponentially damped average number of tasks runnable or in uninterruptible sleep (typically I/O waits), sampled over 1, 5 and 15 minutes. It is not a percentage. On four logical CPUs, a load average of 4 can indicate roughly full runnable capacity, but I/O-blocked tasks can elevate load without high CPU usage.

uptime
nproc
top -H
vmstat 1 5
ps -eo pid,stat,pcpu,pmem,wchan:24,comm --sort=-pcpu | head

Interpret vmstat r (runnable queue), b (blocked tasks), us/sy/id/wa (CPU time), and si/so (swap activity) together. A high wa is not itself proof that storage is the only bottleneck.

Chapter 20 — Linux internals and process lifecycle

20.1 How a Linux command becomes a running process

A shell is a userspace program, not the kernel. When you enter ls /var/log, the shell parses the line, locates the executable through PATH, normally creates a child process with fork() (or a related spawn strategy), and executes the program using execve(). The program's library functions invoke system calls such as openat(), getdents64(), write(), and close(). The kernel checks permissions, resolves paths through the virtual filesystem, and communicates with device drivers as needed. System calls cross the userspace/kernel boundary; output is returned through file descriptors, typically stdout (fd 1). A shell built-in like cd generally does not need to create a child.

Concept: A PID identifies a process in its PID namespace. A thread has its own task ID; threads in one process normally share a virtual address space. A context switch saves/restores CPU execution state, but does not mean every context switch changes address spaces. execve() replaces the process image while generally retaining its PID.

$ type -a ls
ls is /usr/bin/ls
$ strace -f -e trace=execve,openat,write ls /tmp 2>&1 | head
execve("/usr/bin/ls", ["ls", "/tmp"], ...) = 0
openat(AT_FDCWD, "/etc/ld.so.cache", O_RDONLY|O_CLOEXEC) = 3
...
$ ps -eo pid,ppid,stat,ni,pri,comm --sort=pid | head
  PID  PPID STAT  NI PRI COMMAND
    1     0 Ss     0  19 systemd

strace observes system-call activity and can expose repeated failing file accesses; it adds overhead and may expose secrets in arguments. Use it selectively on approved systems. STAT shows process state: R runnable/running, S interruptible sleep, D uninterruptible sleep, T stopped, Z zombie; additional flags such as s and l are modifiers. A zombie has exited but its parent has not reaped its exit status; kill -9 cannot kill an already-dead zombie.

20.2 Scheduling, cgroups and namespaces

The scheduler selects runnable tasks for CPUs. Linux uses different scheduling classes; normal tasks use the fair scheduling class (recent kernels use EEVDF in place of older CFS selection behavior). nice adjusts weight within normal scheduling, not a hard CPU quota. CPU affinity limits eligible CPUs; cgroup CPU quotas can throttle a service even when host CPU is idle. PID, mount, network, user and other namespaces isolate resource views, whereas cgroups account for and constrain resources.

$ cat /proc/$$/status | grep -E '^(Name|Pid|PPid|Threads|VmRSS):'
$ cat /proc/$$/cgroup
$ systemctl show sshd -p CPUQuotaPerSecUSec -p MemoryMax
$ taskset -pc $$

Lab: Launch sleep 120 &, record $!, inspect /proc/$!/status, ps -p $! -o pid,ppid,stat,etime,cmd, then wait. Observe S state and eventual exit. Interview: Why does kill -9 fail for D-state tasks? Because an uninterruptible wait often must return from its kernel wait path before the task can process termination; investigate the underlying I/O or kernel dependency rather than repeatedly signaling it.

Chapter 21 — Load average: internals, diagnosis and remediation

21.1 What load average measures

Linux load average is an exponentially smoothed estimate of tasks runnable (R) plus tasks in uninterruptible sleep (D), over roughly 1, 5 and 15 minutes. It is not a CPU utilization percentage. On an otherwise unrestricted host with four available logical CPUs, load near 4 may indicate roughly full runnable capacity; however D-state I/O waits can increase load even with idle CPU. Compare against effective CPU quota and affinity, not only nproc.

$ uptime
 18:15:00 up 10 days,  3:21,  2 users,  load average: 8.20, 6.10, 3.40
$ nproc
4
$ cat /proc/loadavg
8.20 6.10 3.40 9/840 25310
$ vmstat 1 5
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 7  0      0 620000  70000 820000    0    0     0    18  500  820 88 10  2  0  0

The sample's r=7 suggests CPU run-queue contention; b=0 and low wa suggest no obvious blocked-I/O bottleneck in this interval. vmstat first line can be an average since boot; interpret subsequent samples. A high 1-minute load relative to 15-minute load suggests a rising problem; reverse ordering suggests a declining problem. Do not derive exact CPU utilization from load.

21.2 Diagnosis decision tree

  1. Confirm scope and trend: date; uptime; nproc; cat /proc/loadavg; compare monitoring baseline.
  2. Check runnable/blocked tasks: vmstat 1 10; ps -eo state,pid,ppid,wchan:24,comm | awk '$1 ~ /R|D/'.
  3. Check CPU: mpstat -P ALL 1 5; pidstat -u -t 1 5; top -H -p PID.
  4. Check I/O: iostat -xz 1 5; pidstat -d 1 5; cat /proc/pressure/io.
  5. Check memory: free -h; vmstat 1; cat /proc/pressure/memory; journalctl -k -g 'Out of memory|oom-killer'.
  6. Check throttling/virtualization: cat /sys/fs/cgroup/cpu.stat (for relevant cgroup); look at %steal in mpstat for guest VMs.
  7. Correct the actual cause, then confirm response time, throughput, error rate, load and saturation all improve.

Install common tools using sudo dnf install -y sysstat procps-ng (repository access required). sysstat supplies mpstat, pidstat and iostat.

21.3 Contrasting production incidents

Case A — CPU saturation: load 12 on 4 CPUs; vmstat r=10 b=0, mpstat user CPU ~95%. Identify CPU-heavy process, check recent deployments, thread count, cgroup quota and traffic. Mitigate with controlled concurrency, scale-out or rollback, rather than blindly adding swap.

Case B — Storage stalls: load 15 on 8 CPUs; vmstat r=1 b=12, CPU idle 65%, iostat reports high await, many tasks in D state. Trace device errors (journalctl -k), filesystem, network block storage and upstream storage service. A CPU upgrade would not address this root cause.

Case C — CPU throttling: host has 16 CPUs but container quota is 2 CPUs; load 7, host idle, cpu.stat nr_throttled grows. Investigate quota, workload demand and service latency.

Interview Q&A: If load is 8 on 4 CPUs, is CPU utilization 200%? No. Load is a count-like exponentially smoothed measure of runnable plus D-state tasks; check actual CPU metrics and effective CPU limits.

Lab: In a disposable VM, run a controlled CPU load using stress-ng --cpu 2 --timeout 30s after installing stress-ng from an approved repository if available. Observe uptime, vmstat 1, mpstat -P ALL 1; note that load average lags after the test ends. Avoid stressing shared production hosts.

Chapter 22 — Production process troubleshooting

22.1 Workflow: slow service, apparently high CPU

Start from symptoms, not a preconceived command: response latency, error rates, timestamps, affected instances. Use systemctl status app.service, journalctl -u app.service --since '-15 min', ps -eo pid,ppid,stat,%cpu,%mem,rss,etime,comm --sort=-%cpu | head, and top -H -p PID. %CPU may exceed 100 for a multithreaded process in some tools; RSS is resident physical memory and includes shared pages (so summing RSS across processes can double-count). VSZ is virtual address-space size, not physical RAM consumption.

$ ps -p 4242 -o pid,ppid,stat,%cpu,%mem,rss,vsz,nlwp,etime,cmd
  PID PPID STAT %CPU %MEM   RSS     VSZ NLWP ELAPSED CMD
 4242    1 Sl  182.0  8.2 683240 2140120   16   02:40 /usr/bin/python3 app.py
$ cat /proc/4242/limits | head
Limit                     Soft Limit           Hard Limit           Units
Max cpu time              unlimited            unlimited            seconds

Here %CPU=182 could indicate usage of approximately 1.82 logical CPUs over the sampling convention; NLWP=16 is thread count. Verify with interval-based pidstat -p 4242 -t 1 5. Check open-file exhaustion via ls /proc/4242/fd | wc -l, cat /proc/4242/limits, journalctl errors such as Too many open files, and ss -tanp for socket pressure. For Python, stack diagnosis may require application-specific tracing/profiling and explicit production approval.

22.2 State-specific troubleshooting

State Meaning Investigation Common trap
R Running or runnable CPU, affinity, quotas, runnable backlog Treating load as utilization
S Interruptible sleep Expected wait, sockets, timers Killing healthy sleeping services
D Uninterruptible wait wchan, disk/NFS/storage, kernel logs Repeated kill -9
Z Exited, unreaped child Inspect parent and wait/reaping behavior Assuming zombie consumes CPU
T Stopped/traced SIGSTOP, debugger, job control Misdiagnosing as hung I/O

Safe incident sequence: preserve evidence → identify impact → find parent/service manager → test mitigation in staging → obtain approval for restarts/kill → verify recovery → record root cause. kill -TERM PID allows graceful handling; kill -KILL PID prevents graceful cleanup and should be last resort. systemctl restart can interrupt connections and must follow change procedure.

Lab: sleep 300 & pid=$!; ps -p "$pid" -o stat,wchan,cmd; kill -STOP "$pid"; ps -p "$pid" -o stat; kill -CONT "$pid"; kill -TERM "$pid"; wait "$pid". Expected: sleeping → stopped (T) → resumed → terminated. Interview: Why can an application show high latency with low CPU? Disk/network waits, locks, queueing, remote dependencies or throttling may dominate.

Chapter 23 — LVM from creation to safe recovery

23.1 Architecture and allocation

A physical volume (PV) is a block device or partition initialized with LVM metadata. A volume group (VG) pools PV capacity into physical extents (PEs); logical volumes (LVs) allocate logical extents mapped to PEs. The device-mapper layer presents LVs as block devices. LVM is not a filesystem: an LV normally needs XFS/ext4 formatting and a mount. LVM snapshots are not substitutes for independently verified backups.

23.2 Create a disposable data volume

Prerequisites: New empty /dev/vdb attached to a throwaway VM, 10 GiB or larger; lsblk -f confirms it is not the OS disk. Confirm identifiers from lsblk -o NAME,SIZE,TYPE,MOUNTPOINTS,FSTYPE and wipefs -n /dev/vdb. If uncertain, STOP. The following commands destroy existing data on /dev/vdb.

# lsblk -o NAME,SIZE,TYPE,MOUNTPOINTS,FSTYPE
NAME  SIZE TYPE MOUNTPOINTS FSTYPE
vda    30G disk
├─vda1   1G part /boot       xfs
└─vda2  29G part             LVM2_member
vdb    10G disk
# parted -s /dev/vdb mklabel gpt mkpart primary 1MiB 100% set 1 lvm on
# partprobe /dev/vdb
# pvcreate /dev/vdb1
  Physical volume "/dev/vdb1" successfully created.
# vgcreate vgdata /dev/vdb1
  Volume group "vgdata" successfully created
# lvcreate -L 4G -n lvapp vgdata
  Logical volume "lvapp" created.
# mkfs.xfs /dev/vgdata/lvapp
# mkdir -p /srv/appdata
# mount /dev/vgdata/lvapp /srv/appdata
# df -hT /srv/appdata
Filesystem                 Type  Size  Used Avail Use% Mounted on
/dev/mapper/vgdata-lvapp   xfs   4.0G   61M  3.9G   2% /srv/appdata
# pvs; vgs; lvs -o lv_name,vg_name,lv_size,lv_attr,devices

parted writes a GPT and partition, pvcreate writes LVM metadata, vgcreate makes the pool, lvcreate allocates capacity, mkfs.xfs erases any filesystem previously present on the LV, and mount exposes the filesystem. For persistent mounting use blkid /dev/vgdata/lvapp and add a carefully verified UUID=... /srv/appdata xfs defaults 0 0 to /etc/fstab; test findmnt --verify and mount -a with console recovery access. Use UUID to avoid path changes.

23.3 Grow an XFS logical volume

# vgs vgdata -o vg_name,vg_free
  VG     VFree
  vgdata 5.99g
# lvextend -L +2G /dev/vgdata/lvapp
  Size of logical volume vgdata/lvapp changed from 4.00 GiB to 6.00 GiB.
# xfs_growfs /srv/appdata
# df -hT /srv/appdata

lvextend grows the block device; xfs_growfs grows the mounted XFS filesystem. Alternatively, lvextend -r invokes filesystem resize tooling when supported. Verify lvs, df -hT, and application write tests. XFS cannot be shrunk in place; plan a backup, recreate and restore if a smaller filesystem is required. Ext4 can be shrunk offline under appropriate conditions, but reducing the LV before safely shrinking the filesystem risks irrecoverable corruption.

23.4 Extend VG with a second disk

On another empty disposable disk /dev/vdc, partition and verify, then pvcreate /dev/vdc1; vgextend vgdata /dev/vdc1; pvs; vgs. Use pvmove /dev/vdb1 /dev/vdc1 only when the destination has sufficient free extents and after checking supported layout; vgreduce removes an empty PV from the VG. Never use pvremove on a PV that still holds needed extents.

23.5 Troubleshooting decision table

Symptom Diagnostic Explanation and recovery direction
Insufficient free extents vgs -o vg_free; pvs Add PV capacity or choose a smaller LV
LV active but no mount lvs -a; lsblk -f; findmnt Check filesystem, mountpoint, fstab, SELinux
Filesystem still 4G after LV becomes 6G lvs; df -hT Run appropriate filesystem grow tool
Missing PV warning pvs -o +pv_uuid; journalctl -k Restore connectivity; consult LVM metadata backups before recovery
Boot failure after fstab change Emergency console; findmnt --verify Correct UUID/options; avoid destructive formatting

Interview: Explain the difference between lvextend, xfs_growfs, vgextend and pvresize. lvextend grows LV allocation; xfs_growfs expands an existing XFS filesystem; vgextend adds a PV to a VG; pvresize updates PV size after its underlying block device grows. Lab validation: Unmount the test filesystem, run mount -a, create a test file, check df -hT, and inspect journalctl -k for I/O errors. Never shrink a production LV as an experiment.

Chapter 24 — Memory, swap, OOM and reclaim

Linux uses spare RAM for reclaimable page cache, so low free alone does not mean an incident. available estimates memory that can be allocated without swapping under typical conditions. RSS reflects resident pages mapped by a process, but shared pages can appear in multiple RSS values; PSS apportions shared pages (/proc/PID/smaps_rollup). Swap use does not automatically prove current thrashing. Look for ongoing swap-in/out (vmstat si/so), memory pressure (/proc/pressure/memory), major faults, and latency.

$ free -h
               total   used   free  shared  buff/cache available
Mem:            7.5Gi  5.2Gi  310Mi  210Mi       2.0Gi     1.7Gi
Swap:           2.0Gi  420Mi  1.6Gi
$ vmstat 1 3
$ cat /proc/pressure/memory
some avg10=0.00 avg60=0.12 avg300=0.08 total=123456
full avg10=0.00 avg60=0.00 avg300=0.00 total=4000
$ journalctl -k --since '-1 hour' | grep -Ei 'out of memory|oom-killer|killed process'

some PSI means at least one task stalled on memory; full means all non-idle tasks stalled simultaneously (with cgroup-specific interpretation). OOM can be global or cgroup-scoped. systemctl show SERVICE -p MemoryMax -p MemoryCurrent helps identify service constraints. Do not immediately clear caches or add swap to disguise a memory leak. Correlate process PSS, application heap behavior, page cache, swap traffic and OOM logs.

Scenario: Application killed at 1.5 GiB while host shows 10 GiB available: a systemd or container cgroup memory limit may be responsible. Inspect unit limits and cgroup memory.events (oom, oom_kill), not just free. Interview: Difference between virtual memory and RSS? Virtual address-space mappings are not equivalent to physically resident pages.

Chapter 25 — Storage latency and filesystem diagnostics

Disk capacity and performance are separate dimensions. df -h measures filesystem space; df -i checks inode consumption. du -xsh /path estimates reachable directory usage; deleted but open files can keep disk blocks allocated, creating df/du disagreement. Use lsof +L1 when available, then plan safe service handling. iostat -xz 1 5 shows per-device utilization, request rates, throughput, average wait (await), and queue statistics; do not use %util=100 alone as definitive proof of saturation on modern parallel devices.

# df -hT /var; df -i /var
# du -xhd1 /var | sort -h
# lsof +L1 /var
# iostat -xz 1 5
Device  r/s   w/s  r_await w_await aqu-sz %util
vdb     3.0 120.0     2.1    78.2   9.70  94.0
# journalctl -k --since '-30 min' | grep -Ei 'I/O error|timeout|reset|xfs|nvme'

The illustrative high write await and queue depth warrant investigation. await includes queue and service time; use baselines and application latency. XFS repair: capture logs and backups, unmount first, use xfs_repair -n /dev/... for a non-modifying assessment; any repair may risk data and should follow vendor guidance and verified backups. Never run fsck.ext4 against mounted read-write ext4 filesystems.

Lab: Fill a disposable filesystem with a controlled file (fallocate -l 100M /srv/appdata/test.bin), compare df and du, then remove it. Avoid exhausting disk space on the root filesystem.

Chapter 26 — Boot and systemd recovery

RHEL commonly boots firmware → boot manager/GRUB2 → Linux kernel and initramfs → root filesystem → systemd PID 1 → target dependencies and units. systemd resolves unit ordering and requirement relationships; After= sets order, not a dependency by itself; Requires= adds a requirement but does not necessarily establish ordering. Wants= is weaker than Requires=. A service may fail because a required mount, network dependency, SELinux label or executable is unavailable.

# systemctl --failed
# systemctl status sshd.service --no-pager
# journalctl -b -u sshd.service --no-pager -n 80
# systemctl cat sshd.service
# systemd-analyze critical-chain
# systemctl show sshd -p ExecStart -p After -p Requires -p Wants

Scenario: A service fails after changing ExecStart. First check systemctl status, unit overrides with systemctl cat, journalctl -u, binary path and SELinux denials. After a unit edit run systemctl daemon-reload; use systemd-analyze verify /etc/systemd/system/name.service to validate syntax. systemctl restart is disruptive; test in a VM before production. Boot recovery involving GRUB, LUKS or initramfs is version/boot-mode specific; secure console access and a snapshot are mandatory.

Chapter 27 — Networking incident runbook

Trace from link to DNS to TCP to application: ip -br link; ip -br addr; ip route; nmcli connection show --active; resolvectl status (if available); getent hosts example.com; ss -lntp; curl -vk --connect-timeout 3 https://service.example (avoid exposing secrets). On RHEL NetworkManager commonly manages persistent profiles via nmcli; transient ip route add changes do not survive restart. Inspect firewall-cmd --list-all and SELinux before changing access rules.

Failure patterns: no link/carrier → NIC or switch; no default route → routing/profile; IP works but hostname fails → DNS; TCP refused → no listener/firewall reject; TCP timeout → route/firewall/drop; TLS handshake fails → certificate, SNI, cipher or clock. Packet capture (tcpdump -ni IFACE host IP and port 443) requires authorization because it may contain sensitive traffic.

Interview: What does ss -lntp show? Listening TCP sockets, numeric addresses, processes (with sufficient privilege). It does not prove remote reachability.

Chapter 28 — Production incident simulations

Incident 1: Host load 20, CPU only 25%

Evidence: uptime high; vmstat r=1 b=18; many D tasks; iostat high latency; kernel storage timeouts. Hypothesis: blocked I/O, not CPU saturation. Response: protect data, engage storage team, identify failing mount/device, consider controlled failover. Verification: D-state backlog clears, I/O latency and service response times return to baseline. Postmortem: add storage latency, PSI and device error alerts.

Incident 2: Service repeatedly restarts

Evidence: systemctl status shows auto-restart; journalctl -u has permission denied. Hypotheses: filesystem permissions, SELinux denial, missing path, unit sandbox restriction. Response: inspect namei -l, ls -Z, ausearch -m AVC -ts recent if audit tools are present, unit sandbox options; correct least-privilege configuration. Avoid: globally disabling SELinux.

Incident 3: LV grown but application still reports full filesystem

Evidence: lvs reports 12 GiB; df -hT reports 8 GiB XFS. Root cause: filesystem was not grown. Response: verify correct LV and mount; run xfs_growfs /mountpoint, validate df and write test. Prevent: include block-device and filesystem validation in storage change checklist.

Incident 4: High memory use after deployment

Evidence: RSS and memory PSI rising; memory.events records oom_kill. Hypotheses: application leak, workload increase, too-small cgroup limit. Response: collect metrics and heap evidence, compare deployment versions, mitigate via rollback or limit adjustment after capacity review. Avoid: automatically assuming page cache is the problem.

Incident 5: Full /var but du looks small

Evidence: df reports 100%, du sums far less; lsof +L1 shows deleted open log file. Root cause: open file retains blocks. Response: coordinate safe reopen/restart of writer, ensure logrotate configuration and disk alerts. Avoid: deleting arbitrary files in /var/lib.
