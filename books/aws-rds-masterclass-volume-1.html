Chapter 1 — Relational databases, SQL, ACID and transactions

1.1 Why databases exist

A database stores related data durably and lets concurrent clients query or modify it. A DBMS is the software that manages data, transactions, recovery, security and query execution. An RDBMS represents logical data as relations (tables) and exposes a relational query language, typically SQL. PostgreSQL is a DBMS; Amazon RDS is a managed service that can operate PostgreSQL for you.

A table has rows (tuples) and columns (attributes). A primary key uniquely identifies a row; a foreign key enforces a relationship between tables. A unique constraint prevents duplicates, a check constraint limits accepted values, and NOT NULL rejects missing values. Referential integrity is enforced by the database even if application code has a bug.

Example: a commerce application stores customers, orders, and order_items. An order belongs to one customer; an item belongs to one order. Storing customer names on every order creates update anomalies, whereas storing customer_id makes relationships explicit.

erDiagram
  CUSTOMERS ||--o{ ORDERS : places
  ORDERS ||--|{ ORDER_ITEMS : contains
  PRODUCTS ||--o{ ORDER_ITEMS : referenced_by
  CUSTOMERS { bigint id PK

1.2 Relational theory in practical terms

A relation is a set of tuples in the formal model; real SQL tables have bag (multiset) semantics unless DISTINCT is used. The logical query describes what to return; the planner chooses how to get it. Projection chooses columns, selection filters rows, joins combine relationships, and aggregation summarizes groups. Query results have no guaranteed order without ORDER BY.

SQL families

  • DDL: CREATE, ALTER, DROP — define structures.
  • DML: INSERT, UPDATE, DELETE — change data.
  • DQL: SELECT — read data (terminology varies).
  • DCL: GRANT, REVOKE — privileges.
  • TCL: BEGIN, COMMIT, ROLLBACK, SAVEPOINT — transactions.

Lab 1A — Schema and constraints

Where: psql connected to a disposable PostgreSQL database (local PostgreSQL is fine for this chapter).

CREATE SCHEMA IF NOT EXISTS shop;
CREATE TABLE shop.customers (
  customer_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text NOT NULL UNIQUE,
  full_name text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
CREATE TABLE shop.orders (
  order_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES shop.customers(customer_id),
  status text NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending','paid','cancelled')),
  amount numeric(12,2) NOT NULL CHECK (amount >= 0),
  created_at timestamptz NOT NULL DEFAULT now()
);
INSERT INTO shop.customers(email,full_name)
VALUES ('ada@example.test','Ada Lovelace');
INSERT INTO shop.orders(customer_id,amount)
SELECT customer_id, 1499.00 FROM shop.customers WHERE email='ada@example.test';
SELECT c.email,o.order_id,o.amount FROM shop.customers c
JOIN shop.orders o ON o.customer_id=c.customer_id;

Line-by-line: CREATE SCHEMA creates a namespace; IF NOT EXISTS permits reruns; IDENTITY generates keys; PRIMARY KEY requires uniqueness and non-null values; UNIQUE rejects duplicate emails; REFERENCES enforces parent existence; CHECK enforces domain rules; numeric(12,2) stores exact decimal values; DEFAULT now() supplies timestamps; INSERT ... SELECT derives a foreign key safely; JOIN ... ON connects related rows.

Representative output:

CREATE SCHEMA
CREATE TABLE
CREATE TABLE
INSERT 0 1
INSERT 0 1
      email       | order_id | amount
------------------+----------+---------
 ada@example.test |        1 | 1499.00
(1 row)

Negative test: INSERT INTO shop.orders(customer_id,amount) VALUES (999999,20); should fail with a foreign-key violation; this is evidence the invariant is enforced in the database.

1.3 ACID, carefully defined

  • Atomicity: a transaction's changes commit together or are rolled back together.
  • Consistency: a transaction takes the database from one state satisfying declared invariants to another; application-level business rules still need design.
  • Isolation: concurrent transactions interact according to the selected isolation level, not necessarily as if every transaction ran serially.
  • Durability: committed changes survive failures under the database's configured durability guarantees; backups are still necessary.

A transaction is a logical unit of work. BEGIN starts it, COMMIT makes it permanent, ROLLBACK undoes uncommitted changes. PostgreSQL defaults to READ COMMITTED, where each statement normally sees a new snapshot. PostgreSQL REPEATABLE READ uses a stable transaction snapshot; SERIALIZABLE detects dangerous dependency patterns and may abort transactions with SQLSTATE 40001, requiring a retry of the whole transaction.

Lab 1B — Atomic transfer

CREATE TABLE shop.accounts (
  account_id int PRIMARY KEY,
  balance numeric(12,2) NOT NULL CHECK (balance >= 0)
);
INSERT INTO shop.accounts VALUES (1,1000),(2,200);
BEGIN;
UPDATE shop.accounts SET balance=balance-150 WHERE account_id=1;
UPDATE shop.accounts SET balance=balance+150 WHERE account_id=2;
COMMIT;
SELECT * FROM shop.accounts ORDER BY account_id;

Expected: account 1 = 850.00, account 2 = 350.00; sum remains 1200.00. Failure experiment: begin a transfer of 2000 from account 1; the CHECK fails. ROLLBACK the transaction; verify no partial transfer remains. Production financial workflows also need authorization, idempotency, concurrency controls, and ledger design.

1.4 Normalization, denormalization and indexes

First normal form asks for atomic field values in a table design; second normal form removes dependencies on part of a composite key; third normal form removes non-key transitive dependencies. Normalize transactional data first; denormalize deliberately when measured reads justify the maintenance cost. An index speeds certain predicates and orderings but consumes space and slows writes. A B-tree index on orders(customer_id, created_at DESC) helps customer history queries; it may not help WHERE status='paid' without an appropriate access path.

Troubleshooting case

Symptom: duplicate orders after API retry. Cause candidates: no idempotency key, retrying non-idempotent inserts, missing unique constraint. Fix: require a unique client request key, enforce it with a database unique constraint, and return the prior result on replay. Merely increasing isolation is not a substitute for idempotency.

Senior interview practice

Q: Can a foreign key replace application validation? A: It protects referential integrity, but not authentication, authorization or domain-specific workflows. Use both database constraints and application checks.

Q: Why use numeric instead of float for money? A: Decimal fixed-scale calculations avoid binary floating-point representation surprises; still define rounding and currency rules.

Q: Why can a transaction fail at COMMIT? A: Serialization conflicts, deferred constraints, I/O failures and other errors may surface then. Clients must handle failures and retry safely when appropriate.

Chapter 2 — Amazon RDS fundamentals and responsibility model

2.1 What RDS is and is not

Amazon Relational Database Service (RDS) provisions and operates supported relational engines. It automates or simplifies tasks such as instance provisioning, infrastructure maintenance, automated backups, monitoring integration, storage configuration, failover orchestration and some patch workflows. RDS is not a new SQL language and does not automatically repair inefficient schemas, poorly written queries, broken access policies or flawed application transactions.

RDS database instances are managed compute endpoints running database engines; storage and networking are configured through RDS resource settings. Some deployments use a DB cluster model (for example Multi-AZ DB clusters), and Aurora has a different storage/compute architecture. Never assume that all RDS deployment types share identical failover, read endpoint or storage behavior.

Managed versus self-managed

Concern Self-managed PostgreSQL on EC2 RDS for PostgreSQL
OS patching Customer AWS-managed underlying host
DB schema/indexes Customer Customer
DB query tuning Customer Customer
Backup orchestration Customer RDS features configured by customer
IAM/VPC/security group design Customer Customer
Physical facilities AWS AWS
Engine version upgrade decision Customer Customer controls maintenance settings/upgrade plan
Superuser/root access Usually available Restricted managed privileges

2.2 Shared responsibility and the security boundary

AWS is responsible for security of the cloud (facilities, managed infrastructure). The customer is responsible for security in the cloud: IAM permissions, subnet placement, database users, TLS clients, data classification, retention, application vulnerabilities, backups/restore tests and monitoring. RDS administrative roles are not unrestricted OS root or PostgreSQL superuser. Extensions, parameters and host access may be constrained.

2.3 RDS lifecycle

stateDiagram-v2
  [*] --> Creating
  Creating --> Available
  Available --> Modifying
  Modifying --> Available
  Available --> BackingUp
  BackingUp --> Available
  Available --> Deleting
  Deleting --> [*]

Actual statuses include additional states and differ by engine and operation. The DB endpoint may remain the same logical DNS name across maintenance/failover while its underlying IP changes. Applications should reconnect and re-resolve DNS, not pin an IP.

2.4 Fundamental resource vocabulary

  • DB instance identifier: RDS resource name, not SQL database name.
  • DB name: database created within the engine (for engines/settings that support initial creation).
  • DB instance class: compute capacity and memory profile.
  • Storage type: gp3, io1/io2 or other supported options depending on engine/deployment.
  • DB subnet group: selected VPC subnets in different Availability Zones; actual DB placement depends on deployment.
  • VPC security group: stateful network access policy attached to RDS.
  • Parameter group: database configuration values, some requiring restart.
  • Option group: engine-specific features where applicable.
  • Backup retention: how long automated backups are retained, subject to engine/deployment rules.
  • Maintenance window: preferred time for applicable maintenance, not a guarantee of zero disruption.

Lab 2A — Read-only inventory

Where: AWS CLI v2 on laptop after configuring a named profile.

aws sts get-caller-identity --profile rds-lab
aws rds describe-db-instances --region ap-south-1 --profile rds-lab   --query 'DBInstances[].{Name:DBInstanceIdentifier,Engine:Engine,Status:DBInstanceStatus,Public:PubliclyAccessible}'   --output table
aws rds describe-db-engine-versions --engine postgres --region ap-south-1   --profile rds-lab --query 'DBEngineVersions[].EngineVersion' --output text

Explanation: sts get-caller-identity verifies the account/principal; describe-db-instances is read-only inventory; --query filters returned JSON client-side using JMESPath; --output table formats it; describe-db-engine-versions lists engine versions available in the chosen region, which change over time.

Expected: an account/ARN JSON object, zero or more DB rows, and a list of supported PostgreSQL versions. Never assume an example version is still offered.

Failure modes

AccessDenied: inspect principal, IAM policy, permission boundary and organization SCP. Empty inventory: verify account, profile, region and whether the account truly has RDS instances. Wrong engine expectation: Aurora resources use cluster APIs and should not be inferred from a simple instance list alone.

Senior interview practice

Q: Does RDS mean zero DBA work? A: No. Query plans, schema design, capacity, access policies, maintenance testing and data recovery decisions remain engineering responsibilities.

Q: Can you SSH to an RDS host? A: Not to standard managed RDS database hosts; use documented management APIs, logs and SQL observability instead.

Q: Is Multi-AZ the same as a backup? A: No. High availability protects against certain infrastructure failures; backups and PITR protect against accidental deletion/corruption and support historical recovery.

Chapter 3 — RDS database engines and architectural selection

3.1 Engine families

Amazon RDS supports managed relational engines including PostgreSQL, MySQL, MariaDB, Oracle Database, Microsoft SQL Server and Db2, subject to region, edition and current AWS support. Amazon Aurora is a separately architected AWS relational engine compatible with PostgreSQL or MySQL APIs; compare its architecture explicitly rather than treating it as an ordinary RDS PostgreSQL instance.

Engine Typical fit Major consideration
PostgreSQL Complex SQL, JSONB, rich indexing, extensibility Extension availability and tuning limits on RDS
MySQL Web apps, common ORM workloads Transaction/isolation/replication behavior differs from PostgreSQL
MariaDB MySQL-family applications Version/feature compatibility must be tested
SQL Server Microsoft/.NET and T-SQL ecosystems Editions, licensing, feature availability
Oracle Oracle-dependent enterprise workloads Licensing and migration constraints
Db2 Existing IBM Db2 workloads Engine-specific operational and licensing constraints
Aurora PostgreSQL/MySQL Higher-scale managed architectures Distinct distributed storage, pricing and operational semantics

3.2 Decision framework

Ask: (1) which SQL dialect and driver does the application require? (2) how much downtime is tolerable? (3) peak reads, writes, connections and dataset growth? (4) data residency and regulatory requirements? (5) existing DBA expertise? (6) licensing and total cost? (7) migration complexity? (8) feature and extension requirements? (9) recovery objectives? (10) lock-in tolerance?

Scenario A — Greenfield SaaS: PostgreSQL is a strong starting point when advanced SQL, transactions and JSONB are useful. Scenario B — Legacy .NET application with stored procedures: SQL Server may reduce migration risk. Scenario C — Large write-heavy globally deployed service: benchmark Aurora and alternative architectures; global distribution does not automatically make every read or write strongly consistent.

3.3 Compatibility traps

SERIAL, identity columns, ON CONFLICT, JSON syntax, collation, time zones, isolation behavior and index types vary. ORM portability is partial; vendor-specific migrations must be reviewed. A successful connection test does not prove functional compatibility. Licensing may materially change the economics of Oracle and SQL Server.

Lab 3A — Engine selection exercise

Prepare a one-page architecture decision record (ADR): workload = 1500 writes/s peak, 10k reads/s peak, 500 GiB data, 99.95% service objective, RPO 5 minutes, RTO 30 minutes, team proficient in PostgreSQL. Compare standard RDS PostgreSQL Multi-AZ, Multi-AZ DB cluster and Aurora PostgreSQL. Do not choose solely from these invented workload numbers: measure query patterns, storage and connection behavior and verify each option's capabilities and prices in your region.

Deliverable: context, options, expected performance test, failure/recovery test, cost assumptions, security implications and reversible migration strategy.

Senior interview practice

Q: Why not always choose Aurora? A: Different costs, migration compatibility, feature behavior, operational constraints and workload characteristics may favor standard RDS.

Q: What makes an engine migration risky? A: SQL dialect, stored procedures, data types, collations, extensions, driver behavior, transaction semantics and operational cutover.

Q: How do you evaluate vendor lock-in? A: Inventory proprietary features, define export paths, rehearse migrations and price the operational benefit against switching cost.

Chapter 4 — RDS architecture, control plane and data plane

4.1 Control plane versus data plane

The control plane accepts AWS API operations: CreateDBInstance, ModifyDBInstance, DescribeDBInstances, CreateDBSnapshot and deletion. It orchestrates resources and returns status asynchronously. The data plane is the database protocol endpoint: a client resolves the RDS DNS endpoint and sends PostgreSQL wire-protocol messages over TCP/TLS to the DB. aws rds describe-db-instances is not a SQL query and does not read application rows.

sequenceDiagram
  participant Dev as Engineer/CI
  participant API as RDS API control plane
  participant RDS as RDS managed infrastructure
  participant App as App inside VPC
  participant DB as PostgreSQL data plane
  Dev->>API: CreateDBInstance request
  API-->>Dev: Creating / resource ID
  API->>RDS: Orchestrate compute, storage, network
  RDS-->>API: Available and endpoint
  App->>DB: TLS + authentication
  App->>DB: SELECT / INSERT / COMMIT
  DB-->>App: Rows / transaction result

4.2 Network request lifecycle

  1. Application resolves mydb.abc123.region.rds.amazonaws.com using DNS.
  2. Client attempts TCP connection to port 5432 (PostgreSQL default).
  3. VPC routing, security groups and NACLs must allow the path.
  4. TLS negotiates if configured/requested; use certificate validation for production.
  5. PostgreSQL authenticates user and selects a database.
  6. SQL parser, planner and executor process the statement.
  7. Data is read from buffers/storage or modified through transaction machinery.
  8. Commit confirmation is sent according to durability settings.

Private RDS means it has no direct public accessibility; clients require VPC-reachable network paths. An RDS security group permitting 5432 from an EC2 security group is safer than opening 5432 to 0.0.0.0/0. A public RDS endpoint is not a substitute for access controls.

4.3 Failure and failover semantics

Single-AZ instances do not provide the same infrastructure failover characteristics as Multi-AZ. Multi-AZ DB instance standby infrastructure typically is not a read-serving replica. Multi-AZ DB clusters have different topology and read-capable instances. Read replicas support read scaling and are commonly asynchronous; replication lag means reads can be stale. Failover can interrupt sessions and roll back in-flight transactions; design clients for reconnection and idempotent retry. Never assume exactly-once execution after a timeout: a commit may have succeeded even if its acknowledgement was lost.

4.4 Performance anatomy

Latency comprises application queuing, network round trips, connection acquisition, server CPU, lock waits, buffer/cache misses, storage I/O and result transfer. Throughput is constrained by the bottleneck, not simply the instance's vCPU count. A slow endpoint can result from exhausted app connection pools even when DB CPU is low. Distinguish metrics: CPU utilization, freeable memory, database connections, read/write latency, disk queue depth, free storage, and transaction/lock waits.

Lab 4A — Follow a query end-to-end

Where: application host with psql and database credentials; database from Chapter 6 or local PostgreSQL.

getent ahostsv4 "$RDS_ENDPOINT"   # Linux DNS resolution
nc -vz "$RDS_ENDPOINT" 5432       # TCP reachability; nc may need installation
psql "host=$RDS_ENDPOINT port=5432 dbname=appdb user=app_reader sslmode=verify-full sslrootcert=$HOME/.postgresql/global-bundle.pem" -c 'SELECT current_database(), inet_server_addr(), now();'

Explanation: getent queries system DNS; nc -vz tests TCP without authenticating; psql performs a real PostgreSQL connection; sslmode=verify-full validates the CA and hostname; sslrootcert points to AWS's RDS CA bundle downloaded from the official AWS trust store. app_reader must already exist. Avoid passing passwords in command arguments; use a protected PGPASSFILE or interactive prompt.

Sample output: Connection ... succeeded!, then one SQL result row. DNS success + TCP failure points toward network filtering/routing; TCP success + password authentication failed points toward credentials; TLS certificate errors point toward trust/hostname/time configuration.

Senior interview practice

Q: Can a successful nc prove RDS is healthy? A: No. It proves a TCP connection can be established, not that SQL, auth, storage or queries work.

Q: Why should apps not cache the RDS endpoint IP? A: Failover or maintenance can change the resolved address; DNS name and connection retry are required.

Q: Is an RDS read replica an HA replacement? A: Not automatically; asynchronous replication and manual/engine-specific promotion considerations differ from Multi-AZ HA mechanisms.

Chapter 5 — AWS identity, CLI, budget and secure lab networking

5.1 Preflight and cost safety

RDS, EC2, EBS, backups, public IPv4, data transfer and other resources can cost money. Set an AWS Budget and alert before deployment and consult the current AWS Pricing Calculator; budgets are alerts, not hard spending caps. Free-tier eligibility varies by account and date; do not assume these labs are free. Use one disposable lab account, a tagged resource prefix and a planned teardown. Avoid production accounts.

Where: Debian 12 or comparable Linux shell with AWS CLI v2 installed from AWS's official instructions. Verify:

aws --version
psql --version
aws configure list-profiles
aws sts get-caller-identity --profile rds-lab

Use IAM Identity Center or a short-lived role session where possible. Avoid long-lived access keys. Region for examples is ap-south-1; substitute your own. Set AWS_PROFILE=rds-lab and AWS_REGION=ap-south-1 for a shell session after validating the identity.

For the lab, you may reuse a pre-existing approved VPC and SSM-managed EC2 host. If building from scratch, create a VPC, two DB subnets in separate AZs, a DB subnet group, an EC2 instance profile with AmazonSSMManagedInstanceCore, SSM network access via appropriate VPC endpoints or NAT/internet egress, and security groups. A private EC2 instance without NAT or SSM endpoints may be unreachable by Session Manager. An EC2 instance with a public IP can reach SSM via outbound internet if correctly secured; it still must be in a network path to RDS. No inbound SSH is needed for Session Manager.

5.3 Security groups, least privilege and secrets

Define an RDS security group that allows inbound TCP 5432 only from the application/admin EC2 security group. SGs are stateful. Network ACLs are stateless and can block return traffic if customized. IAM permission to create RDS is different from PostgreSQL role permission to execute SQL. Keep the master credential in Secrets Manager or use the RDS-managed master password feature; do not paste passwords into Terraform state or shell history.

Lab 5B — Create a dedicated DB security group

DB_SG=$(aws ec2 create-security-group   --group-name rds-v1-db-sg --description 'RDS Volume 1 PostgreSQL access'   --vpc-id "$VPC_ID" --query GroupId --output text)
aws ec2 authorize-security-group-ingress   --group-id "$DB_SG" --protocol tcp --port 5432   --source-group "$APP_SG"
aws ec2 describe-security-groups --group-ids "$DB_SG"   --query 'SecurityGroups[0].IpPermissions' --output json

Prerequisites: VPC_ID is an existing VPC; APP_SG is the security group attached to the SSM-managed EC2 host in the same VPC (or otherwise valid SG reference topology). create-security-group creates the target SG and prints its ID; authorize-security-group-ingress allows source-group traffic on PostgreSQL's port; describe verifies it. No internet-wide inbound rule is created.

Representative output: an IpPermissions entry with FromPort: 5432, ToPort: 5432, and UserIdGroupPairs containing the app SG ID.

5.4 IAM policy example for inventory-only automation

{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "RdsReadOnlyInventory",
    "Effect": "Allow",
    "Action": ["rds:DescribeDBInstances", "rds:DescribeDBSubnetGroups", "rds:DescribeDBSnapshots"],
    "Resource": "*"
  }]
}

Line-by-line: Version is the IAM policy grammar version; Statement holds grants; Sid is an optional label; Effect: Allow grants listed actions; Action enumerates read-only RDS API permissions; Resource: * is used here because some describe actions do not support resource-level restriction. Add write permissions only to a dedicated lab provisioning role and constrain resources/tags where AWS action support allows.

Troubleshooting

SSM target not online: inspect EC2 IAM instance profile, SSM Agent, VPC endpoint/NAT connectivity, DNS and endpoint SGs. RDS subnet group invalid: ensure suitable subnets across at least two AZs and supported VPC configuration. Security group rule fails: validate SG IDs, VPC, permissions and group-reference restrictions. Budget alert did not stop billing: expected—budgets are alerts, not hard limits.

Senior interview practice

Q: Why use SG-to-SG rules? A: Access tracks workload membership without relying on dynamic private IPs; still control who can attach or modify those groups.

Q: Can IAM alone allow PostgreSQL SQL access? A: No. SQL access also needs a reachable endpoint and database authentication/authorization; IAM DB authentication is an optional supported authentication path, not blanket SQL permission.

Chapter 6 — Provision, connect, test and remove PostgreSQL RDS

6.1 Lab contract

Goal: create a private, encrypted, Single-AZ PostgreSQL DB instance in an approved lab VPC, connect from an SSM-managed EC2 host, run SQL, inspect metrics and delete everything. Prerequisites: completed Chapter 5; AWS CLI v2; VPC with two suitable subnets in distinct AZs; app EC2 security group; EC2 host reachable via Session Manager; adequate IAM rights; current cost review. Caution: instance class, storage options, and version support vary by region. The values below are examples, not guaranteed availability.

6.2 Create DB subnet group

Where: AWS CLI on laptop.

export AWS_PROFILE=rds-lab AWS_REGION=ap-south-1
export DB_ID=rds-v1-pg-lab
aws rds create-db-subnet-group   --db-subnet-group-name rds-v1-private-subnets   --db-subnet-group-description 'Private DB subnets for Volume 1'   --subnet-ids "$DB_SUBNET_A" "$DB_SUBNET_B"   --tags Key=Project,Value=RDSMasterclass Key=Environment,Value=Lab

Chapter 7 — PostgreSQL internals, MVCC, WAL, buffers and vacuum

7.1 PostgreSQL process and memory model

PostgreSQL uses a server process architecture: a postmaster (main server process) coordinates background processes and typically one backend process per client connection. The backend parses, plans and executes SQL, uses shared buffers, consults catalogs and participates in transaction/locking mechanisms. Important components include checkpointer, background writer, WAL writer, autovacuum launcher/workers and statistics mechanisms. Exact process names/behavior vary by PostgreSQL version and managed engine settings.

flowchart TB
  C[Application client] --> P[PostgreSQL backend process]
  P --> Parser[Parser / rewrite / planner / executor]
  Parser --> SB[(Shared buffers)]
  Parser --> WAL[(WAL buffers)]
  SB <--> Pages[(Table/index pages on storage)]
  WAL --> WALDisk[(WAL files)]
  CK[Checkpointer / background writer] --> Pages
  V[Autovacuum workers] --> Pages

Shared buffers cache database pages. PostgreSQL also benefits from the OS page cache; shared_buffers is not the entirety of cached data. Work memory (work_mem) is per sort/hash operation rather than a global total; setting it too high with many concurrent queries can cause memory pressure. Maintenance memory is used by operations such as vacuum and index creation, subject to operation-specific settings.

7.2 A SELECT request internally

  1. Client sends query over the wire protocol.
  2. Parser checks syntax and creates a parse tree.
  3. Analyzer resolves names/types and privileges.
  4. Rewriter applies rewrite rules/views.
  5. Planner estimates costs/cardinality and selects access paths.
  6. Executor runs scans, joins, filters, aggregates and sorts.
  7. Buffer manager finds needed pages in shared buffers or requests storage reads.
  8. MVCC snapshot determines visible row versions.
  9. Result rows are serialized back to the client.

Key insight: EXPLAIN reports estimated plan; EXPLAIN (ANALYZE, BUFFERS) actually executes the query and reports observed timing/buffer activity. Avoid EXPLAIN ANALYZE on a destructive DML statement unless enclosed in a rollback transaction and you understand side effects.

Lab 7A — Query plans

CREATE TABLE training.measurements (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  device_id int NOT NULL,
  recorded_at timestamptz NOT NULL,
  reading numeric(10,2) NOT NULL
);
INSERT INTO training.measurements(device_id,recorded_at,reading)
SELECT (g % 100), now() - (g || ' seconds')::interval, (g % 1000)::numeric / 10
FROM generate_series(1,100000) AS g;
ANALYZE training.measurements;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM training.measurements WHERE device_id=42
ORDER BY recorded_at DESC LIMIT 10;
CREATE INDEX idx_measurements_device_time
  ON training.measurements(device_id,recorded_at DESC);
ANALYZE training.measurements;
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM training.measurements WHERE device_id=42
ORDER BY recorded_at DESC LIMIT 10;

Line-by-line: GENERATED ... IDENTITY supplies IDs; generate_series creates test rows; % distributes device IDs; ANALYZE refreshes statistics; EXPLAIN (ANALYZE, BUFFERS) measures real execution and cache usage; composite B-tree index matches equality on device_id followed by descending time order. Planner may still select a sequential scan depending on table size, cache, costs and selectivity. Expected pattern: first plan often scans/sorts; second may use an index scan and reduce scanned rows. Compare actual rows, planning time, execution time and buffer hits/reads, not just the operator name.

7.3 MVCC and row versions

Multi-Version Concurrency Control lets readers see a consistent snapshot while writers create new row versions. PostgreSQL heap tuples carry transaction metadata (xmin/xmax); updates generally create new row versions rather than overwriting the old version in place. Old versions remain until safe to reclaim. This reduces reader/writer blocking but makes vacuum essential. Visibility is not determined by timestamps alone: transaction IDs, commit state and snapshots matter.

sequenceDiagram
  participant T1 as Transaction A
  participant DB as PostgreSQL
  participant T2 as Transaction B
  T1->>DB: BEGIN; SELECT balance (snapshot)
  T2->>DB: UPDATE balance; COMMIT
  T1->>DB: SELECT balance again
  Note over T1,DB: READ COMMITTED can see new value on next statement
  Note over T1,DB: REPEATABLE READ keeps stable transaction snapshot

Lab 7B — Two sessions and isolation

Where: two separate psql sessions connected to same disposable DB.

Session A:

CREATE TABLE IF NOT EXISTS training.counter (id int PRIMARY KEY, value int NOT NULL);
INSERT INTO training.counter VALUES (1,10) ON CONFLICT (id) DO UPDATE SET value=10;
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT value FROM training.counter WHERE id=1;

Session B:

UPDATE training.counter SET value=20 WHERE id=1;
SELECT value FROM training.counter WHERE id=1;

Session A:

SELECT value FROM training.counter WHERE id=1;
COMMIT;
SELECT value FROM training.counter WHERE id=1;

Expected: first two Session A reads return 10; after COMMIT, next statement sees 20. Repeat using READ COMMITTED: the second SELECT in the transaction should normally see 20 after B commits. For a full isolation exercise, add concurrent updates and observe lock waits, serialization errors and deadlock detection.

7.4 Write-ahead logging and crash recovery

WAL records changes before modified data pages must be flushed to permanent storage. During a commit, PostgreSQL ensures required WAL is flushed according to configured durability settings, so crash recovery can replay committed changes even if corresponding heap pages had not yet been written. A checkpoint bounds recovery work by flushing dirty pages and recording a recovery starting point. WAL also supports replication and point-in-time recovery workflows. RDS controls many underlying backup and storage details, so do not assume self-managed filesystem access.

Important distinctions: WAL is not a backup by itself; a replica is not a backup; synchronous replication is not the same as a zero-data-loss guarantee under every failure scenario. Verify actual engine/deployment guarantees and recovery tests.

Lab 7C — WAL and transactions

SHOW wal_level;
SHOW synchronous_commit;
SHOW shared_buffers;
SHOW work_mem;
SELECT pg_current_wal_lsn();
BEGIN;
INSERT INTO training.events(message) VALUES ('wal experiment');
COMMIT;
SELECT pg_current_wal_lsn();

Explanation: SHOW reads active configuration; pg_current_wal_lsn() displays a log sequence number; insert/commit produces WAL activity; the second LSN may advance. Exact values are nondeterministic and may advance due to other concurrent activity. Do not equate the difference with only your transaction's WAL bytes without controlled measurement.

7.5 Vacuum, bloat and autovacuum

Updates and deletes leave row versions that may become dead to all active snapshots. VACUUM reclaims reusable space and helps maintain transaction ID health; autovacuum automates this. Long-running transactions, replication slots and other retention conditions can prevent cleanup and contribute to bloat. VACUUM FULL rewrites a table and takes an intrusive lock; do not schedule it casually. ANALYZE refreshes planner statistics; autovacuum may run both vacuum and analyze operations. PostgreSQL's transaction ID wraparound protection makes vacuum an availability concern, not just a performance optimization.

Lab 7D — Observe dead tuples

SELECT relname,n_live_tup,n_dead_tup,last_autovacuum,last_autoanalyze
FROM pg_stat_user_tables WHERE schemaname='training';
UPDATE training.measurements SET reading=reading+1 WHERE id <= 10000;
SELECT relname,n_live_tup,n_dead_tup FROM pg_stat_user_tables
WHERE schemaname='training' AND relname='measurements';
VACUUM (ANALYZE) training.measurements;
SELECT relname,n_live_tup,n_dead_tup,last_vacuum FROM pg_stat_user_tables
WHERE schemaname='training' AND relname='measurements';

Explanation: statistics views expose approximate, asynchronously updated estimates; UPDATE creates new row versions; VACUUM (ANALYZE) reclaims eligible tuples and refreshes statistics; post-vacuum dead-tuple counts may not immediately be zero if old snapshots still need tuples or stats lag. Do not run manual vacuum aggressively in production without investigating workload, table size and locking.

7.6 Locks, waits and deadlocks

Row locks protect concurrent updates; table locks protect structural and data operations. A deadlock occurs when transactions wait cyclically on resources; PostgreSQL detects it and aborts one participant. pg_stat_activity exposes sessions and wait events; pg_locks exposes lock state. Avoid killing sessions without determining the owning application, business transaction and rollback cost.

Lab 7E — Lock wait investigation

Session A:

BEGIN;
UPDATE training.counter SET value=value+1 WHERE id=1;
-- Keep transaction open temporarily; DO NOT do this in production.

Session B:

SET lock_timeout='3s';
UPDATE training.counter SET value=value+1 WHERE id=1;

Expected in B: ERROR: canceling statement due to lock timeout. Session A: ROLLBACK;. Observe while waiting in a third session:

SELECT pid,usename,state,wait_event_type,wait_event,
       pg_blocking_pids(pid) AS blockers, left(query,120) AS query
FROM pg_stat_activity
WHERE datname=current_database();

Troubleshooting: find blocker PID and transaction age; ask why the transaction remains open; shorten transaction scope; ensure appropriate indexes; set sensible statement/lock timeouts; avoid blind session termination.

7.7 Database connections and pooling

A PostgreSQL backend per client connection consumes memory and scheduler overhead. Hundreds of idle connections can still matter. Use bounded application connection pools, reasonable idle timeouts, and consider RDS Proxy where supported. Connection pool sizing must reflect total application replicas × per-replica pool size, plus operational sessions, migration jobs and failover headroom. The database max_connections limit is not a target to saturate.

Senior interview practice

Q: What is the difference between WAL and data files? A: WAL is an ordered change record used for recovery/replication; data files contain heap/index pages that may be flushed later.

Q: Why does a read-only SELECT sometimes wait? A: DDL locks, resource contention, I/O, buffer pin waits or other mechanisms; MVCC does not eliminate every wait.

Q: Why is high n_dead_tup concerning? A: It can signal vacuum lag, long snapshots or high churn, increasing bloat and I/O; verify estimates and blockers before tuning.

Q: What does a buffer hit prove? A: PostgreSQL found a page in shared buffers; it does not mean the query is necessarily efficient or that all underlying system cache effects are captured.

Q: How do you respond to a deadlock? A: Capture logs/SQLSTATE, identify lock order, ensure transactions acquire resources consistently, shorten critical sections and retry aborted transactions with bounded backoff.

Interview question bank

  1. Explain ACID with a bank transfer. Atomic debit/credit, constraints, isolation and durable commit; also describe retries and idempotency.
  2. What does RDS manage? Infrastructure lifecycle, backups and selected maintenance operations; not app SQL correctness or access design.
  3. RDS versus EC2 PostgreSQL? RDS reduces OS/backup operational burden but restricts host access and some extensions/settings.
  4. RDS versus Aurora? Aurora has a distinct storage architecture and deployment/price characteristics; choose by measured workload.
  5. Can a private RDS be accessed from a laptop? Yes through secure VPC connectivity such as VPN, approved tunnel or SSM host, not direct public internet exposure.
  6. Why two AZs in DB subnet group? To give RDS eligible placement across AZs; actual failover depends on deployment.
  7. What is an RDS endpoint? DNS hostname for the DB service; not a fixed IP address.
  8. How do you verify TLS? Client sslmode=verify-full with trusted CA plus pg_stat_ssl session check.
  9. What is MVCC? Visibility of multiple row versions under transaction snapshots.
  10. What is WAL? Write-ahead change log used for crash recovery and replication.
  11. Why can PostgreSQL grow after DELETE? Dead tuples may remain until vacuum can reclaim space; physical file size need not shrink.
  12. Why is EXPLAIN ANALYZE potentially dangerous? It executes the statement and can modify data or create heavy load.
  13. What causes connection exhaustion? Too many clients, leaked pools, scaling replicas or long-held sessions.
  14. What is an idempotent API? Repeating the same request has the same intended effect; use stable request keys and DB uniqueness.
  15. How do you debug slow RDS queries? Correlate app latency, pool waits, DB CPU/I/O/locks, query plans and load trends.
  16. How do you prevent SQL injection? Parameterized queries and least-privileged roles, never string-concatenate untrusted SQL.
  17. What is a DB parameter group? Engine configuration settings; some apply immediately, others require reboot.
  18. Why not use public RDS for convenience? Expands exposure and complicates network threat model; use private connectivity.
  19. Why are backups not enough without restore drills? Recovery time, completeness and procedural correctness are unproven until tested.
  20. What happens when a client loses connection during COMMIT? Commit outcome may be ambiguous; query by idempotency key or reconcile before retrying side effects.
  21. What is read replica lag? Delay between source commits and replica visibility; stale reads are possible.
  22. What does Multi-AZ protect against? Certain infrastructure/AZ failures, not application bugs or all logical corruption.
  23. What is a lock timeout? Maximum wait for a lock; it protects request latency but doesn't repair contention.
  24. What is transaction ID wraparound? Finite transaction IDs require vacuum/freeze maintenance to preserve visibility safety.
  25. How would you present a production design review? Requirements, workload measurements, RPO/RTO, security, HA, tests, cost, rollback and observability.
