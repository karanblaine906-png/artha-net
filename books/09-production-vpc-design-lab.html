CHAPTER 9 --- PRODUCTION VPC DESIGN LAB

Page: 237--282

9.1 Chapter Objective

This chapter converts AWS VPC theory into a complete production-style network design.

You will design a highly available three-tier AWS network containing:

Internet
   |
   v
Application Load Balancer
   |
   v
Private Application Tier
   |
   v
Private Database Tier

The environment will span two Availability Zones and include controlled outbound connectivity, private AWS service access, logging, DNS, security controls, validation, failure testing, and troubleshooting exercises.

9.3 Production Requirement

Assume a company is deploying:

Customer-facing web application

Requirements:

1. Application must be reachable over HTTPS.

2. Application servers must not have public IP addresses.

3. Database must never be directly internet-facing.

4. Architecture must survive failure of one application instance.

5. Application tier must span two Availability Zones.

6. Database architecture must support Multi-AZ deployment.

7. Private application servers need controlled outbound access.

8. Application servers must access selected AWS services privately where practical.

9. Administrative access should not require public SSH exposure.

10. Network activity must be observable.

11. Infrastructure must be suitable for later Terraform automation.

12. Network boundaries must follow least privilege.

We need three logical tiers:

PUBLIC TIER
PRIVATE APPLICATION TIER
PRIVATE DATABASE TIER

=

=

9.5 Why Separate Tiers?

Do not place everything in one subnet.

Poor architecture:

Internet
   |
   v
EC2 + Database + Admin Tools
same public subnet

Better:

Internet
   |
   v
ALB
   |
   v
Private Application
   |
   v
Private Database

Each tier has a different exposure requirement.

9.6 Step 2 --- Choose VPC CIDR

We choose:

10.60.0.0/16

This provides a large address pool for the lab.

Before using this in a real company, verify that it does not overlap:

Other VPCs
On-premises networks
VPN networks
Partner networks
Future regions
Transit networks

9.7 CIDR Capacity

A /16 contains:

65,536 IPv4 addresses

We do not create one giant subnet.

We divide it into smaller subnets according to:

Tier
Availability Zone
Growth
Operational purpose

Use six /24 subnets.

Public 10.60.1.0/24 10.60.2.0/24 Application 10.60.11.0/24 10.60.12.0/24 Database 10.60.21.0/24 10.60.22.0/24

9.9 Why Leave Address Gaps?

Notice:

Public:
1, 2

Application:
11, 12

Database:
21, 22

This is intentional.

It leaves conceptual space for future expansion:

10.60.3.0/24
10.60.13.0/24
10.60.23.0/24

A clean IP plan makes infrastructure easier to operate.

9.10 Availability Zone Design

We use two AZs.

Example:

AZ-A
AZ-B

Do not hard-code assumptions that another AWS account's named ap-south-1a represents the same physical Availability Zone as yours.

AWS maps AZ names per account.

For cross-account designs, AZ IDs can provide a more consistent reference.

9.11 Failure-Domain Principle

Architecture:

AZ-A
 |
 +--> Public-A
 +--> App-A
 +--> DB-A

AZ-B
 |
 +--> Public-B
 +--> App-B
 +--> DB-B

If one AZ has a major problem, the second AZ provides another failure domain.

But application and database design must also support failover.

9.14 What Makes These Public Subnets?

The route:

0.0.0.0/0 -> IGW

is the key routing characteristic.

But an EC2 instance would additionally need suitable public addressing and security controls for direct IPv4 internet connectivity.

Subnet naming alone does nothing.

9.15 Step 5 --- NAT Architecture

Private application instances may need outbound connectivity for activities such as:

External APIs
Software updates
Third-party services

For this lab:

App-A -> NAT-A
App-B -> NAT-B

9.16 NAT Placement

NAT Gateways belong in public subnets for this internet-egress architecture.

Public-A
   |
   v
NAT-A

Public-B
   |
   v
NAT-B

Each NAT Gateway uses a public Elastic IP.

9.17 Why One NAT Per AZ?

Possible low-cost design:

App-A ----\
           > NAT-A
App-B ----/

Problem:

NAT-A/AZ-A dependency
Cross-AZ traffic from B
Potential additional transfer cost

More resilient design:

App-A -> NAT-A
App-B -> NAT-B

9.20 Database Route Tables

Database subnets should not automatically receive internet access merely because it is convenient.

A restrictive design may contain:

10.60.0.0/16 -> local

plus only other explicitly required private routes.

Do not automatically add:

0.0.0.0/0 -> NAT

unless the database architecture genuinely requires it.

9.25 Health Check Design

Do not make health checks meaningless.

Weak:

GET /

which always returns:

200

even if dependencies are broken.

A useful health endpoint should reflect the intended health semantics without making every optional dependency a reason to remove the instance.

9.27 ALB Security Group

Inbound:

TCP 443
Source: approved internet range

For a public website this may be:

0.0.0.0/0

and, if IPv6 is enabled:

::/0

according to requirements.

Administrative ports should not be exposed here.

9.28 Application Security Group

Inbound:

TCP 8080
Source:
ALB-SG

Not:

TCP 8080
0.0.0.0/0

The application accepts traffic from the load balancer, not from the entire internet.

9.29 Database Security Group

For PostgreSQL:

TCP 5432
Source:
APP-SG

For MySQL:

TCP 3306
Source:
APP-SG

Use only the database engine port actually required.

9.30 Why Security Group References Matter

Suppose application instances scale:

2
4
10
30

Their private IPs change.

A rule based on:

Source = APP-SG

continues to express architectural identity.

You do not need to constantly update IP lists.

9.31 Egress Rules

Do not forget outbound traffic.

Examples:

ALB -> application
Application -> database
Application -> HTTPS services
Application -> DNS

Security Group egress should reflect operational requirements.

Overly restrictive egress without understanding dependencies can break workloads.

9.32 Step 7 --- Network ACL Strategy

For many workloads:

Security Groups

provide the primary workload access control.

NACLs can remain simple unless subnet-level deny/guardrail requirements exist.

Avoid building hundreds of fragile NACL rules without a clear security requirement.

9.33 NACL Reminder

NACL:

Stateless

Therefore both directions matter.

If allowing:

Client -> Server:443

you must account for return traffic.

9.34 Ephemeral Port Reminder

Example:

Client:
10.60.11.25:53144

Server:
10.60.21.50:5432

Return:

10.60.21.50:5432
        |
        v
10.60.11.25:53144

A stateless filter must permit the required return-port behavior.

9.36 Database Public Accessibility

9.37 Database DNS

    v

9.152 Interview Question --- Why Not Put EC2 in Public Subnet?

Because internet users should reach:

Load Balancer

not application instances directly.

Private application placement reduces direct exposure and centralizes ingress controls.

9.153 Interview Question --- Why NAT?

Private IPv4 workloads may require outbound internet connectivity without accepting unsolicited inbound internet traffic through that NAT path.

9.154 Interview Question --- Why Two NAT Gateways?

To avoid making private subnets in multiple AZs depend on one NAT/AZ path when higher availability is required.

Also reduces unnecessary cross-AZ NAT routing.

9.155 Interview Question --- Why No NAT for Database?

A database usually communicates with private application and managed service paths.

If it does not require general internet egress, there is no reason to provide it.

Least connectivity is safer.

9.156 Interview Question --- SG vs NACL in This Architecture

Security Groups:

Primary workload-level access control
Stateful
SG references

NACLs:

Subnet-level stateless guardrail
Allow/deny
Used carefully

9.157 Interview Question --- How Does ALB Reach Private EC2?

Both are connected through VPC networking.

The ALB sends traffic to registered targets using private network connectivity according to target type/configuration.

The target does not need a public IP.

9.158 Interview Question --- How Do Private Instances Reach S3 Without NAT?

Use an S3 Gateway VPC Endpoint where suitable.

The relevant route tables direct S3 traffic to the endpoint.

9.159 Interview Question --- How Would You Remove SSH?

9.162 Senior Scenario --- DB Failover

Application uses:

Hard-coded DB IP

RDS failover occurs.

Application fails.

Better:

Use database endpoint DNS

and ensure connection/retry behavior handles failover appropriately.

9.163 Senior Scenario --- Secret Retrieval Fails

Application starts but cannot retrieve secret from Secrets Manager.

Investigate separately:

DNS
Endpoint/NAT path
Endpoint SG
IAM role
Identity policy
KMS permission
Endpoint policy
Resource policy if applicable

Network and IAM failures can look similar at application level.

9.164 Senior Scenario --- AccessDenied from S3

Do not change route tables immediately.

If AWS returns:

AccessDenied

the request likely reached an AWS authorization layer.

Investigate:

IAM
Bucket policy
Endpoint policy
KMS
SCP
Permissions boundary

Distinguish authorization from connectivity.

9.165 Senior Scenario --- Could not resolve host

Focus first on:

DNS

Check:

cat /etc/resolv.conf
getent hosts <hostname>
dig <hostname>

Then investigate VPC DNS and resolver architecture.

9.166 Senior Scenario --- Connection timed out

Focus on:

Route
Security Group
NACL
Firewall
Return path
Unreachable target

Use Flow Logs and path analysis.

9.167 Senior Scenario --- Connection refused

Focus on:

Listener
Process
Port
Bind address
Host firewall/reject

Network routing may already be functioning.

9.168 Senior Scenario --- TLS Certificate Error

If TCP connection succeeds but TLS validation fails:

Do not modify VPC routing.

Check:

Certificate hostname
Certificate chain
Expiration
Listener certificate
Client trust
SNI

Troubleshoot the correct layer.

9.169 Senior Scenario --- HTTP 502 from ALB

Potential causes include:

Target connection issue
Application closes connection
Malformed response
Port/protocol mismatch
Target-side problem

Check:

ALB metrics/logs
Target health
Application logs
Listener/target protocol

Do not assume "502 = AWS network broken."

9.170 Senior Scenario --- HTTP 504

Potential:

Backend response timeout
Slow dependency
Network timeout
Application hung
Database latency

Trace:

ALB -> App -> Dependency

and measure each stage.
