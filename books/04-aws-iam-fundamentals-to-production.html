4.2 Why IAM Exists

Imagine an AWS account containing:

EC2 Instances
S3 Buckets
RDS Databases
VPCs
Secrets
KMS Keys
CloudWatch Logs
Production Applications

Now imagine every engineer has unrestricted access.

Engineer
   |
   v
AdministratorAccess
   |
   +--> Production
   +--> Development
   +--> Databases
   +--> Security
   +--> Billing

This creates unnecessary risk.

AWS needs a mechanism to answer:

WHO
 |
 v
can perform
 |
 v
WHAT ACTION
 |
 v
on WHICH RESOURCE
 |
 v
under WHAT CONDITIONS?

That mechanism is IAM.

4.3 What Is IAM?

IAM means:

Identity and Access Management

IAM controls access to AWS resources and APIs.

A useful mental model is:

Principal
   |
   v
Authentication
   |
   v
Authorization
   |
   v
AWS Resource/API

IAM is primarily concerned with:

Identities
Permissions
Roles
Policies
Authentication
Authorization
Access control

4.4 Authentication vs Authorization

These two concepts must be separated.

Authentication

Authentication asks:

Who are you?

Examples:

Password
MFA
Access credentials
Federated sign-in
Workload identity

Authorization

Authorization asks:

What are you allowed to do?

Example:

Can this identity execute:

s3:GetObject

against:

arn:aws:s3:::company-reports/*

4.5 IAM Authorization Mental Model

Principal
   |
   v
Makes Request
   |
   v
AWS Authorization
   |
   +--> Identity Policy
   |
   +--> Resource Policy
   |
   +--> Permissions Boundary
   |
   +--> SCP
   |
   +--> Session Policy
   |
   +--> Other applicable controls
   |
   v
ALLOW or DENY

The complete evaluation logic depends on the request and policy types involved.

4.6 AWS Account Root User

The AWS account root user is created with the AWS account.

It has extremely powerful access.

Examples of operations that may require or involve root credentials include certain account-level tasks.

Production principle:

Do not use the root user for everyday administration.

Protect it carefully.

Recommended controls include:

Strong unique password
MFA
No routine use
Secure recovery mechanisms
Monitoring
No root access keys unless absolutely required

4.7 IAM User

An IAM user represents an identity inside an AWS account.

Concept:

AWS Account
    |
    +--> IAM User: Alice
    |
    +--> IAM User: Bob

An IAM user can have credentials for supported access methods.

However, modern enterprise environments increasingly prefer:

Federation
IAM Identity Center
Roles
Temporary credentials

over creating large numbers of long-lived IAM users.

4.8 IAM Groups

An IAM group is a collection of IAM users.

Example:

Developers Group
       |
       +--> Alice
       +--> Bob
       +--> Charlie

Permissions can be attached to the group.

Developers Group
       |
       v
Developer Policy
       |
       v
Users inherit group permissions

Important:

IAM groups contain users, not IAM roles.

4.9 Why Groups Are Useful

Without groups:

Alice --> Policy
Bob --> Policy
Charlie --> Policy
David --> Policy

With a group:

          Developers
         /    |    \
        /     |     \
     Alice   Bob   Charlie
          |
          v
       Policies

This can simplify permission administration for IAM users.

4.10 IAM Role

An IAM role is an AWS identity with permissions that can be assumed by trusted principals.

Unlike a traditional IAM user, a role is designed around temporary sessions.

Concept:

Principal
   |
   | Assume Role
   v
IAM Role
   |
   v
Temporary Credentials
   |
   v
AWS Resources

Roles are fundamental to production AWS architecture.

4.11 Who Can Assume a Role?

Depending on configuration, trusted principals can include:

AWS services
IAM identities
Other AWS accounts
Federated users
Applications/workloads
OIDC identities
SAML identities

Trust is controlled through the role's trust policy and related authorization requirements.

4.12 Why Roles Are Better for Workloads

Bad architecture:

EC2 Application
      |
      v
Hardcoded Access Key
      |
      v
AWS API

Problems include:

Long-lived credential
Secret storage
Credential rotation
Accidental exposure
Git leakage
Operational overhead

Better:

EC2 Instance
      |
      v
IAM Role
      |
      v
Temporary Credentials
      |
      v
AWS API

4.13 IAM Policy

An IAM policy is a JSON document describing permissions or access-control rules.

Example:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::example-bucket/reports/*"
    }
  ]
}

4.14 Policy Structure

Common elements include:

Version
Statement
Effect
Action
Resource
Condition
Principal

Not every element appears in every policy type.

4.15 Version

Example:

"Version": "2012-10-17"

This is the IAM policy language version.

It is not the date when your policy was created.

That distinction is frequently asked in interviews.

4.16 Statement

A policy can contain one or more statements.

Example:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::example-bucket/*"
    }
  ]
}

The array:

Statement

contains permission statements.

4.17 Effect

Common values:

Allow
Deny

Example:

"Effect": "Allow"

means the statement grants the specified access if the rest of the statement matches and no overriding deny applies.

4.18 Action

Action describes AWS API operations.

Example:

"Action": "s3:GetObject"

Another:

"Action": [
  "s3:GetObject",
  "s3:PutObject"
]

Wildcards can broaden permissions:

"Action": "s3:*"

This means all actions matching the S3 action namespace and should be used only when justified.

4.19 Resource

Resource identifies the AWS resource or resources to which the statement applies.

Example:

"Resource": "arn:aws:s3:::example-bucket/reports/*"

This refers to objects under:

example-bucket/reports/

4.20 Resource Wildcard

Example:

"Resource": "*"

means all resources applicable to that action.

Sometimes AWS APIs require:

"*"

because they do not support resource-level permissions.

But never assume * is necessary.

Check the service authorization documentation.

4.21 Condition

Conditions allow permissions to depend on request context.

Concept:

Allow Action
     |
     v
Only if Condition Matches

Examples of conditions may inspect:

Source IP
Requested Region
Principal tags
Resource tags
MFA context
TLS usage
VPC endpoint
Organization ID

Exact supported condition keys depend on the service and request.

4.22 Condition Example

Example concept:

{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::example-bucket/*",
  "Condition": {
    "Bool": {
      "aws:SecureTransport": "true"
    }
  }
}

This statement allows matching access when the request uses secure transport.

For strict enforcement, organizations commonly design an explicit deny for insecure transport because an allow statement alone does not necessarily block access granted elsewhere.

4.23 Principal

Principal identifies who is allowed or denied by resource-based or trust policies.

Example:

"Principal": {
  "AWS": "arn:aws:iam::111122223333:role/DeploymentRole"
}

You normally do not place Principal in a standard IAM identity-based permissions policy.

The identity to which that policy is attached is already the principal context.

4.24 Identity-Based Policy

An identity-based policy is attached to:

IAM User
IAM Group
IAM Role

Example:

IAM Role
   |
   v
Permissions Policy
   |
   v
S3 Read Permission

Example JSON:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::example-bucket/*"
    }
  ]
}

4.25 Resource-Based Policy

A resource-based policy is attached directly to a supported resource.

Examples include:

S3 bucket policy
KMS key policy
SQS queue policy
SNS topic policy
IAM role trust policy

Concept:

Resource
   |
   v
Resource Policy
   |
   v
Who may access it?

4.26 S3 Bucket Policy Example

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:role/AnalyticsRole"
      },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-data/*"
    }
  ]
}

The policy answers:

WHO?
AnalyticsRole

CAN DO WHAT?
s3:GetObject

ON WHAT?
company-data objects

4.27 IAM Managed Policies

Managed policies exist as reusable policy objects.

Two broad categories are:

AWS managed policies

Customer managed policies

AWS managed policies are created and maintained by AWS.

Customer managed policies are created and controlled by your organization.

4.28 Inline Policies

An inline policy is embedded directly in a single IAM identity.

Concept:

IAM Role
   |
   +--> Inline Policy

It has a one-to-one relationship with that identity.

Managed policies are usually easier to reuse and centrally manage.

4.29 Managed vs Inline Policy

Feature Managed Policy Inline Policy
Separate policy object Yes No
Reusable Yes No
Can attach to multiple identities Yes No
Lifecycle tied directly to one identity No Yes
Central management Easier More limited

Inline policies still have legitimate use cases, but should be chosen intentionally.

4.30 Least Privilege

Least privilege means:

Give only the permissions required to perform the intended task.

Bad:

{
  "Effect": "Allow",
  "Action": "*",
  "Resource": "*"
}

Better:

{
  "Effect": "Allow",
  "Action": [
    "s3:GetObject",
    "s3:ListBucket"
  ],
  "Resource": [
    "arn:aws:s3:::company-reports",
    "arn:aws:s3:::company-reports/*"
  ]
}

4.31 Why S3 Often Needs Two ARNs

Consider:

s3:ListBucket

This applies to the bucket:

arn:aws:s3:::company-reports

Whereas:

s3:GetObject

applies to objects:

arn:aws:s3:::company-reports/*

Therefore policies frequently contain both.

4.32 Example S3 Read Policy

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ListBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::company-reports"
    },
    {
      "Sid": "ReadObjects",
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::company-reports/*"
    }
  ]
}

4.33 Sid

Sid means:

Statement ID

Example:

"Sid": "ReadObjects"

It can make policies easier to understand and troubleshoot.

It does not itself grant permission.

4.34 Default Deny

AWS authorization begins conceptually with:

DENY

If no applicable permission allows the request:

Request denied

This is often called:

Implicit Deny

4.35 Implicit Deny

Suppose a user has no permission for:

ec2:TerminateInstances

The result is:

Denied

because no matching allow exists.

Concept:

No Allow
   |
   v
Implicit Deny

4.36 Explicit Deny

A policy can explicitly deny an action.

Example:

{
  "Effect": "Deny",
  "Action": "s3:DeleteObject",
  "Resource": "arn:aws:s3:::company-data/*"
}

An applicable explicit deny generally overrides an allow.

Mental rule:

Explicit Deny
     |
     v
   WINS

within the relevant AWS authorization evaluation.

4.37 Allow + Deny Example

Policy A:

{
  "Effect": "Allow",
  "Action": "s3:*",
  "Resource": "*"
}

Policy B:

{
  "Effect": "Deny",
  "Action": "s3:DeleteObject",
  "Resource": "*"
}

For:

s3:GetObject

the allow may apply.

For:

s3:DeleteObject

the explicit deny applies.

4.38 IAM Policy Evaluation — Simplified

A useful beginner model:

Request
   |
   v
Is there an applicable explicit deny?
   |
   +--> YES --> DENY
   |
   v
Is there an applicable allow?
   |
   +--> YES --> ALLOW
   |
   v
DENY

Real AWS policy evaluation is more detailed because several policy types can intersect.

4.39 Permissions Boundary

A permissions boundary sets the maximum permissions that an IAM user or role can receive through identity-based policies.

Think of it as a ceiling.

Identity Policy
      |
      v
Possible Permissions

      AND

Permissions Boundary
      |
      v

Effective Identity Permissions

A boundary does not grant permissions by itself.

4.40 Permissions Boundary Example

Identity policy allows:

EC2
S3
RDS
IAM

Boundary permits only:

EC2
S3

Then identity-based permissions are limited by the boundary.

Conceptually:

Identity Policy:

EC2 + S3 + RDS + IAM

Boundary:

EC2 + S3

Result:

EC2 + S3

subject to other applicable controls and denies.

4.41 Why Permissions Boundaries Are Useful

Suppose developers are allowed to create IAM roles.

Without guardrails, they might create roles with excessive permissions.

A permissions boundary can constrain delegated IAM administration.

Example:

Platform Team
     |
     v
Defines Boundary
     |
     v
Developer-Created Roles
     |
     v
Cannot exceed approved permission ceiling

4.42 Service Control Policy

SCP means:

Service Control Policy

SCPs are used with AWS Organizations.

They define permission guardrails for affected accounts or organizational units.

Important:

An SCP does not grant permission.

4.43 SCP Example

Suppose IAM policy allows:

EC2
S3
RDS

SCP allows the account to use only:

EC2
S3

Conceptually:

IAM Permission
     INTERSECTION
SCP Guardrail
     =
Available Permission

Other policy types and explicit denies can further restrict access.

4.44 IAM + Boundary + SCP

A simplified mental model:

Identity-Based Permissions
          |
          v
Permissions Boundary
          |
          v
SCP
          |
          v
Other Applicable Controls
          |
          v
Effective Access

Do not treat any one policy as the entire authorization decision.

4.45 IAM Role Components

An IAM role commonly has two important policy concepts:

IAM Role
   |
   +--> Trust Policy
   |
   +--> Permissions Policies

Trust policy:

Who can assume this role?

Permissions policy:

What can the role session do after assumption?

This distinction is critical.

4.46 Trust Policy

Example:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "ec2.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}

This trusts the EC2 service principal to assume the role in the relevant service-role workflow.

4.47 Permissions Policy for the Role

Example:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::application-data/*"
    }
  ]
}

Now separate the two ideas:

Trust Policy
=
EC2 can assume role

Permissions Policy
=
Role can read application-data objects

4.48 AWS STS

STS means:

AWS Security Token Service

STS provides temporary security credentials.

Temporary credentials typically contain:

Access Key ID
Secret Access Key
Session Token
Expiration

4.49 Why Temporary Credentials Matter

Long-lived credentials:

Created
  |
  v
Remain valid until rotated/disabled

Temporary credentials:

Issued
  |
  v
Used
  |
  v
Expire

Temporary credentials reduce the lifetime of exposed credentials.

They do not eliminate the need for secure handling.

4.50 AssumeRole

One of the most important STS operations is:

AssumeRole

Workflow:

Principal
   |
   | sts:AssumeRole
   v
IAM Role
   |
   v
STS
   |
   v
Temporary Role Session
   |
   v
AWS API

4.51 AssumeRole Requirements

A successful role assumption generally requires the appropriate trust and authorization relationship.

Conceptually:

Caller
  |
  | permission to request AssumeRole where required
  v
Role
  |
  | trust policy accepts caller/context
  v
STS
  |
  v
Temporary Session

Cross-account and same-account details can differ depending on policy configuration.

4.52 AWS CLI AssumeRole Example

Example:

aws sts assume-role \
  --role-arn arn:aws:iam::123456789012:role/DeploymentRole \
  --role-session-name deployment-session

The response includes temporary credentials.

Never publish real credential values.

4.53 Role Session

When a role is assumed, AWS creates a role session.

Concept:

IAM Role
   |
   v
Assumed Role Session
   |
   v
Temporary Credentials

CloudTrail may show an assumed-role principal rather than the base IAM role ARN alone.

This is important during investigations.

4.57 Credential Provider Chain

Production rule:

Understand where your application is actually obtaining credentials.

4.60 Terraform Authentication

Terraform AWS Provider needs AWS credentials.

Avoid:

provider "aws" {
  access_key = "REAL_KEY"
  secret_key = "REAL_SECRET"
}

Never commit static credentials to Terraform configuration.

4.61 Better Terraform Authentication

Possible approaches include:

AWS CLI/SDK credential chain
IAM Role
AssumeRole
Environment-based temporary credentials
Federation
Workload identity

Example provider:

provider "aws" {
  region = "ap-south-1"
}

Credentials can be obtained through the supported credential chain.

provider "aws" {

4.64 Cross-Account Trust

The production role in Account B needs an appropriate trust policy.

Example concept:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:role/JenkinsRole"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}

The calling identity must also have the necessary authorization to assume the role.

4.65 Cross-Account Flow

Jenkins
   |
   v
Account A JenkinsRole
   |
   | sts:AssumeRole
   v
Account B DeploymentRole
   |
   v
Temporary Credentials
   |
   v
Production Deployment

Benefits include:

No permanent production keys in Jenkins
Short-lived sessions
Clear role separation

4.121 Interview Questions — Beginner

Q1. What is IAM?

IAM is AWS Identity and Access Management. It controls identities and authorization to AWS resources and APIs.

Q2. What is an IAM user?

An IAM user is an identity defined within an AWS account.

Q3. What is an IAM role?

An IAM role is an assumable AWS identity that provides temporary role sessions with permissions.

Q4. What is an IAM policy?

An IAM policy is a JSON policy document defining permissions or access-control rules.

Q5. What is least privilege?

Grant only the permissions required for the intended task.

4.122 Interview Questions — Intermediate

Q6. IAM user vs IAM role?

IAM users can represent long-lived account identities.

IAM roles are assumed and normally provide temporary credentials.

Roles are preferred for many workload, federation and cross-account use cases.

Q7. Identity policy vs resource policy?

Identity policy:

Attached to identity

Resource policy:

Attached to supported resource

Resource policies commonly contain a Principal.

Q8. What is STS?

AWS Security Token Service issues temporary security credentials and supports operations such as AssumeRole.

Q9. What is a trust policy?

A trust policy defines which principals or services can assume an IAM role under specified conditions.

Q10. What is iam:PassRole?

It controls whether a principal can pass an IAM role to an AWS service.

4.123 Interview Questions — Advanced

Q11. IAM policy allows an action but it is still denied. Why?

Possible reasons:

Explicit deny
SCP
Permissions boundary
Session policy
Resource policy
Trust policy
Condition mismatch
KMS key policy
Wrong principal
Wrong resource ARN

Q12. Does a permissions boundary grant permission?

No.

It defines a maximum permission boundary for identity-based permissions.

Q13. Does an SCP grant permission?

No.

An SCP is an organization-level permission guardrail.

Q14. Why are roles safer than static access keys for workloads?

Roles provide temporary credentials and avoid distributing permanent credentials to workloads.
