Trust boundaries: Internet traffic terminates at ALB; application nodes are not publicly reachable; RDS accepts only approved source security groups; secrets are retrieved through IAM-authorized API calls; TLS protects transport; KMS protects supported encrypted data at rest. TLS and KMS are not interchangeable.

Chapter 16 — VPC fundamentals and packet paths

16.1 Mental model: what actually happens when code connects

A PostgreSQL client resolves a DNS hostname to an IP address, selects a route from the source subnet, sends TCP SYN to port 5432, traverses security controls, negotiates TCP and PostgreSQL/TLS, authenticates, then issues SQL. A timeout usually means a path/filter problem; an immediate refusal means a listener/path issue; password authentication failed means the TCP path already worked.

VPC is an isolated logical IP network in an AWS Region. A subnet is a CIDR range in one Availability Zone. A route table chooses the next hop for destination prefixes. IGW is a gateway for public internet routing when instances also have appropriate public addressing. NAT gateway allows outbound connections from private IPv4 resources; it is not required for app→RDS traffic within the VPC. Security groups are stateful allow rules attached to ENIs; NACLs are stateless subnet-level allow/deny rules. A DB subnet group identifies subnets from which RDS can place database network interfaces; it is not itself a firewall.

16.2 Packet path and routing decisions

sequenceDiagram
    participant App as App ENI 10.40.11.25
    participant DNS as VPC Resolver
    participant RDS as RDS ENI 10.40.21.80
    App->>DNS: Resolve mydb.abcdef.us-east-1.rds.amazonaws.com
    DNS-->>App: 10.40.21.80 (example)
    App->>RDS: TCP SYN :5432 (local VPC route)
    RDS-->>App: SYN ACK (SG stateful return)
    App->>RDS: TLS negotiation and startup packet
    RDS-->>App: Authentication challenge/result

Key nuance: RDS endpoint IPs may change during maintenance/failover. Connect using the DNS endpoint, never hard-code a current IP. For a private address inside the same VPC, the local route is used, not the NAT gateway or internet gateway.

16.3 Design choices and tradeoffs

Design Advantages Costs/risks Use when
Private DB + private app Small attack surface Requires private administration path Production default
Private DB + public ALB Public API without public DB Must harden ALB/app Typical web services
Public DB (lab only) Easy connectivity Broad exposure, poor production posture Prefer avoiding entirely
Peering / Transit Gateway Private cross-VPC paths Routing and CIDR complexity Multi-account platforms
VPN / Direct Connect On-prem access Operational and network dependencies Enterprise hybrid

16.4 Lab: inspect an existing VPC (workstation)

aws sts get-caller-identity
aws ec2 describe-vpcs --query 'Vpcs[].{ID:VpcId,CIDR:CidrBlock}' --output table
aws ec2 describe-subnets --filters Name=vpc-id,Values=<VPC_ID> \
  --query 'Subnets[].{ID:SubnetId,AZ:AvailabilityZone,CIDR:CidrBlock}' --output table
aws ec2 describe-route-tables --filters Name=vpc-id,Values=<VPC_ID> \
  --query 'RouteTables[].{ID:RouteTableId,Routes:Routes}' --output json

Line by line: sts get-caller-identity validates the active principal; describe-vpcs finds address space; describe-subnets confirms AZ and CIDR; describe-route-tables reveals local/IGW/NAT/peering/TGW destinations. --filters narrows API results; --query formats JMESPath output; --output selects representation.

Example output: 10.40.0.0/16 VPC, private subnets 10.40.11.0/24 in AZ A and 10.40.21.0/24 in AZ B, each with local route 10.40.0.0/16 → local.

16.5 Senior interview

Q: Does a private subnet mean no internet connectivity? A: No. A private subnet generally lacks a direct route to an internet gateway for instances with public addresses; it may still have outbound access through NAT, IPv6 egress-only internet gateway, or private service endpoints. Define the exact path.

Q: Why does RDS failover break IP-based allowlisting? A: Endpoint DNS may resolve to a new IP after failover. Prefer stable DNS names and SG-to-SG references within supported network arrangements.

Chapter 17 — Private RDS access and network security

17.1 Security groups vs NACLs

Security groups allow traffic and track established connection state. NACLs evaluate ingress and egress separately, support explicit deny, and must account for ephemeral response ports. For ordinary same-VPC app-to-RDS traffic, SG references are clearer and safer than allowing an entire VPC CIDR. SGs do not support arbitrary DNS names as sources.

17.2 Network isolation blueprint

flowchart LR
  Internet -->|443| ALBSG[ALB SG]
  ALBSG -->|8080| AppSG[Application SG]
  AppSG -->|5432| DBSG[Database SG]
  Operator[Operator workstation] -->|SSM authenticated session| EC2[Private admin EC2]
  EC2 -->|5432| DBSG
  DBSG --> RDS[(RDS)]

Restrict DBSG inbound 5432 to AppSG (and an explicitly controlled administration SG when needed). Outbound SG rules on application nodes must permit the connection. Keep PubliclyAccessible=false. Place the DB in a subnet group spanning at least two AZs for normal RDS designs.

17.3 Lab: create DB SG and rule (workstation)

export AWS_REGION=us-east-1
export VPC_ID=vpc-REPLACE
export APP_SG=sg-REPLACE
DB_SG=$(aws ec2 create-security-group --region "$AWS_REGION" \
  --group-name rds-vol3-db --description 'RDS access from application only' \
  --vpc-id "$VPC_ID" --query GroupId --output text)
aws ec2 authorize-security-group-ingress --region "$AWS_REGION" \
  --group-id "$DB_SG" --protocol tcp --port 5432 --source-group "$APP_SG"
aws ec2 describe-security-groups --group-ids "$DB_SG" --region "$AWS_REGION"

Explain: create-security-group creates a VPC-scoped filter; --query GroupId --output text captures its ID; authorize-security-group-ingress adds exactly TCP/5432 sourced from application SG; the final command checks effective rules. A source SG reference identifies traffic from ENIs with that SG, not a human user's identity. If this SG is already attached to a DB, do not delete it during cleanup.

17.4 Lab: prove RDS private posture

aws rds describe-db-instances --db-instance-identifier <DB_ID> \
 --query 'DBInstances[0].{Endpoint:Endpoint.Address,Public:PubliclyAccessible,SG:VpcSecurityGroups,SubnetGroup:DBSubnetGroup.DBSubnetGroupName}'
# Run on an approved EC2 node inside VPC:
getent hosts <RDS_ENDPOINT>
nc -vz -w 5 <RDS_ENDPOINT> 5432

Example output: Public: false; Connection to ... 5432 port [tcp/postgresql] succeeded! only from authorized source. nc success proves TCP reachability, not TLS correctness or authentication.

17.5 Safe private administration: SSM port forwarding

On a workstation with Session Manager plugin and permissions, tunnel through an SSM-managed EC2 instance in the VPC:

aws ssm start-session --target i-REPLACE \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters '{"host":["<RDS_ENDPOINT>"],"portNumber":["5432"],"localPortNumber":["15432"]}'

In a second terminal, use psql to 127.0.0.1:15432. TLS hostname validation nuance: sslmode=verify-full compares the certificate name with the host supplied by the client. With an ordinary localhost tunnel, set host=<RDS_ENDPOINT> hostaddr=127.0.0.1 port=15432 in libpq so TCP uses localhost but the server hostname remains the verified RDS DNS name. Confirm the RDS CA bundle is present and sslrootcert points to it. The SSM target needs permission to reach the DB and SSM network connectivity; IAM permissions for Session Manager are separate from DB authentication.

17.6 Troubleshooting decision tree

flowchart TD
  A[Connection failed] --> B{DNS resolves?}
  B -- No --> C[Check endpoint, resolver, VPC DNS, split-horizon]
  B -- Yes --> D{TCP 5432 reachable?}
  D -- No --> E[Check SG both ends, NACL, routes, endpoint status]
  D -- Yes --> F{TLS verifies?}
  F -- No --> G[Check CA bundle, hostname, sslmode, clock]
  F -- Yes --> H{DB login succeeds?}
  H -- No --> I[Check role, secret, pg_hba managed behavior, IAM token]
  H -- Yes --> J[Check query permissions and app configuration]

Q: Can I ping RDS to test it? A: ICMP is not a reliable RDS reachability test; test TCP/5432 and a real TLS-authenticated DB session.

Q: Why can an EC2 instance reach RDS while a laptop cannot? A: The laptop may lack any routed private path into the VPC; SG permission alone cannot create routing.

Chapter 18 — TLS, IAM DB authentication, and credentials

18.1 Three different protections

  • TLS in transit: encryption, integrity, and server identity verification for a client↔DB connection.
  • KMS-backed encryption at rest: storage/snapshot/log protection under supported RDS encryption features; does not replace TLS or SQL permissions.
  • Database authentication/authorization: proves who may connect and which SQL operations they can perform. IAM authentication is a way to authenticate; it does not automatically grant SQL privileges.

18.2 TLS handshake mental model

sequenceDiagram
  participant Client
  participant RDS
  Client->>RDS: TCP connection and PostgreSQL SSLRequest
  RDS-->>Client: TLS supported
  Client->>RDS: ClientHello
  RDS-->>Client: Certificate chain + TLS handshake
  Client->>Client: Validate trust anchor and RDS hostname
  Client->>RDS: PostgreSQL startup/authentication over TLS

sslmode=require encrypts transport but does not guarantee hostname verification. Prefer sslmode=verify-full with a trusted current RDS CA bundle. Certificate verification requires the actual RDS endpoint name. Certificate rotations must be rehearsed before expiration.

18.3 Lab: TLS verification (authorized EC2 or SSM tunnel)

Download the current region/global RDS trust bundle from AWS's official RDS certificate page and verify its provenance; do not disable validation to make a broken connection work.

export PGHOST='<RDS_ENDPOINT>'
export PGPORT=5432
export PGDATABASE='appdb'
export PGUSER='app_user'
export PGSSLMODE='verify-full'
export PGSSLROOTCERT="$HOME/.postgresql/rds-ca-bundle.pem"
psql -c 'select current_user, current_database();'
psql -c 'select ssl, version, cipher from pg_stat_ssl where pid=pg_backend_pid();'

Line by line: PGHOST is the DNS identity to verify; PGPORT is TCP listener; PGDATABASE and PGUSER identify the logical database and role; PGSSLMODE=verify-full checks chain and hostname; PGSSLROOTCERT specifies CA file; first query proves SQL login; second proves TLS and negotiated cipher. Supply password securely (e.g. managed secret injected at runtime), not as a command-line argument.

Example output: ssl | version | cipher → t | TLSv1.3 | TLS_AES_256_GCM_SHA384 (negotiation varies).

18.4 IAM database authentication

For supported RDS engines/configurations, IAM DB authentication replaces a static DB password at connection time with a short-lived authentication token. The token validity window is 15 minutes for establishing the connection, not a hard lifetime for an already established DB session. Tokens are generated client-side; a token is not a general AWS credential and should never be logged. Verify engine and proxy compatibility before enabling. IAM authentication has scaling and memory tradeoffs; evaluate RDS Proxy for connection-heavy workloads.

Two permissions must align: IAM principal needs rds-db:connect on the DB resource ID ARN (not ordinary rds DB instance ARN); PostgreSQL DB role must exist and be granted rds_iam appropriately. In PostgreSQL, granting rds_iam changes authentication behavior; test password fallback expectations before rollout.

18.5 Lab: PostgreSQL IAM auth (workstation and authorized DB session)

1. Enable feature (workstation; maintenance/change approval required):

aws rds modify-db-instance --db-instance-identifier <DB_ID> \
  --enable-iam-database-authentication --apply-immediately
aws rds wait db-instance-available --db-instance-identifier <DB_ID>
aws rds describe-db-instances --db-instance-identifier <DB_ID> \
  --query 'DBInstances[0].IAMDatabaseAuthenticationEnabled'

--apply-immediately may cause operational effects depending on pending modifications; use a change window and inspect pending changes. wait confirms an instance state, not that the application works.

2. DB admin psql session:

CREATE ROLE app_iam LOGIN;
GRANT rds_iam TO app_iam;
GRANT CONNECT ON DATABASE appdb TO app_iam;
-- Inside appdb, grant only required schema/table privileges:
GRANT USAGE ON SCHEMA public TO app_iam;
GRANT SELECT ON TABLE public.orders TO app_iam;

Do not grant rds_iam to an existing password-authenticated production role without testing authentication precedence and a rollback.

3. IAM permission template:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "rds-db:connect",
    "Resource": "arn:aws:rds-db:us-east-1:123456789012:dbuser:db-RESOURCEID/app_iam"
  }]
}

db-RESOURCEID is the RDS database resource ID returned in DB metadata; replace account, region, and role. For proxy-based IAM authentication, the relevant resource identity and policy requirements differ; use the proxy resource ID as documented for that mode.

4. Generate token and connect from approved private path:

export RDSHOST='<RDS_ENDPOINT>'
export DBTOKEN="$(aws rds generate-db-auth-token --hostname "$RDSHOST" --port 5432 --region us-east-1 --username app_iam)"
PGPASSWORD="$DBTOKEN" psql "host=$RDSHOST port=5432 dbname=appdb user=app_iam sslmode=verify-full sslrootcert=$HOME/.postgresql/rds-ca-bundle.pem" \
  -c 'select current_user;'
unset DBTOKEN

generate-db-auth-token signs an auth request with the current AWS identity; PGPASSWORD is supplied only to the child command environment rather than pasted into the shell command; unset removes the shell variable (not a guarantee of forensic erasure). Prefer workload roles and short-lived credentials. Ensure application connection pools regenerate tokens for new physical connections rather than reusing expired tokens.

18.6 Senior interview

Q: Can IAM database authentication replace authorization? No. IAM decides whether the caller may authenticate as a role; PostgreSQL grants still control SQL privileges.

Q: Why does an IAM token work for 15 minutes but a query run for an hour? The token is validated at connection establishment. The established session can continue subject to normal server/session constraints.

Chapter 19 — Secrets Manager, KMS, and rotation

Secrets Manager securely stores database credentials; KMS protects encryption keys. Use least privilege, managed master password where appropriate, rotation with validation, and cache refresh.

aws secretsmanager describe-secret --secret-id <SECRET_ARN>
aws kms describe-key --key-id <KMS_KEY_ARN>

Interview: Does at-rest encryption prevent SQL access from stolen credentials? No. SQL authorization is separate.

Chapter 20 — RDS Proxy and connection management

RDS Proxy pools database connections. It helps connection churn but cannot optimize SQL. Session pinning and long transactions reduce multiplexing.

flowchart LR
 A[App] --> P[RDS Proxy] --> D[(RDS)]

aws rds describe-db-proxies
aws rds describe-db-proxy-targets --db-proxy-name <PROXY_NAME>

Troubleshooting: Check target health, borrow latency, DB CPU, long transactions, and pinning. Interview: Proxy is not a query cache.

Chapter 21 — Auditing, hardening, and incident response

CloudTrail covers supported AWS API events; DB logs cover configured SQL/authentication events; VPC Flow Logs provide network metadata, not SQL text.

aws rds describe-db-log-files --db-instance-identifier <DB_ID>
aws logs describe-log-groups --log-group-name-prefix /aws/rds/instance/

Use least-privilege SQL roles, redacted logs, incident evidence preservation, credential rotation, containment and postmortems.

CREATE ROLE reader NOLOGIN;
GRANT CONNECT ON DATABASE appdb TO reader;
GRANT USAGE ON SCHEMA public TO reader;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO reader;

Terraform private RDS lab

This minimal template is an educational starting point. Supply VPC, subnet IDs in two AZs, a restricted app security group, and supported engine class. Never commit state or secrets.

resource "aws_db_subnet_group" "private" {
 name = "rds-v3-private"
 subnet_ids = var.private_db_subnet_ids
}
resource "aws_security_group" "db" {
 vpc_id = var.vpc_id
 ingress {
  from_port = 5432
  to_port = 5432
  protocol = "tcp"
  security_groups = [var.app_security_group_id]
 }
}
resource "aws_db_instance" "db" {
 identifier = "rds-v3-lab"
 engine = "postgres"
 instance_class = var.db_class
 allocated_storage = 20
 db_subnet_group_name = aws_db_subnet_group.private.name
 vpc_security_group_ids = [aws_security_group.db.id]
 publicly_accessible = false
 storage_encrypted = true
 username = "dbadmin"
 manage_master_user_password = true
 backup_retention_period = 7
 deletion_protection = true
 skip_final_snapshot = false
 final_snapshot_identifier = "rds-v3-final-unique"
}

Line by line: subnet group selects private AZ subnets; security group limits TCP 5432 to app SG; RDS resource configures PostgreSQL, encrypted storage, managed master secret, backups and deletion protection. Check regional engine class and storage compatibility, define var inputs, and configure a secure Terraform backend. No application host, proxy, or access path is created here.

terraform fmt
terraform init
terraform validate
terraform plan -out=tfplan
terraform show tfplan
terraform apply tfplan

Representative result: a private RDS DNS endpoint after provisioning. These commands were not executed. Review charges before apply. To destroy a lab, disable deletion protection via approved apply; final snapshots continue billing.

Production troubleshooting runbooks

  1. Timeout: DNS, route, SG, NACL, RDS status; nc -vz -w 5 <RDS_ENDPOINT> 5432 from permitted host.
  2. TLS error: CA bundle, exact endpoint, verify-full, client library and certificate rotation.
  3. IAM error: rds-db:connect resource ID, rds_iam, token age, AWS identity, TLS.
  4. Rotation outage: secret staging, DB password state, app cache and connection pool refresh.
  5. Proxy borrow timeout: target health, pinned sessions, long transactions, backend capacity.
  6. Suspicious login: preserve CloudTrail and DB logs, revoke credentials, contain, validate and document.
