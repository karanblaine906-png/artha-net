CPU: Instructions execute karta hai, registers maintain karta hai, privilege state check karta hai, aur exceptions raise kar sakta hai. RAM: Executable instructions aur runtime data store karti hai; physical RAM locations virtual addresses se different hote hain. Device controller: Disk/NIC/USB hardware ko manage karta hai; driver registers aur DMA descriptors ke through controller ko command de sakta hai. Kernel: Hardware resource sharing aur protection enforce karta hai.

2.1 Fetch–decode–execute: step by step

  1. CPU instruction pointer (x86-64 RIP) ke indicated location se instructions fetch karta hai (caches and translation may participate).
  2. Instruction decode hota hai; operands registers, immediate values, ya memory se aa sakte hain.
  3. Execution units operation perform karte hain; memory access mein virtual-to-physical translation involved hoti hai.
  4. Architectural state update hota hai. Exceptions, interrupts, speculation and out-of-order execution actual hardware timeline ko complex banate hain.

Important distinction: CPU utilization aur memory usage ek hi cheez nahi. Busy CPU compute kar sakta hai bina zyada resident RAM consume kiye; process large resident RAM hold kar sakta hai while mostly sleeping.

2.2 Registers: conceptual table

Register/group Typical purpose Caution
RIP Instruction pointer Kernel/user transitions save/restore state
RSP Stack pointer Kernel and user stacks are distinct
RAX Return values; syscall number on x86-64 Linux Calling convention dependent
RDI, RSI, RDX, R10, R8, R9 First six x86-64 Linux syscall arguments Not same as ordinary C function ABI
RFLAGS Flags and control bits Some privileged operations restricted
CR3 Page-table root context (simplified) Privileged; PCID and KPTI complicate details

Kernel code architecture-specific hai. ARM64 par exception levels and registers alag honge; don't generalize x86 ring terminology to every CPU.

3. Privilege levels: user mode vs kernel mode

x86-64 Linux typically applications ko CPL 3 aur kernel ko CPL 0 par run karta hai. Iska purpose isolation hai: user process directly privileged CPU instructions execute nahi kar sakta, kernel memory freely access nahi kar sakta, aur arbitrary device control nahi kar sakta.

Common misconception: "Shell → system calls → kernel" ek universal path nahi. Shell bhi user-space process hai. cat ya Python program directly library wrappers ke through syscall kar sakta hai. Some libc calls never invoke syscalls; some program operations invoke multiple syscalls.

shell launches app -> app invokes libc wrapper -> syscall instruction
    -> CPU enters privileged kernel entry path
    -> argument validation / permission checks / subsystem
    -> return value or -errno -> user-space resumes

Kernel-to-user direction bhi exist karti hai: return from syscall, signal delivery, copying results into user buffers, waking blocked tasks. Kernel user pointers ko blindly dereference nahi karta; access helpers such as copy_from_user() and copy_to_user() exist for safe handling (subject to API rules).

3.1 System call vs normal function

printf() normally libc user-space function hai; write() libc wrapper generally write syscall tak pahunchta hai. Buffered printf() call immediately syscall trigger kare, zaroori nahi; flush par ho sakta hai. getpid() wrapper often syscall invokes (implementation dependent). strace observes system calls, not every ordinary C function.

4. MMU, virtual memory, page tables and TLB

Virtual address process ke address space ka address hota hai; physical address RAM/device physical address space ka. CPU memory access par MMU translation/protection check karta hai. Page table entries mapping aur flags represent karti hain: present, writable, user accessible, execute permissions (architecture-dependent).

User virtual address
        |
      CPU/MMU ----> TLB lookup (cached translation)
        |                 |
        | miss            | hit
        v                 v
   page-table walk ----> physical page + offset
        |
   not present / permission violation
        v
   page-fault exception -> kernel handler -> resolve or signal

TLB miss ≠ page fault. TLB miss par hardware page-table walk kar sakta hai. Page fault tab ho sakta hai jab mapping absent ho, permissions mismatch karein, ya OS intervention required ho. Linux demand paging ke through fault ko resolve kar sakta hai; invalid access par SIGSEGV (or other outcome) possible hai.

4.1 Paging fundamentals

Typical base page size x86-64 par 4 KiB hota hai, but huge pages bhi available hain. 4 KiB page mein address offset 12 bits hota hai. Modern Linux supports architecture-dependent multi-level page-table abstractions (PGD, P4D, PUD, PMD, PTE); some levels folded ho sakte hain. mm_struct process address-space metadata hold karta hai; VMA mappings permissions and backing describe karti hain. Detailed page-fault implementation Volume IV mein revisit hoga.

4.2 RSS vs VSZ

  • VSZ/VIRT: Mapped virtual address space; necessarily RAM occupied nahi.
  • RSS/RES: Currently resident physical memory attributed to process, including shared resident mappings; it is not exclusive private RAM.
  • Page cache: Filesystem I/O cache, generally reclaimable under pressure, but not equivalent to immediately free memory.
  • Swap: Selected memory pages disk-backed swap space mein move ho sakte hain; swap usage alone does not prove a problem.

Observe:

ps -eo pid,comm,vsz,rss,%mem --sort=-rss | head
free -h
cat /proc/meminfo | head -25
cat /proc/self/maps | head

5. Interrupts, exceptions and DMA

Exception: Current instruction execution se related synchronous event, e.g. page fault or invalid opcode. Interrupt: Often asynchronous device/event notification, though details architecture-dependent. System call: Controlled software-initiated entry, not identical to a hardware interrupt on modern x86-64.

NIC example: device DMA se packet data host memory buffers mein transfer kar sakta hai; interrupt moderation and NAPI polling processing ko batch karte hain. Driver and network stack packets ko process karte hain. DMA ka matlab CPU bilkul involved nahi, aisa nahi: CPU device ko configure karta hai, buffers prepare karta hai, synchronization/ownership handle karta hai.

NIC packet arrives -> DMA into prepared RX buffer
      -> IRQ/NAPI scheduling -> poll packet budget
      -> driver builds skb -> network stack -> socket queue
      -> sleeping application wakes -> recv() returns

Warning: Above is a common simplified RX path, not a universal path. XDP, GRO, hardware offloads, virtualization and driver differences behavior change kar sakte hain.

7. Implementation A — Observe real syscalls with C

Goal: Prove syscall boundary using a small C program and strace.

Install tools in VM:

sudo apt update
sudo apt install -y build-essential strace gdb linux-perf

syscall_demo.c:

#define _GNU_SOURCE
#include <unistd.h>
#include <sys/syscall.h>
#include <string.h>
#include <stdio.h>

int main(void) {
    const char *msg = "Hello from userspace via write syscall\n";
    long n = syscall(SYS_write, STDOUT_FILENO, msg, strlen(msg));
    if (n < 0) { perror("write"); return 1; }
    printf("Bytes written: %ld\n", n);
    return 0;
}

Build and run:

gcc -Wall -Wextra -O0 -g syscall_demo.c -o syscall_demo
./syscall_demo
strace -e trace=write ./syscall_demo

Line-by-line: _GNU_SOURCE exposes GNU interfaces; unistd.h declares POSIX-related functions; sys/syscall.h provides syscall identifiers; SYS_write selects write syscall; STDOUT_FILENO is fd 1; strlen() calculates payload length; syscall() invokes libc's generic syscall wrapper; negative return indicates wrapper-reported error and perror prints detail; printf() writes buffered text via libc.

Expected observation (illustrative): One write(1, "Hello...", 39)-like event and another write for printf output. Exact byte count and grouping depend on text and buffering; trust observed trace, not this illustrative number.

Debugging: strace -f -tt -T -e trace=write,openat ./syscall_demo adds child tracking, timestamps and durations. gdb ./syscall_demo, break main, run, disassemble main shows user-space assembly, not kernel internals. To inspect kernel-side entry use matching kernel source and kernel debugger/tracing.

8. Implementation B — Virtual memory, mappings and page faults

mmap_demo.c:

#define _GNU_SOURCE
#include <sys/mman.h>
#include <sys/resource.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <string.h>

int main(void) {
    const size_t n = 64UL * 1024 * 1024;
    struct rusage before, after;
    getrusage(RUSAGE_SELF, &before);
    char *p = mmap(NULL, n, PROT_READ | PROT_WRITE,
                   MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }
    printf("PID=%ld mapping=%p size=%zu\n", (long)getpid(), (void *)p, n);
    for (size_t i = 0; i < n; i += (size_t)sysconf(_SC_PAGESIZE)) p[i] = 1;
    getrusage(RUSAGE_SELF, &after);
    printf("minor faults delta=%ld, major faults delta=%ld\n",
           after.ru_minflt - before.ru_minflt,
           after.ru_majflt - before.ru_majflt);
    if (munmap(p, n) != 0) { perror("munmap"); return 1; }
    return 0;
}

Mechanism: mmap anonymous virtual mapping reserve karta hai; initial mapping necessarily 64 MiB resident nahi hoti. Loop har page mein write karta hai, typically demand-zero pages allocate/map hoti hain and minor faults increase. Not a guarantee: transparent huge pages, kernel optimizations and prior accounting influence counts. Major faults need not increase. munmap virtual mapping release karta hai. getrusage process resource counters report karta hai.

12. Production-style scenarios and worked reasoning

Scenario A — High memory use, but no immediate memory shortage

Symptom: free -h shows low free, high buff/cache, application works normally. Hypothesis: Page cache occupies RAM. Evidence: MemAvailable, Cached, SReclaimable, process RSS, memory PSI. Do not conclude: All cache is immediately reclaimable or RAM exhaustion exists. Action: Check actual memory pressure, reclaim stalls and OOM events before tuning.

Scenario B — Application gets SIGSEGV

Symptom: Crash at a pointer dereference. Investigation: coredumpctl where available; gdb backtrace, info registers, x/i $rip, address mapping, source with debug symbols. Possible causes: Null/invalid pointer, use-after-free, out-of-bounds, stack corruption. Caution: Not every segfault is a kernel bug; kernel normally enforces process isolation.

Scenario C — Kernel module fails to load

Symptom: insmod: ERROR: could not insert module. Evidence: dmesg, modinfo -F vermagic, uname -r, module signing status. Hypotheses: Version mismatch, missing symbol, signature policy, lockdown. Fix: Rebuild against correct headers, sign module through approved procedure where required. Regression: Reload on snapshot VM, confirm logs and clean unload.

Scenario D — System CPU high but process CPU modest

Symptom: Host busy; no single userspace process dominates. Investigate: top CPU states (sy, si, hi), vmstat 1, /proc/softirqs, perf top if permitted, NIC packet rates. Possible causes: Network softirq load, interrupt storm, filesystem work, kernel background threads. No shortcut: High system CPU is not itself proof of driver bug.

Scenario E — Page allocation failure with available memory

Symptom: page allocation failure kernel log despite nonzero MemAvailable. Investigate: allocation order/GFP flags, /proc/buddyinfo, zones, fragmentation, cgroup context, NUMA policy. Reason: High-order physically contiguous pages may be unavailable even with substantial free memory. Mitigation: Depends on call site; simply adding swap may not help.

13. Interview Q&A — fundamentals to senior level

Q1. Kernel vs OS? Kernel privileged core hai jo scheduling, memory, I/O and protection implement karta hai; operating system broadly kernel plus userspace services, libraries and tools include kar sakta hai.

Q2. System call kya hai? Controlled transition to privileged kernel service with defined ABI, argument validation, permission checks and return semantics. Ordinary library calls do not necessarily enter kernel.

Q3. TLB miss and page fault difference? TLB miss cached translation absent; page-table walk may succeed. Page fault occurs on translation/protection condition needing fault handling.

Q4. RSS vs VSZ? RSS resident mapped physical pages count karta hai; VSZ mapped virtual space. RSS includes shared mappings and is not private-only footprint.

Q5. Why can mmap() succeed but later memory access fail? Virtual mapping creation and physical allocation can be decoupled; later page faults may encounter limits, allocation failures or permissions.

Q6. strace vs ftrace? strace syscall boundary observe karta hai; ftrace kernel internal functions/events trace kar sakta hai with appropriate config and permissions.

Q7. What happens when write() is called? libc wrapper syscall invoke karta hai; kernel fd and arguments validate karta hai, file/socket-specific operations execute karta hai, result/error return hota hai. Exact path fd type and kernel version par depend karta hai.

Q8. Why is a module risky? Kernel code privileged address space mein execute hota hai; invalid memory access, races, bad locks or incorrect hardware programming entire system affect kar sakte hain.

Q9. Is a page fault always an error? No. Demand paging, copy-on-write and stack growth can produce legitimate resolvable page faults; invalid faults may cause signals or kernel oops.

Q10. Why not always add swap when RAM usage high? Swap does not resolve all constraints: pinned memory, kernel contiguous allocation, cgroup policy, latency-sensitive workloads and unreclaimable pages may be limiting factors.

Chapter 02 — Operating System Internals: Processes, Threads, Scheduling, Paging

Objective: Sirf ps chalana nahi: CPU par instructions execute kaise hote hain, kernel process state kaise maintain karta hai, scheduler kis basis par task select karta hai, aur page fault par CPU/kernel kya karte hain — sab samajhna.

2.1 Operating system kya solve karta hai?

CPU, RAM, disks aur NIC physical resources hain. Agar har application ko hardware directly control karne diya jaye, toh ek program dusre ka memory overwrite kar sakta hai; ek driver hardware ko indefinitely hold kar sakta hai; concurrent file writes corrupt ho sakte hain. OS controlled abstraction provide karta hai: process (execution and protection domain), virtual memory (private address space), files (persistent byte streams and metadata), sockets (network endpoints), scheduler (CPU time allocation), permissions (access control). Kernel trusted code hai jo privileged CPU mode mein hardware aur shared state manage karta hai. User applications usually unprivileged mode mein execute karti hain.

Kernel har instruction execute nahi karta. User program ke normal arithmetic instructions CPU par directly execute hote hain. Kernel transition tab hoti hai jab syscall, exception ya interrupt aata hai, ya task preemption/rescheduling required hota hai.

Userspace task A      Userspace task B
  | read(fd)             | compute
  v                      |
libc syscall wrapper     |
  | syscall instruction  |
  v                      |
Kernel entry -> VFS -> driver -> completion
  |                  ^
  +-- sleep/wakeup --+---- scheduler chooses runnable task
  |
return to user mode

Interview trap: 'Shell -> syscall -> kernel' universal flow nahi hai. Shell ek userspace program hai; app direct libc/syscall invoke kar sakti hai. printf userspace buffering use karta hai; actual write syscall later ho sakta hai.

2.2 Program, process aur thread — difference

Program disk par executable bytes aur metadata hota hai. Process running program ka execution context aur resource container hai. Thread independently schedulable execution flow hai, jiska register state, stack aur scheduling state hota hai. Same process ke threads typically mm_struct (address space), file descriptor table aur signal handlers share karte hain, lekin implementation clone() flags ke according sharing vary karti hai. Linux scheduler threads/tasks schedule karta hai, 'whole process' ko atomic CPU unit ke roop mein nahi.

Linux data structures

  • task_struct: scheduler-visible task metadata, task state, identifiers, scheduling fields, references to memory/files/credentials. include/linux/sched.h.
  • mm_struct: userspace virtual address space ka description. include/linux/mm_types.h.
  • files_struct: file descriptor table and related synchronization. include/linux/fdtable.h.
  • signal_struct / sighand_struct: shared signal state and dispositions.

Exact fields release-dependent hain; field offsets ko stable ABI mat samjho.

Process lifecycle

fork()/clone() -> task created -> runnable -> running
                                    |          |
                                    |          +-> blocking syscall -> sleeping
                                    |                     |
                                    +<---- wakeup --------+
                                               |
                                  exit -> zombie (until parent reaps)

TASK_RUNNING ka matlab running ya runnable ho sakta hai. D state usually uninterruptible sleep represent karta hai; har D process disk I/O ki wajah se blocked ho, zaroori nahi. Zombie process CPU execute nahi kar raha; parent ne exit status reap nahi kiya.

2.3 fork() aur execve() ke internals

fork() parent ke execution context se child create karta hai. Linux internal implementation commonly kernel_clone()/copy_process() paths use karti hai, release-specific differences ke saath. Parent-child initial memory contents same lagte hain, lekin modern kernels private writable pages ko copy-on-write se share kar sakte hain. 2.4 CPU scheduling — kernel task ko kab run karta hai?

Single CPU ek instant mein generally ek software thread execute karta hai; multiple cores parallel tasks execute kar sakte hain. Scheduler runnable tasks mein selection karta hai. Context switch mein current task ka execution state save aur next task ka state restore hota hai. Scheduler runqueue per-CPU state manage karti hai; task wakeups, affinity, priorities aur load balancing decisions ko affect karte hain.

Preemption: higher-priority runnable task ya scheduling conditions ke basis par currently executing task ko replace kiya ja sakta hai, subject to kernel preemption configuration and critical sections. nice normal fair scheduling mein relative weight influence karta hai; RT policies (SCHED_FIFO, SCHED_RR) ka behavior alag hai. Contemporary Linux fair scheduler EEVDF logic use karta hai; older tutorials ke pure CFS red-black-tree explanations ko historical context mein padho.

What happens during context switch?

  1. Scheduler invocation: current task yield/block/preempt hota hai.
  2. Runnable candidates aur scheduling class evaluate hoti hai.
  3. Current task ka CPU-specific context (registers, stack pointer etc.) preserve hota hai.
  4. Next task ka kernel stack and architecture state activate hota hai.
  5. Address-space switch aur TLB behavior architecture, PCID/ASID aur same-mm optimizations par depend karta hai.
  6. CPU new task resume karta hai.

Important: Context switch aur user↔kernel mode switch same cheez nahi. Syscall kernel mode enter kar sakta hai bina task switch kiye.

Practical C program: thread concurrency

Create threads.c:

#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>

static void *worker(void *arg) {
    long id = *(long *)arg;
    for (int i = 0; i < 3; ++i) {
        printf("worker=%ld iteration=%d\n", id, i);
        usleep(100000);
    }
    return NULL;
}

int main(void) {
    pthread_t t[2];
    long ids[2] = {1, 2};
    for (int i = 0; i < 2; ++i) {
        int rc = pthread_create(&t[i], NULL, worker, &ids[i]);
        if (rc) { fprintf(stderr, "pthread_create failed: %d\n", rc); return 1; }
    }
    for (int i = 0; i < 2; ++i) pthread_join(t[i], NULL);
    return 0;
}

2.8 Interview questions with substantive answers

Q: Syscall aur context switch mein kya difference hai?
A: Syscall privilege transition hai jo same thread mein kernel code run kara sakta hai. Context switch CPU ko ek schedulable task se dusre task par transfer karta hai. Blocking syscall context switch trigger kar sakta hai, lekin every syscall nahi.

Q: fork memory ko copy karta hai ya share?
A: Child ko logically independent address space milta hai, but implementation COW use karke private writable physical pages temporarily share kar sakti hai. Write par page fault ke through private backing establish hoti hai. Shared mappings ka semantics alag hai.

Q: TASK_RUNNING ka matlab kya hai?
A: Running ya runnable state; CPU currently execute kar raha ho zaroori nahi.

Q: TLB miss and page fault difference?
A: TLB miss cached translation absent hai; hardware page-table walk se resolve ho sakta hai. Page fault mapping/protection problem ka exception hai, jise kernel handle karta hai.

Q: Linux load average CPU usage kyu nahi?
A: Load runnable aur selected uninterruptible tasks ko account karta hai; CPU busy percentage CPU time accounting ka alag metric hai. I/O blocked workloads high load with idle CPU dikha sakte hain.

Deep Implementation Workshop A — Loadable Kernel Module

Safety: disposable QEMU guest mein run karo; kernel headers guest ke uname -r se match hone chahiye.

hello.c:

#include <linux/init.h>
#include <linux/module.h>
#include <linux/printk.h>

static int __init hello_init(void)
{
    pr_info("hello_kernel: module loaded\n");
    return 0;
}

static void __exit hello_exit(void)
{
    pr_info("hello_kernel: module unloaded\n");
}

module_init(hello_init);
module_exit(hello_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Minimal instructional Linux kernel module");

Makefile (recipe line starts with TAB):

obj-m += hello.o
KDIR ?= /lib/modules/$(shell uname -r)/build

all:
	$(MAKE) -C $(KDIR) M=$(CURDIR) modules

clean:
	$(MAKE) -C $(KDIR) M=$(CURDIR) clean

Commands (inside VM):

sudo apt install -y build-essential linux-headers-$(uname -r)
make
modinfo ./hello.ko
sudo insmod ./hello.ko
sudo dmesg | tail -20
sudo rmmod hello
sudo dmesg | tail -20
make clean

Line-by-line: linux/init.h init/exit annotations deta hai; module.h module metadata aur lifecycle macros; pr_info kernel ring buffer mein message emit karta hai; __init init section reclaimable banata hai; module_init entry registration hai; MODULE_LICENSE license string set karta hai (security guarantee nahi). obj-m external module ko select karta hai; -C kernel build directory; M= external module directory.

Deep Implementation Workshop B — Page Fault and Copy-on-Write

cow.c:

#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
#include <sys/mman.h>
#include <sys/wait.h>
#include <sys/resource.h>

int main(void) {
    size_t n = (size_t)sysconf(_SC_PAGESIZE);
    char *p = mmap(NULL, n, PROT_READ | PROT_WRITE,
                   MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }
    p[0] = 'A';
    pid_t pid = fork();
    if (pid < 0) { perror("fork"); munmap(p,n); return 1; }
    if (pid == 0) {
        p[0] = 'B'; /* private COW fault may occur */
        printf("child=%c\n", p[0]);
        munmap(p,n);
        _exit(0);
    }
    waitpid(pid, NULL, 0);
    printf("parent=%c\n", p[0]);
    munmap(p,n);
    return 0;
}

Build and run:

gcc -O0 -Wall -Wextra cow.c -o cow
./cow
/usr/bin/time -v ./cow

Expected: parent prints A; child may not show its buffered output because _exit skips stdio flush. Change child to fflush(stdout); _exit(0); to reliably see B. COW means fork initially shares physical backing and a write creates a private copy as required. Page-fault counts depend on runtime and compiler; don't assert a fixed count.

Deep Implementation Workshop C — LVM + RAID1 + ext4 (DISPOSABLE VM ONLY)

This is a destructive lab. Only run in a dedicated disposable VM. Verify every device before each command. The example uses two loopback files (not physical disks) and assumes mdadm, lvm2, e2fsprogs, util-linux installed. It requires root. The script includes checks, but mistakes can still cause data loss.

Architecture:

raid-a.img -> /dev/loopX --+
                            +-> /dev/md/labmirror (RAID1)
raid-b.img -> /dev/loopY --+             |
                                      PV (LVM)
                                        |
                                     VG labvg
                                        |
                                     LV labdata
                                        |
                                      ext4
                                        |
                                  /mnt/labdata

Run inside VM (root shell):

sudo -i
set -euo pipefail
mkdir -p /root/kernel-storage-lab
cd /root/kernel-storage-lab
truncate -s 512M raid-a.img
truncate -s 512M raid-b.img
LOOPA=$(losetup --find --show "$(pwd)/raid-a.img")
LOOPB=$(losetup --find --show "$(pwd)/raid-b.img")
printf 'Using %s and %s\n' "$LOOPA" "$LOOPB"
lsblk "$LOOPA" "$LOOPB"
# STOP here if either loop device is not backed by the lab image.
mdadm --create /dev/md/labmirror --metadata=1.2 --level=1 \
  --raid-devices=2 "$LOOPA" "$LOOPB"
cat /proc/mdstat
mdadm --detail /dev/md/labmirror
pvcreate /dev/md/labmirror
vgcreate labvg /dev/md/labmirror
lvcreate -L 256M -n labdata labvg
mkfs.ext4 /dev/labvg/labdata
mkdir -p /mnt/labdata
mount /dev/labvg/labdata /mnt/labdata
printf 'kernel-lab-data\n' > /mnt/labdata/check.txt
sha256sum /mnt/labdata/check.txt
pvs; vgs; lvs -a -o +devices
findmnt /mnt/labdata

Observe: /proc/mdstat RAID1 sync progress; mdadm --detail active devices; pvs/vgs/lvs PV→VG→LV relationship; findmnt confirms ext4 mount. md and LVM device names may differ across distro/udev configuration.

Extend LV and filesystem (free extents permitting):

lvextend -L +64M -r /dev/labvg/labdata
df -h /mnt/labdata

-r asks LVM to resize the filesystem through fsadm; filesystem tools must be installed. ext4 can grow online; shrinking is different and risky.

Simulate a member failure (replace $LOOPA only after checking it):

mdadm --manage /dev/md/labmirror --fail "$LOOPA"
mdadm --detail /dev/md/labmirror
cat /proc/mdstat
cat /mnt/labdata/check.txt
mdadm --manage /dev/md/labmirror --remove "$LOOPA"
mdadm --manage /dev/md/labmirror --add "$LOOPA"
watch -n 2 cat /proc/mdstat

The array should continue serving data in degraded RAID1 mode, and re-added member should resync. RAID is availability, not backup: deletion and corruption propagate.

Safe cleanup (after resync; no other mounts/users):

umount /mnt/labdata
lvremove -y /dev/labvg/labdata
vgremove -y labvg
pvremove -y /dev/md/labmirror
mdadm --stop /dev/md/labmirror
losetup -d "$LOOPA" "$LOOPB"
rm -f /root/kernel-storage-lab/raid-a.img /root/kernel-storage-lab/raid-b.img

If cleanup fails, inspect findmnt, lsof, lsblk, /proc/mdstat, and dmsetup ls --tree rather than force-removing busy devices.

Source-code mapping: userspace mdadm configures drivers/md/md.c; LVM tools configure device mapper in drivers/md/dm.c; ext4 writes via fs/ext4/ and the block layer. These are separate subsystems with distinct recovery semantics.

Deep Implementation Workshop D — RAID Level Engineering Decisions

Level Minimum drives Usable capacity (equal-sized disks) Tolerates Key trade-off
RAID0 2 N × S 0 failures Striping improves throughput but increases loss risk
RAID1 2 Typically S for two-way mirror One of two members Copies data, capacity overhead
RAID5 3 (N−1) × S 1 member failure Parity write penalty, rebuild exposure
RAID6 4 (N−2) × S 2 member failures More parity overhead
RAID10 4 (N/2) × S Depends on failed mirror pairs Fast rebuild, more disks

Worked example: 4 × 2 TiB disks: RAID5 ≈ 6 TiB usable, RAID6 ≈ 4 TiB, RAID10 ≈ 4 TiB (before filesystem/metadata overhead). Exact resilience of RAID10 depends on layout and which members fail.

Debugging checklist: cat /proc/mdstat, mdadm --detail /dev/md/..., journalctl -k, SMART/drive health, iostat -xz, verify backups, identify member by serial number before replacement. Never interpret mdadm --detail alone as proof that data is application-consistent.

Advanced Engineering Supplement — Verified Concepts and Worked Examples

Yeh supplement un mechanisms par extra implementation-level detail deta hai jahan production incidents mein surface-level knowledge kaam nahi aata. Isko chapter references ke saath padho. Output aur feature availability kernel/configuration-specific hain.

A. fork() ke baad copy-on-write ki actual semantics

fork() parent address space ka logical snapshot child ko deta hai. Kernel page-table entries ko shareable backing ki taraf point karwa sakta hai aur writable private mappings ko read-only protect karta hai. Jab parent ya child private page par write karta hai, CPU protection fault generate karta hai. Kernel fault path VMA permissions check karta hai, writable private mapping ke liye naya page allocate/copy kar sakta hai, page-table mapping update karta hai, aur execution resume karta hai. Har fork par saari RAM copy nahi hoti. Shared mappings, huge pages, pinned pages aur filesystem mappings alag details laate hain. mm/memory.c mein fault handlers release-specific names ke saath padho.

Lab: mmap(MAP_PRIVATE|MAP_ANONYMOUS) + fork() program mein child ko fflush(stdout) ke saath print karao; /usr/bin/time -v se minor faults compare karo. Counters process setup ke karan vary karenge; child/parent values alag honi chahiye. Debugging: permission fault, COW fault aur missing-page fault ko ek jaisa mat samjho.

B. Scheduler: EEVDF, runnable state aur latency

Linux fair scheduling historically CFS red-black tree/virtual runtime ideas se associated hai; newer kernels EEVDF-based task selection use karte hain. kernel/sched/fair.c ko target version ke saath read karo. task_struct task ki identity/state hold karta hai; runqueue CPU-specific scheduling state maintain karti hai. Context switch mein runnable task choose karna, previous task state account karna, registers aur address-space context switch karna alag steps hain. load average CPU utilization ka synonym nahi; uninterruptible tasks bhi contribute kar sakte hain.

Lab: CPU stress process start karo (VM only), pidstat -w -u 1, vmstat 1, perf sched timehist (supported kernels) compare karo. Scenario: high context-switch count alone issue prove nahi karta—latency aur throughput correlate karo.

C. Block I/O: write() se disk tak

write() ka success hamesha persistent storage ka proof nahi: buffered I/O page cache ko dirty kar sakta hai; background writeback later device tak bhejta hai. fsync() file data aur required metadata ko stable storage tak flush karne ki guarantee ke liye request karta hai, but real durability filesystem, drive caches aur hardware behavior par depend karti hai. VFS -> filesystem -> bio -> blk-mq -> device driver -> controller path inspect karo. Device mapper aur md layers stacking mein requests remap/mirror kar sakti hain.

Debugging: iostat -xz 1, /proc/diskstats, cat /proc/pressure/io, journalctl -k ke saath latency timeline banao. await, aqu-sz, %util ka meaning device type aur parallelism ke hisaab se interpret karo. NVMe par %util=100 necessarily full saturation nahi hota.

D. LVM architecture in depth: PV, VG, LV aur device mapper

  • PV: block device par LVM metadata aur physical extents ka representation. PV ko disk partition, md RAID device, ya loop device par create kiya ja sakta hai.
  • VG: PV extents ka pooled address space. vgs se free extents dekhna important hai: df filesystem free space dikhata hai, VG capacity nahi.
  • LV: logical address range jise device mapper targets physical extents se map karte hain. Linear LV, striped LV, thin LV, snapshot LV ki semantics alag hain.
  • Filesystem: LV ke upar ext4/XFS ka independent metadata aur size hota hai. LV resize ke baad filesystem resize separate concern hai; lvextend -r suitable filesystem tools ke through combine kar sakta hai.

Data path: app write() -> VFS -> ext4/XFS -> block I/O -> dm logical sector mapping -> underlying md/physical block device. Control path: lvcreate userspace metadata modify karta hai aur kernel device-mapper targets configure karta hai; kernel itself VG planning nahi karta.

Snapshot semantics: Classic COW snapshot origin changes ko preserve karne ke liye snapshot exception store use karta hai. Thin snapshots shared mappings aur reference accounting par based hote hain. Snapshot backup nahi: same underlying pool fail hone par snapshot bhi lose ho sakta hai. Thin pool data aur metadata usage dono monitor karo: lvs -a -o lv_name,segtype,data_percent,metadata_percent.

Grow workflow: pvs; vgs; lvs -a -o +devices; findmnt -T /mount; df -h /mount -> verify VG free extents -> lvextend -L +... -r /dev/VG/LV -> lvs and df verify. Shrink workflow: filesystem-dependent. XFS shrink support nahi karta; ext4 shrink offline and careful order ke saath possible hai. Never blindly run lvreduce—filesystem truncate hone se permanent data loss ho sakta hai.

Incident: df 100% but vgs has free space: determine filesystem type, mount, LV path, snapshots/thin pool state, backup and growth plan. vgs 100% but df low: storage allocation aur filesystem occupancy alag metrics hain. pvmove migration mein transient risk and performance overhead evaluate karo.

E. md RAID internals and failure recovery

mdadm kernel md driver ko configure karta hai. RAID1 writes multiple members par mirror hote hain; read selection and resync kernel manage karta hai. RAID5 parity XOR relationship par based hoti hai: parity data se reconstruct ho sakti hai, but degraded writes/rebuilds I/O intensive hain. RAID6 two independent parity schemes use karta hai. RAID10 mirrors + striping combine karta hai, failure tolerance specific layout aur affected pairs par depend karti hai.

RAID1 failure flow: drive I/O error -> kernel logs -> md member faulty mark -> array degraded -> remaining member serves I/O -> replacement identify by stable device serial -> add replacement -> resync -> verify array clean and application checksums. cat /proc/mdstat and mdadm --detail /dev/md/... essential hain; journalctl -k actual I/O errors reveal karta hai. Never remove random /dev/sdX by name without mapping serial and mount graph.

RAID5/6 write-hole risk: unexpected power loss partial data/parity updates cause inconsistency. Journal/PPL features, battery-backed caches and filesystem-level checksums/recovery are mitigation considerations, not universal guarantees. RAID does not protect against deletion, ransomware, filesystem corruption, operator error or site loss. Independent, tested backup zaroori hai.

Failure scenario: array degraded, resync 20%, latency spikes. Priority: verify backups, check drive health and kernel errors, avoid unnecessary writes, confirm spare capacity, monitor resync speed and user latency. Do not rush --force assembly: metadata event counters and member freshness matter.

F. Locking and memory ordering

Mutex sleepable context ke liye hai; spinlock critical sections ko non-sleeping context mein protect kar sakta hai. IRQ context mein sleep karna invalid ho sakta hai. RCU read-heavy structures mein readers ko low-overhead access deta hai, but lifetime/grace-period rules maintain karna mandatory hai. Atomic variables alone multi-field invariants protect nahi karte. Memory barriers compiler/CPU reordering semantics se related hain; locks ke memory-order guarantees ko understand karo.

Lab: kernel module code review mein kmalloc(..., GFP_KERNEL) under spinlock ko flag karo: allocation sleep kar sakti hai. Fix context and allocation strategy change karke karo, blind GFP_ATOMIC use karke nahi. Debugging: lockdep, KCSAN, ftrace, perf lock where available; production overhead aur kernel config check karo.

G. Networking: packet receive to application

NIC DMA RX descriptors fill karta hai; interrupt NAPI polling schedule kar sakta hai; driver budget ke andar packets process karta hai. Generic stack mein skb metadata protocols ko carry karta hai. IP routing, Netfilter hooks, transport demultiplexing, socket receive queue and recv() complete path banate hain. XDP native path early drop/redirect kar sakta hai, sometimes skb creation se pehle.

Incident: packet drops: NIC hardware counters (ethtool -S), interface (ip -s link), softnet (/proc/net/softnet_stat), TCP (nstat), socket buffers (ss -m) separately check karo. Ek drop counter ko blindly app fault mat bolo.

H. Kernel debugging decision tree

Failure? -> reproducible?
          | yes -> disposable VM + matching debug symbols
          | no  -> capture timestamp, logs, workload, baseline
      kernel panic/oops? -> vmcore + crash/gdb + source mapping
      latency? -> perf/ftrace/tracepoints with bounded sampling
      memory corruption? -> KASAN/KFENCE in test kernel
      data race? -> KCSAN/lockdep in test kernel
      storage? -> block stats + md/dm/filesystem logs
      networking? -> NIC -> driver -> IP -> transport -> socket counters

Always document: exact uname -a, config, module taint, kernel log timestamp, reproducer, last-known-good kernel, mitigation, rollback, post-fix regression test.

I. Kernel patch and testing workflow

  1. git checkout target stable or mainline commit; save hash.
  2. Write failing reproducer or KUnit test first when practical.
  3. Small patch with clear commit message: problem, mechanism, why fix works, test evidence.
  4. git diff --check; run scripts/checkpatch.pl as guidance, not correctness proof.
  5. Build affected configuration, run kselftest/KUnit, sanitizers when relevant.
  6. Test in QEMU; compare baseline performance and failure behavior.
  7. git format-patch -1; inspect MAINTAINERS and Documentation/process/submitting-patches.rst before any actual submission.

Interview exercise: Why does a patch compile but still fail code review? Because locking, lifetime, error unwinding, ABI compatibility, test coverage, maintainability and subsystem conventions matter beyond syntax.

E2. Kernel module with parameters, concurrency-safe counters and debugfs-free introspection

Design objective: Build a minimal external module that demonstrates module lifetime, read-only module parameter, periodic delayed work and safe shutdown. No /dev node and no hardware access. VM only.

lab_counter.c:

// SPDX-License-Identifier: GPL-2.0
#include <linux/atomic.h>
#include <linux/init.h>
#include <linux/jiffies.h>
#include <linux/module.h>
#include <linux/moduleparam.h>
#include <linux/workqueue.h>

static unsigned int period_ms = 1000;
module_param(period_ms, uint, 0444);
MODULE_PARM_DESC(period_ms, "Sampling interval in milliseconds (read-only)");

static atomic64_t samples = ATOMIC64_INIT(0);
static struct delayed_work sample_work;

static void sample_once(struct work_struct *work)
{
    s64 n = atomic64_inc_return(&samples);

    pr_info_ratelimited("lab_counter: sample=%lld\n", (long long)n);
    schedule_delayed_work(&sample_work, msecs_to_jiffies(period_ms));
}

static int __init lab_counter_init(void)
{
    if (period_ms < 100 || period_ms > 60000)
        return -EINVAL;

    INIT_DELAYED_WORK(&sample_work, sample_once);
    schedule_delayed_work(&sample_work, msecs_to_jiffies(period_ms));
    pr_info("lab_counter: loaded period_ms=%u\n", period_ms);
    return 0;
}

static void __exit lab_counter_exit(void)
{
    cancel_delayed_work_sync(&sample_work);
    pr_info("lab_counter: unloaded after %lld samples\n",
            (long long)atomic64_read(&samples));
}

module_init(lab_counter_init);
module_exit(lab_counter_exit);
MODULE_LICENSE("GPL");
MODULE_DESCRIPTION("Kernel teaching module: periodic delayed work");

Makefile (the two recipe lines must begin with a TAB):

obj-m += lab_counter.o
KDIR ?= /lib/modules/$(shell uname -r)/build

all:
	$(MAKE) -C $(KDIR) M=$(CURDIR) modules

clean:
	$(MAKE) -C $(KDIR) M=$(CURDIR) clean

Why each mechanism exists: module_param exposes a parameter that can be set at insertion time (period_ms=500); mode 0444 allows read-only sysfs visibility. atomic64_t avoids a data race for the counter, though it does not make a compound multi-field state update atomic. delayed_work executes in process context through a workqueue; its callback is not a hard IRQ handler. msecs_to_jiffies() converts time units, subject to tick granularity. cancel_delayed_work_sync() waits for an executing callback and prevents pending work from running after teardown; don't hold a lock needed by the callback while calling it. pr_info_ratelimited() avoids unlimited log volume. period_ms is validated to avoid accidental extremely frequent scheduling. Module parameter permissions do not provide a security boundary against a privileged administrator.

Failure analysis: Invalid parameters → validate range; invalid module format → check vermagic/headers/architecture; Key was rejected → signing/lockdown; missing build directory → install matching headers. dmesg may require elevated privileges. Do not load on critical hosts.

E3. A user-space page-fault investigation (safe without kernel modules)

fault_lab.c:

#define _GNU_SOURCE
#include <errno.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>
#include <sys/resource.h>
#include <unistd.h>

static void report(const char *stage)
{
    struct rusage u;
    if (getrusage(RUSAGE_SELF, &u) == -1) {
        perror("getrusage");
        exit(EXIT_FAILURE);
    }
    printf("%s: minor=%ld major=%ld\n", stage, u.ru_minflt, u.ru_majflt);
}

int main(void)
{
    long ps = sysconf(_SC_PAGESIZE);
    const size_t pages = 2048;
    if (ps <= 0) { fprintf(stderr, "page size error\n"); return 1; }
    size_t bytes = pages * (size_t)ps;
    unsigned char *p = mmap(NULL, bytes, PROT_READ | PROT_WRITE,
                            MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (p == MAP_FAILED) { perror("mmap"); return 1; }
    report("before touching");
    for (size_t i = 0; i < pages; ++i)
        p[i * (size_t)ps] = (unsigned char)i;
    report("after touching");
    if (munmap(p, bytes) == -1) { perror("munmap"); return 1; }
    return 0;
}

gcc -std=c11 -O0 -Wall -Wextra -Werror fault_lab.c -o fault_lab
./fault_lab
/usr/bin/time -v ./fault_lab

Mechanism: mmap() virtual address range reserve karta hai; physical pages may be provisioned lazily. First write to each page can trigger minor faults as mappings are established. ru_minflt/ru_majflt cumulative counters hain, so before/after difference meaningful hai. The exact number is not guaranteed due to transparent huge pages, kernel version, page-table behavior and other runtime activity. major generally indicates a fault requiring I/O, not simply a more serious error. Correlate with /proc/<pid>/smaps and tracing in a controlled experiment.

E4. Storage engineering: md RAID1 under LVM and ext4

Layering

          /mnt/labdata  (mounted ext4)
                 |
        /dev/labvg/labdata  (logical volume)
                 |
              labvg (VG)
                 |
       /dev/md/labmirror (LVM PV)
                 |
           md RAID1 mirror
              /       \
      loop-a.img     loop-b.img

Key invariants: RAID1 mirrors blocks and can survive one member failure, but does not protect against accidental deletion, ransomware, filesystem corruption or two simultaneous failures. LVM provides flexible logical allocation, not redundancy by itself. ext4 online grow works, but online shrink does not. A filesystem snapshot must be consistent at the application level for reliable recovery; LVM snapshots alone do not guarantee transaction consistency.

Provisioning and validation

Use the full Deep Implementation Workshop C from the masterbook, only inside a disposable VM, and verify both loop devices are backed by your test files. Add these diagnostic commands:

lsblk -o NAME,MAJ:MIN,SIZE,TYPE,FSTYPE,MOUNTPOINTS
cat /proc/mdstat
sudo mdadm --detail /dev/md/labmirror
sudo dmsetup ls --tree
sudo pvs -o pv_name,vg_name,pv_size,pv_free
sudo vgs -o vg_name,vg_size,vg_free
sudo lvs -a -o lv_name,vg_name,lv_size,devices
findmnt /mnt/labdata

Observe layer boundaries: mdadm controls md RAID metadata, pvcreate writes LVM metadata, lvcreate maps logical extents, and mkfs.ext4 writes filesystem metadata. fsync() durability depends on lower-layer flush/barrier behavior, filesystem and device reliability. iostat measures queue and latency, but interpreting %util as universal saturation is wrong on parallel devices.

Recovery decision tree

I/O errors?
  |
  +-- No --> inspect fs usage, VG free extents, inode exhaustion, latency
  |
  +-- Yes --> identify stable device IDs, read dmesg + mdadm status
                 |
                 +-- RAID degraded but mounted --> confirm backup, replace member
                 |
                 +-- metadata inconsistent --> preserve images, seek recovery plan
                 |
                 +-- filesystem errors --> unmount before offline fsck; no blind repair

Avoid: running fsck on mounted writable filesystems, using lvreduce without a verified shrink plan, or issuing mdadm --create against existing data. Record exact commands, disk serials, metadata version, UUIDs, backup status and rollback point in the incident report.

E5. Tracing and debugging: a practical escalation ladder

Reproducible incident notebook

  1. Symptom: exact observable failure and start time.
  2. Environment: uname -a, config, hardware/VM, container limits, workload.
  3. Baseline: CPU, run queue, memory PSI, block latency, network counters.
  4. Hypotheses: at least two competing explanations with falsification criteria.
  5. Targeted tracing: choose one subsystem; measure tracing overhead.
  6. Evidence: save timestamps, raw logs, graphs and source commit ID.
  7. Mitigation: reversible short-term change, with risk and rollback.
  8. Verification: reproduce original workload and regression test.

Worked incident: slow writes on a RAID1 + LVM + ext4 server

Observation: application p99 write latency rises, but CPU is only 25% utilized. Do not conclude that CPU is fine and add RAM. First inspect iostat -xz 1, cat /proc/mdstat, mdadm --detail, journalctl -k, lvs -a -o +devices, df -h, and application fsync() frequency. Suppose /proc/mdstat shows a RAID1 rebuild and block latency is high: the rebuild may compete for I/O bandwidth. Validate with timestamps and workload measurements; correlation alone does not establish causation. Mitigate by controlling background rebuild speed where supported and operationally safe, checking hardware health, and ensuring backups. Never stop an active rebuild casually without understanding the fault state.

E6. Code review and publishing checklist

  • Specify exact Linux release/tag and architecture for every kernel-specific code sample.
  • Show complete source, Makefile/build invocation and required config.
  • Explain each API, lock, reference, lifetime, and error/cleanup path.
  • Separate safe host diagnostics from privileged VM-only destructive commands.
  • Test compilation with warnings enabled and record output.
  • Test runtime behavior, unload/cleanup and repeated execution.
  • For drivers: validate partial initialization and teardown on failures.
  • For concurrency: assess lock ordering, sleeping context and use-after-free risks.
  • For storage: verify backups, stable device IDs and recoverability before mutation.
  • Cross-check source links and references against the selected release.
  • Replace provisional diagrams with publication-quality numbered figures.
  • Generate actual page numbers and alphabetical index only in final typeset PDF/DOCX.
