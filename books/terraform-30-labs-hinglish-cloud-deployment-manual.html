Terraform Zero to AWS Cloud Deployment

Hinglish Theory, Command Workflows, Practical Labs, Troubleshooting and Interview Preparation

Audience: Linux / DevOps engineers moving from Terraform basics to practical AWS provisioning.
Platform: Debian 12 or comparable Linux, Terraform CLI, AWS CLI, AWS account.
Time: 10–14 days, ~2–4 hours/day.
Outcome: Write, plan, deploy, inspect, modify, and safely remove AWS infrastructure using reusable Terraform configurations.

Cost & security: AWS resources can incur charges, including EC2, public IPv4 addresses, NAT gateways, load balancers and data transfer. Use a dedicated learning account, configure billing alerts, and run terraform destroy after each lab. Do not commit secrets, state files, .terraform/, or credential files. Never run an unfamiliar apply or destroy without inspecting the plan.

Chapter 1 — Terraform kya hai?

Terraform ek Infrastructure as Code (IaC) tool hai. Matlab AWS console par manually click karke VPC/EC2 create karne ke bajay hum infrastructure ko declarative configuration files (.tf) mein describe karte hain.

Imperative vs declarative: Imperative mein aap bolte ho kaise karna hai: create subnet, create route. Declarative mein aap bolte ho desired result kya hai: aws_subnet resource with specified CIDR. Terraform provider APIs use karke current infrastructure ko desired configuration ke saath reconcile karta hai.

Core pieces:

  • Terraform CLI/core: Parses HCL, resolves dependency graph, computes changes, and coordinates execution.
  • Provider: Plugin that communicates with external APIs, e.g., hashicorp/aws, hashicorp/local.
  • Resource: Managed infrastructure object, e.g., aws_vpc.main.
  • Data source: Reads existing external information without managing its lifecycle.
  • State: Terraform's mapping of resource addresses to real objects and recorded attributes; it can contain sensitive information.
  • Module: A folder of Terraform configuration. Every project has a root module; reusable child modules are invoked with module blocks.
  • Backend: Storage mechanism for Terraform state; may support locking.

Workflow and internal mechanism

main.tf / variables.tf / outputs.tf
              |
              v
      terraform init
      providers + modules + backend
              |
              v
      terraform validate
      syntax + configuration consistency
              |
              v
      terraform plan
      read state + query provider APIs
      build dependency graph + diff
              |
              v
      human reviews changes
              |
              v
      terraform apply
      call cloud APIs in dependency order
              |
              v
      update Terraform state
              |
              v
      terraform output / AWS verification

Terraform is not a full configuration management system: use cloud-init, Ansible, images, or Kubernetes for substantial application configuration.

Chapter 2 — Install Terraform on Debian 12

Run in Debian terminal. Prefer the official HashiCorp apt repository. The commands below use Debian's standard GPG/keyring flow; verify the current instructions at https://developer.hashicorp.com/terraform/install before installing.

sudo apt-get update
sudo apt-get install -y gnupg software-properties-common curl ca-certificates
wget -O- https://apt.releases.hashicorp.com/gpg | \
  gpg --dearmor | sudo tee /usr/share/keyrings/hashicorp-archive-keyring.gpg >/dev/null
printf 'deb [signed-by=/usr/share/keyrings/hashicorp-archive-keyring.gpg] https://apt.releases.hashicorp.com %s main\n' \
  "$(. /etc/os-release && echo "$VERSION_CODENAME")" | \
  sudo tee /etc/apt/sources.list.d/hashicorp.list
sudo apt-get update
sudo apt-get install -y terraform
terraform version
terraform -help

If wget is missing: sudo apt-get install -y wget. Never use curl | sudo bash from an unverified source.

Important file names

terraform-project/
├── versions.tf        # Terraform and provider version constraints
├── providers.tf       # Provider configuration
├── main.tf            # Resources and data sources
├── variables.tf       # Input variable declarations
├── terraform.tfvars   # Non-secret variable values (optional)
├── outputs.tf         # Outputs
├── .terraform.lock.hcl # Selected provider versions; commit to Git
└── .gitignore

Terraform loads all .tf files in the same directory together. File names are conventions, not execution order.

Lab 1 — Your first Terraform resource (no cloud cost)

Goal: Use Terraform to create a file on your local machine. Where: Debian terminal.

mkdir -p ~/terraform-course/lab01-local
cd ~/terraform-course/lab01-local
cat > main.tf <<'HCL'
terraform {
  required_providers {
    local = {
      source  = "hashicorp/local"
      version = "~> 2.5"
    }
  }
}

resource "local_file" "hello" {
  filename = "${path.module}/hello.txt"
  content  = "Hello from Terraform!\n"
}

output "file_path" {
  value = local_file.hello.filename
}
HCL
terraform fmt
terraform init
terraform validate
terraform plan
terraform apply
cat hello.txt
terraform output
terraform state list
terraform destroy

Expected conceptual output: Plan shows + create for local_file.hello; after apply, hello.txt exists; destroy removes the managed file.

Command workflow:

  • fmt: normalizes HCL formatting; does not deploy.
  • init: downloads provider plugin, writes .terraform.lock.hcl; does not create your managed resources.
  • validate: checks configuration validity; does not guarantee AWS permissions or runtime success.
  • plan: calculates intended actions; may query remote APIs; does not apply changes.
  • apply: executes proposed actions after approval; -auto-approve bypasses interactive approval and is risky.
  • state list: shows addresses Terraform manages.
  • destroy: plans and deletes managed resources; always inspect first.

Try it: Change file content, run terraform plan, note ~ update or replacement according to provider behavior, and apply again.

Chapter 3 — HCL explained line by line

resource "local_file" "hello" {
  filename = "${path.module}/hello.txt"
  content  = "Hello from Terraform!\n"
}
  • resource: managed object declaration.
  • "local_file": resource type defined by local provider.
  • "hello": local name, forming address local_file.hello.
  • { ... }: block body.
  • filename: argument expected by provider.
  • path.module: built-in reference to current module directory.
  • content: desired file contents.

References create dependencies. If resource B refers to aws_vpc.main.id, Terraform knows B depends on A. depends_on is for dependencies Terraform cannot infer from expressions.

Lab 2 — Variables, types, locals, functions and outputs

mkdir -p ~/terraform-course/lab02-variables
cd ~/terraform-course/lab02-variables
cat > main.tf <<'HCL'
terraform {
  required_providers {
    local = { source = "hashicorp/local", version = "~> 2.5" }
  }
}

variable "environment" {
  type        = string
  description = "Deployment environment"
  default     = "dev"
  validation {
    condition     = contains(["dev", "test", "prod"], var.environment)
    error_message = "environment must be dev, test or prod"
  }
}

variable "owners" {
  type    = list(string)
  default = ["platform", "security"]
}

locals {
  app_name = "web-${var.environment}"
  message  = "App=${local.app_name}; Owners=${join(",", var.owners)}\n"
}

resource "local_file" "config" {
  filename = "${path.module}/config.txt"
  content  = local.message
}

output "app_name" {
  value = local.app_name
}
HCL
terraform init
terraform plan -var='environment=test'
terraform apply -var='environment=test'
cat config.txt
terraform destroy -var='environment=test'

Theory: var.environment reads an input; local.app_name computes an internal value; output exposes a result. list(string) is an ordered list. Other useful types: number, bool, set(string), map(string), object({ name=string, port=number }). for_each works with maps or sets of strings; count uses numeric indices.

Variable precedence (practical overview): defaults, environment variables TF_VAR_name, terraform.tfvars / .auto.tfvars, and explicit -var / -var-file overrides. See official docs for full precedence and same-level ordering.

Secrets warning: sensitive = true hides values in normal CLI presentation but does not necessarily prevent storage in state or plan files. Prefer temporary credentials, secret managers and secure state access.

Chapter 4 — State and dependency graph

Terraform state records resource addresses, object IDs, attributes and metadata. It is not simply a copy of your .tf files. Never hand-edit state JSON.

terraform state list
terraform state show local_file.config
terraform show
terraform plan -out=review.tfplan
terraform show review.tfplan

Plan files can contain secrets; protect and delete them after use. terraform state show may reveal sensitive attributes. terraform refresh is deprecated in modern workflows; prefer terraform plan -refresh-only and review before terraform apply -refresh-only when appropriate.

Drift example: Manually edit the local managed file. Run terraform plan. Terraform will detect the discrepancy and propose reconciliation (exact action depends on provider).

Lifecycle concepts: create_before_destroy, prevent_destroy, ignore_changes. These are specialized tools, not substitutes for careful planning. ignore_changes can hide meaningful drift.

Chapter 5 — AWS setup and identity verification

Goal: Provision AWS infrastructure from Debian using credentials safely.

  1. Create or select a dedicated learning AWS account and a least-privilege IAM principal. Avoid using root access keys.
  2. Prefer short-lived credentials via AWS IAM Identity Center (SSO) or an assumed role. Do not paste credentials into .tf.
  3. Install AWS CLI v2 following https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html and verify:
aws --version
aws configure sso --profile terraform-lab
aws sso login --profile terraform-lab
aws sts get-caller-identity --profile terraform-lab
export AWS_PROFILE=terraform-lab
export AWS_REGION=ap-south-1

If your account does not use SSO, ask the account administrator for an appropriate temporary role-based access method. Verify aws sts get-caller-identity before running Terraform.

Permissions: VPC, subnets, route tables, IGW, security groups, EC2 instance operations, describe/read actions and (for later remote state) S3 permissions. IAM permissions vary with lab scope; use a dedicated scoped role and avoid AdministratorAccess in shared/production accounts.

Check in browser: Open the URL shown by terraform output -raw web_url. Initial EC2 user data may take 1–3 minutes. HTTP is deliberately unencrypted for a temporary lab; do not use this architecture for production.

CLI verification:

aws ec2 describe-instances \
  --instance-ids "$(terraform output -raw instance_id)" \
  --query 'Reservations[].Instances[].{State:State.Name,IP:PublicIpAddress}' \
  --output table
curl -I "$(terraform output -raw web_url)"
terraform state list
terraform graph > graph.dot

Cleanup (mandatory):

terraform plan -destroy
terraform destroy
aws ec2 describe-instances --filters Name=tag:Project,Values=tf-crash-lab \
  --query 'Reservations[].Instances[].{ID:InstanceId,State:State.Name}' --output table

Why the command sequence matters: init installs provider and sets backend, validate checks syntax, plan -out freezes a reviewed proposal, apply lab.tfplan applies that saved proposal (subject to possible failures if real infrastructure changed), output reads computed state values, destroy removes managed resources. Never assume destroy succeeded until you check AWS.

Line-by-line key ideas: data "aws_ami" discovers an AMI, aws_vpc.main.id creates implicit dependency, map_public_ip_on_launch makes subnet eligible for public IPs, 0.0.0.0/0 route points internet traffic to IGW, SG ingress allows only TCP 80, user_data bootstraps Nginx, and metadata_options.http_tokens = "required" enforces IMDSv2.

Lab 4 — Reusable modules

A module groups reusable infrastructure. Structure:

lab04-modules/
├── main.tf
├── variables.tf
└── modules/
    └── network/
        ├── main.tf
        ├── variables.tf
        └── outputs.tf

Child module modules/network/variables.tf:

variable "cidr" { type = string }
variable "name" { type = string }

modules/network/main.tf:

resource "aws_vpc" "this" {
  cidr_block = var.cidr
  tags       = { Name = var.name }
}

modules/network/outputs.tf:

output "vpc_id" { value = aws_vpc.this.id }

Root main.tf (with AWS provider configured as in Lab 3):

module "network" {
  source = "./modules/network"
  cidr   = "10.30.0.0/16"
  name   = "training-vpc"
}
output "network_vpc_id" { value = module.network.vpc_id }

Run terraform init, terraform plan, terraform apply, terraform output, then terraform destroy.

Difference: module.network.vpc_id is a child module output, while aws_vpc.this.id is a resource attribute inside that module.

Chapter 6 — count vs for_each

variable "subnets" {
  type = map(string)
  default = {
    app = "10.30.1.0/24"
    ops = "10.30.2.0/24"
  }
}

resource "aws_subnet" "named" {
  for_each   = var.subnets
  vpc_id     = module.network.vpc_id
  cidr_block = each.value
  tags       = { Name = each.key }
}

for_each gives stable addresses like aws_subnet.named["app"]; count creates indexed addresses like aws_subnet.named[0]. Use stable keys for long-lived resources. For AWS subnet creation, CIDRs must not overlap, and each subnet belongs to one AZ.

Chapter 7 — Remote state on S3 and locking

Why: Local terraform.tfstate on one laptop creates collaboration and loss risks. An S3 backend stores state centrally. For current Terraform releases, S3 native locking can use use_lockfile = true (check installed Terraform backend support). Older guides often show DynamoDB locking, which is deprecated for this backend in current documentation.

Bootstrap: Create a private, versioned S3 bucket separately (through a dedicated bootstrap Terraform stack or approved admin process). Ensure bucket name is globally unique; configure encryption, block public access, bucket versioning and restricted IAM. Never put the state bucket under the same state that depends on it without a deliberate bootstrap design.

terraform {
  backend "s3" {
    bucket       = "REPLACE-WITH-YOUR-UNIQUE-STATE-BUCKET"
    key          = "terraform-course/dev/terraform.tfstate"
    region       = "ap-south-1"
    encrypt      = true
    use_lockfile = true
  }
}

Migration: Add backend block after creating bucket, then run:

terraform init -migrate-state
terraform state list
terraform plan

Important: Backends do not accept normal var.* interpolation. Use partial backend config or separate backend config files when appropriate. State contains sensitive data; restrict read/write, enable versioning, audit access and test recovery. The .tflock object requires appropriate S3 permissions. Never manually delete a lock without establishing that no operation is active.

Chapter 8 — Import, drift, refactoring and state operations

Scenario: Existing VPC was created manually. To bring it under Terraform management, write matching resource configuration and use an import block:

import {
  to = aws_vpc.imported
  id = "vpc-REPLACE_WITH_REAL_ID"
}
resource "aws_vpc" "imported" {
  cidr_block = "10.50.0.0/16"
}

Run terraform plan, review all proposed changes, then terraform apply. The resource config must match reality or Terraform may plan modifications. You can also use terraform import aws_vpc.imported vpc-... with the resource configuration present.

Refactor without recreation:

moved {
  from = aws_vpc.old
  to   = aws_vpc.main
}

A moved block communicates a resource address change to Terraform. For complex refactors and shared modules, test the plan in a nonproduction environment.

Commands and cautions:

  • terraform state list: enumerate managed objects.
  • terraform state show ADDRESS: inspect one object.
  • terraform state mv OLD NEW: move state address; prefer declarative moved blocks for versioned refactors.
  • terraform state rm ADDRESS: stops managing an object without deleting it; can create orphaned infrastructure.
  • terraform apply -replace=ADDRESS: deliberately replace one resource; check downtime and data loss.
  • terraform plan -refresh-only: inspect remote drift in recorded state.

Chapter 9 — Environments and production structure

infrastructure/
├── modules/

├── environments/

Best practice: Separate state keys, credentials, approval controls and blast radius for dev/prod. A single state should not own unrelated environments. Use version-pinned modules and providers, code review, protected branches and least-privilege CI roles. Workspaces can help with identical deployments but are not a substitute for strong production isolation.

Production architecture concept: Multi-AZ VPC, public subnets for ALB, private app subnets, private database subnets, tightly scoped SGs, TLS/ACM, logging/monitoring, backup, tagging, and policy checks. This crash course does not automatically deploy a production-grade design; the single-EC2 lab is intentionally simpler.

Example GitHub Actions validation workflow (safe, no cloud apply):

name: Terraform checks
on:
  pull_request:
    paths: ['infra/**']
jobs:
  validate:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: infra
    steps:
      - uses: actions/checkout@v4
      - uses: hashicorp/setup-terraform@v3
      - run: terraform fmt -check -recursive
      - run: terraform init -backend=false
      - run: terraform validate

For cloud plans, configure GitHub OIDC to assume a scoped AWS IAM role; never store permanent AWS access keys in repository secrets if role federation is available. Pin third-party actions to reviewed commit SHAs for high-assurance production pipelines. Treat plan artifacts as sensitive, protect environment approvals, and ensure apply executes only the reviewed plan.

Chapter 13 — Interview Q&A (senior DevOps focus)

Q1. Terraform vs Ansible? Terraform mainly manages desired infrastructure objects and lifecycle via providers; Ansible focuses on configuration and procedural automation. They complement each other.

Q2. init vs plan vs apply? init sets up provider/modules/backend; plan proposes changes; apply executes changes and updates state.

Q3. Why state? To map config resource addresses to real remote objects and track attributes for planning.

Q4. What if state is deleted? Terraform loses the mapping; do not blindly apply. Recover versioned remote state or reconstruct/import resources with care.

Q5. What is drift? Actual infrastructure differs from recorded/configured desired state, often due to manual changes.

Q6. How is resource order decided? Terraform creates a dependency graph from references and explicit dependencies, then schedules independent operations concurrently.

Q7. count vs for_each? count addresses resources by numeric index; for_each uses stable map/set keys, generally better for named resources.

Q8. Data source vs resource? Data source reads existing external information; resource manages an object's lifecycle.

Q9. Module? Reusable configuration package with inputs, resources and outputs; modules enable standardized deployments.

Q10. What is state locking? Prevents conflicting concurrent state writes. For S3 backend, current Terraform can use an S3 lockfile.

Q11. What is terraform import? Brings an existing object under Terraform state management, paired with matching configuration.

Q12. How do you protect secrets? Use IAM roles/OIDC, avoid hardcoded secrets, restrict encrypted state access, minimize plan artifact exposure and use managed secret services.

Q13. How do you safely deploy production changes? Version-control, validate, scan, plan, peer review, approve, apply saved plan in trusted runner, monitor and have rollback/recovery steps.

Q14. What does prevent_destroy do? Terraform lifecycle protection that rejects planned destruction of a resource while the rule is present; not an absolute protection against manual/cloud deletion.

Q15. Why does a resource replace instead of update? Some provider attributes are immutable or changes require recreation. Read plan's replacement reason and provider docs.

Q16. Can Terraform manage Kubernetes? Yes via Kubernetes/Helm providers, but consider cluster bootstrap dependencies, state ownership and GitOps separation.

Q17. How would you manage dev/test/prod? Separate state, IAM roles, environment config, approvals and cost boundaries; shared versioned modules.

Q18. Terraform in Jenkins? Jenkins checks out code, initializes backend, validates/scans, creates plan, requests approval, applies reviewed plan with scoped temporary credentials, and records audit results.

Q19. Terraform taint? Legacy workflow to mark replacement; modern usage prefers terraform apply -replace=ADDRESS.

Q20. How to debug provider errors? Confirm versions, credentials, region, permissions, API quotas and request details. Use TF_LOG=DEBUG only temporarily and protect logs because they may expose sensitive data.

Q21. Why commit .terraform.lock.hcl? It records provider selections/checksums to improve reproducibility across machines.

Q22. What is a backend migration? Moving state storage from one backend to another, e.g., local to S3, using terraform init -migrate-state after verifying destination and backups.

Q23. What happens if apply partially fails? Some resources may have been created; inspect state and cloud, correct the root issue, re-plan and reconcile. Never assume automatic rollback.

Q24. What is a saved plan? terraform plan -out=... writes a binary plan for subsequent terraform apply <file>; sensitive, and must match appropriate state/context.

Q25. How would you review a Terraform PR? Check blast radius, replacements, IAM scope, network exposure, encryption, tagging, module versions, cost, outputs, backend isolation and rollback path.

Final capstone acceptance checklist

  • Terraform code passes fmt and validate and uses pinned provider constraints.
  • Network includes two AZs, public/private subnet separation and correct routes.
  • ALB targets are healthy; instances have only necessary ingress.
  • RDS is private, uses managed password, and is not reachable from the public internet.
  • Backend is encrypted, versioned and uses state locking; state is not in Git.
  • CI produces a reviewable plan and requires approval for apply.
  • All resources are tagged; budget alarms and cleanup are verified.
  • Document a simulated failure, RCA, corrective action and rollback strategy.
