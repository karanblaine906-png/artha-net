Start with one single-node kind cluster, not three full Linux VMs, EKS or an OpenShift CRC instance. Troubleshooting checklist

  • Docker daemon unreachable → inspect systemctl status docker, permissions, and available disk.
  • ImagePullBackOff → inspect kubectl describe pod, DNS, registry access, tag, pull secrets; offline labs need cached images.
  • kubectl reaches wrong cluster → check kubectl config get-contexts and kubectl config current-context before any mutation.
  • NodeNotReady → inspect kubectl describe node, container runtime and system Pods.
  • OOM/host swapping → stop other applications, delete old kind clusters, reduce replicas and resource requests.
  • kubectl top fails → metrics-server is an optional installation and not guaranteed by kind.
  • NetworkPolicy seems ineffective → confirm the installed CNI enforces it; a Policy object existing does not prove network traffic is restricted.

Lesson 1 — Kubernetes from first principles (taught lesson)

Level: beginner → interview-ready explanation. Estimated study: 3–5 hours including exercises. Run on: your Debian 12 host, using a disposable local kind cluster. Goal: stop treating Kubernetes as a magic command-line tool; learn its control-loop architecture.

1. Why Kubernetes exists

Imagine an API service with three containers on one Linux host. You need to release version 2 while serving traffic, restart failed processes, place workloads on healthy hosts, manage configuration, and discover the correct network endpoint even when container IPs change. Shell scripts can do pieces of this but become brittle as applications and servers multiply.

Kubernetes provides a declarative system: you submit a desired state, and control loops work to achieve it. Kubernetes does not make your application code reliable, fix inconsistent databases, or create physical capacity. It coordinates many of the mundane and difficult operations so your team can define policies and respond to failures systematically.

Hinglish mental model: spec mein tum likhte ho kya chahiye; controllers dekhte hain abhi kya hai; phir dono ka difference close karte hain. Isi process ko reconciliation bolte hain.

2. Pre-Kubernetes building blocks

Container is not a virtual machine

A container is generally a process tree using the host Linux kernel. On Linux, namespaces isolate things such as PID, mount and networking views; cgroups track and constrain resources; image layers and a container runtime help package/start the process. A VM has a separate guest kernel. Kubernetes runs containers in Pods using a container runtime through the Container Runtime Interface (CRI).

Kubernetes is an API-driven control system

  • kubectl is a client. It communicates with kube-apiserver (normally through HTTPS).
  • kube-apiserver validates/admission-processes requests and reads/writes cluster API state, commonly backed by etcd.
  • Controller manager controllers notice desired changes and create/modify dependent objects.
  • Scheduler assigns eligible, unscheduled Pods to nodes using constraints and available resources.
  • kubelet, a node agent, arranges for the runtime to run the containers described in assigned Pods and reports results.
  • CNI plugin implements Pod connectivity; CoreDNS handles cluster DNS; kube-proxy is one possible Service dataplane implementation, not universal in all modern clusters.

Architecture flow

flowchart TD
    A[Developer: kubectl apply] --> B[kube-apiserver]
    B <--> C[(etcd: cluster API state)]
    D[Deployment controller] --> B
    E[Scheduler] --> B
    B <--> F[kubelet on chosen node]
    F --> G[Container runtime]
    G --> H[Application Pods]
    H --> I[Service / cluster networking]

Important correction: The API server handles object API state; it does not itself launch application processes. Also, etcd is not where your container logs or application database must live.

3. The desired-state story (follow every hop)

You submit this object:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: artha-lab
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: nginx
          image: nginx:1.27
          ports:
            - containerPort: 80

Walk the lifecycle:

  1. Client sends a create/update request to the API server (authenticated/authorized/admitted as configured).
  2. The API server stores the desired Deployment object.
  3. Deployment controller observes that the requested revision needs a ReplicaSet.
  4. ReplicaSet controller creates Pod objects toward replicas: 2.
  5. Scheduler chooses nodes for unscheduled Pods.
  6. Kubelets see their assigned Pods and request image pulls/container creation through CRI.
  7. The status reports readiness, errors and observed conditions. If a Pod dies, controllers reconcile the missing replica (subject to constraints).

Do not confuse: spec.replicas: 2 means desired number, not proof that two healthy replicas exist. You must inspect Deployment status, Pod readiness, events and requests through a Service.

4. Understand YAML line by line

  • apiVersion: apps/v1 selects the Deployment API group/version.
  • kind: Deployment selects the API object type.
  • metadata.name gives a namespace-scoped name; metadata.namespace selects its namespace.
  • spec.replicas: 2 declares desired Pod count.
  • spec.selector.matchLabels tells the Deployment which Pods it owns through its label selector; it must match the template labels.
  • spec.template is the blueprint of each Pod, not an actual Pod.
  • template.metadata.labels.app: web is used for selection by controller and later by Service.
  • template.spec.containers enumerates containers within one Pod.
  • image: nginx:1.27 identifies a container image tag. For important production releases, prefer an immutable digest to a mutable tag.
  • containerPort: 80 provides descriptive/container port metadata; it does not by itself expose the Pod to the internet.

7. Lab 3 — intentionally break and repair

Safely test in this disposable namespace:

kubectl set image deployment/web nginx=nginx:tag-that-does-not-exist -n artha-lab
kubectl rollout status deployment/web -n artha-lab --timeout=60s || true
kubectl get pods -n artha-lab
kubectl describe pod -n artha-lab <ACTUAL-POD-NAME>
# Use a real failed Pod name from `kubectl get pods` above.
kubectl rollout undo deployment/web -n artha-lab
kubectl rollout status deployment/web -n artha-lab --timeout=180s

Do not type angle brackets literally. Replace the placeholder using the actual failing Pod's name. During a rolling Deployment update, older healthy Pods may continue to serve; the exact effect depends on rollout configuration and available capacity.

Diagnosis: A failing image pull usually appears in kubectl describe pod events (ErrImagePull / ImagePullBackOff). A pod that starts but crashes instead may show CrashLoopBackOff and container logs. Learn to distinguish these paths.

9. Reasoning drills

  1. A Deployment has desired replicas = 3 and available replicas = 0. Which commands and events will you inspect, in which order?
  2. An API server is unreachable while a Pod remains running. Which duties can still continue, and what management capabilities are degraded?
  3. Why is a Pod IP not a durable application endpoint?
  4. Why doesn't raising replicas automatically guarantee application capacity?
  5. You created a Service with no EndpointSlices. Which selectors, labels and readiness signals are relevant?

Short answer key

  1. kubectl get deployment -o yaml, get pods -o wide, describe pod, get events --sort-by=.lastTimestamp; look for scheduling, image, readiness, quota and node faults.
  2. Already running processes generally may persist, but changes, scaling, scheduling and cluster coordination can be impaired; precise behavior depends on control-plane and node conditions.
  3. Pods are replaceable and Pod IPs can change; Services provide discovery/routing abstraction.
  4. Nodes may lack requested resources or have placement constraints, bad images or failed readiness.
  5. Confirm Service selector vs Pod labels, Pod readiness, namespace, EndpointSlice controller and service/cluster health.

10. Interview question (simple English)

Question: "Explain what happens when you run kubectl apply -f deployment.yaml."

Strong answer: "kubectl submits the declarative Deployment to the Kubernetes API server. After authentication, authorization and admission, the API object is persisted. The Deployment controller creates or updates ReplicaSets, and the ReplicaSet controller creates Pod objects toward the desired count. The scheduler assigns unscheduled Pods to feasible nodes. Kubelets on those nodes use the container runtime to launch containers and report observed status. Controllers continue to reconcile the actual state with the desired state. I validate both API object status and real application readiness, not only the success of kubectl apply."

Staff-level follow-up: Discuss admission webhook unavailability, scheduler constraints, network pull failures, PDB misconceptions, reconciler idempotency and what signals make a rollout automatically reversible.

Deep dive — Kubernetes network engineering and outages

Entry requirement: Complete weeks 1–4. Level: senior production troubleshooting. Outcome: explain and debug traffic from client socket to Pod and back. Where commands run: Kubernetes cluster terminal or authorized Linux node as specified. A local kind cluster is helpful but cannot replicate every real cloud dataplane behavior.

1. Four planes to keep separate

  1. API/control plane: Service, EndpointSlice, NetworkPolicy and Gateway resources communicate desired routing/policy semantics.
  2. Pod address plane: a CNI plugin configures Pod interfaces, IPAM, routes, veths or other network attachments.
  3. Service dataplane: kube-proxy can use Linux packet rules; alternative implementations (including eBPF) can implement Service forwarding without kube-proxy. Identify the actual cluster implementation.
  4. External access plane: provider load balancer, Gateway/Ingress controller, DNS, TLS and edge/network firewalls.

Many outages occur because an engineer confirms only that a Service object exists, assumes routing must work, and never inspects endpoints or dataplane.

2. Pod → Service → Pod request walk

Imagine Pod A calls http://orders.prod.svc.cluster.local:8080.

  1. A's resolver uses /etc/resolv.conf search path and DNS to resolve the Service name to a ClusterIP (with DNS caching effects).
  2. A opens a TCP socket toward the Service IP/port (assuming standard ClusterIP implementation).
  3. The node dataplane consults its Service implementation and selects an eligible backend endpoint from EndpointSlices, applying supported policy and session handling.
  4. CNI/node routes deliver packets to Pod B; depending on placement and implementation, this may be local veth forwarding or node-to-node routing/encapsulation.
  5. NetworkPolicy may restrict permitted connections only if the network plugin enforces it; host firewalls, security groups and gateway policies can add other gates.
  6. Return packets traverse reverse/connection-tracked or dataplane-specific paths; TCP correctness needs bidirectional reachability, MTU and proper state.

This is a reference mental model, not a guarantee that every implementation uses a VIP translation or identical routing steps. Headless Services, externalName, sidecars, proxies, eBPF service handling and topology-aware routing vary.

3. Debug from layer to layer

# Kubernetes API/objects (kubectl host)
kubectl get svc orders -n prod -o yaml
kubectl get endpointslices -n prod -l kubernetes.io/service-name=orders -o wide
kubectl get pods -n prod --show-labels -o wide
kubectl describe pod <pod-name> -n prod
kubectl get networkpolicy -n prod
kubectl get pods -n kube-system

# Inside a disposable debug Pod or existing authorized app Pod, if tools exist:
cat /etc/resolv.conf
getent hosts orders.prod.svc.cluster.local

# On an authorized node/host only (not generic production advice):

Not every container image ships getent, ip, curl, ss or a shell. Prefer ephemeral authorized debug tooling with least privilege rather than editing production images or granting unrestricted host access.

4. Three often-confused failure cases

Case A — NXDOMAIN or resolution timeouts

  • Check complete FQDN and namespace suffix.
  • Check CoreDNS Pods, Service IP and upstream resolver behavior.
  • Check whether network restrictions permit DNS UDP/TCP 53 to the right service/backend.
  • Compare resolution from two Pods in different namespaces/nodes.
  • Separate NXDOMAIN (name doesn't exist) from timeout (resolver/path can't respond).

Case B — DNS resolves but connection refused / times out

  • Confirm Service has eligible endpoints.
  • Confirm listening container address/port (0.0.0.0 vs 127.0.0.1); verify Service targetPort resolves correctly.
  • Inspect Pod readiness, netpol policies/CNI enforcement, node/firewall/SG restrictions, routes and packet captures if authorized.
  • Compare same-node vs cross-node behavior; this helps localize CNI/routing/MTU faults.

Case C — high p99 latency but 2xx replies

  • Compare application spans, DNS time, TCP handshakes, TLS, queues, retries and downstream dependencies.
  • Inspect CPU throttling, memory pressure, packet retransmits, connection pools and backlog.
  • Avoid blaming kube-proxy without evidence: the bottleneck may be app logic, DNS caching, remote storage or upstream service saturation.

5. Why network policies sometimes lie by omission

You can successfully kubectl apply a default-deny NetworkPolicy even on a cluster where the chosen CNI does not enforce NetworkPolicy. The API object may exist while traffic still passes. Your test must include a known permitted flow and a known denied flow, from a real probe Pod, while recording installed CNI version and implementation.

For this reason, manifests/11-default-deny-policy.yaml is for reading and policy design on default kind networking; it is not offered as a validated isolation implementation.

6. Ingress versus Gateway API

Ingress is a mature API and still widely deployed, but Kubernetes documentation notes its API is frozen and recommends Gateway API for new use cases. Gateway API has role-oriented resources such as GatewayClass (implementation), Gateway (listener/infra owner), and HTTPRoute (routing owner). A Gateway definition alone does not magically install its controller. Plan TLS certificates, backend permissions, client source IP, WAF needs and rollout procedures.

System design question: You need a shared external gateway for 30 teams. Which permissions can a team configure without changing other teams' hostnames/listeners? Design the Gateway/Route ownership model, and specify rate limiting/authentication implementations as controller-specific where needed.

7. Production scenario and scoring

Scenario: 80% of cross-node calls time out after a CNI upgrade; same-node calls remain healthy. CPU and app metrics are normal.

Strong analysis: compare node placement, CNI rollout status, packet path, MTU/encapsulation, routing or tunnel health and changes in iptables/eBPF state. Determine whether the new daemonset is healthy on every node. Verify via canary rollback if supported, not with a blind cluster-wide change. Record packet-level evidence only with authorization.

Wrong shortcut: "Restart all CoreDNS Pods" without any indication that DNS resolution failed.

Deep dive — Become a Kubernetes engineer who writes controllers

Entry requirement: Understand Deployments/CRDs and foundational Go. Level: advanced / staff. Outcome: design an idempotent, secure reconciliation loop and explain why it is resilient to retries and failures.

1. Why writing controllers matters

Kubernetes has a powerful extensibility model: developers can add a CRD so that users declare domain-specific intentions as Kubernetes API objects. A controller watches changes and brings dependent resources into agreement with the declared state.

Example: a developer creates:

apiVersion: platform.artha.example/v1alpha1
kind: PreviewEnvironment
metadata:
  name: pr-1024
  namespace: demo
spec:
  image: registry.example.invalid/team/app@sha256:EXAMPLE_ONLY
  ttlHours: 12

This is an illustrative API design, not an installable object until a compatible CRD and controller are implemented, the manifest is corrected to a real image digest, and a namespace exists.

Our operator might create a Deployment and Service, report a URL in .status, apply ownership labels and delete the environment on expiration. Real controller engineering begins when the first create partially fails or is repeated.

2. The reconcile contract

A reliable loop reads current state, compares it with spec, makes safe minimum changes, writes status, and requeues appropriately. It must not assume every event arrives once, in order, or while its process stays alive.

Reconcile(namespace/name):
    load custom resource by key
    if resource does not exist: return success  # already deleted
    if resource deleting:
        reconcile cleanup of owned/external resources
        when cleanup verified: remove our finalizer
        return retry/success
    validate desired intent; set status condition on invalid input
    ensure finalizer exists if outside-K8s cleanup is required
    ensure owned Deployment/Service match spec
    observe rollout/readiness of children
    update status conditions and observedGeneration (avoid unnecessary writes)
    return requeue based on missing readiness or API errors

This is pseudocode; a real Go implementation would use controller-runtime, Kubernetes clients and update conflict retries. Never use unbounded tight retries in hot reconcile paths.

3. Design the CRD schema

  • Prefer a domain-oriented resource name (PreviewEnvironment) instead of encoding low-level implementation details in every request.
  • Validate required image, TTL range, quota/tenant constraints and allowed namespace scope.
  • Reserve spec for caller intent, status for controller-owned conditions and observed state.
  • Track .status.observedGeneration so clients know whether status corresponds to the latest spec.
  • Design version conversion policy before promoting from v1alpha1 to a stable version.
  • Write RBAC that accesses only resources the controller truly needs; avoid blanket * verbs and resources.

4. Three difficult failure scenarios

Scenario A — duplicate reconciliation

The controller creates a child Deployment but crashes before updating status. On restart it must observe the existing child and update/create only what is missing. Naming, owner references and conflict management are fundamental.

Scenario B — external side-effect

An operator provisions an external cloud resource but crashes before recording its identifier. A naive retry can create duplicates and bill money. Require idempotency keys, deterministic lookup, transaction records and external approval/cost controls. If external action is not authorized, stop and report an approval blocker.

Scenario C — stuck finalizer

A resource is marked deleting; cleanup API is unreachable. Removing a finalizer prematurely can orphan billable or privileged resources. Conversely, keeping it forever creates stuck objects. Design operational overrides, audit events, escalation and safe compensating actions.

5. Unit and integration tests you must write

  1. Create valid CR; expected Deployment/Service present after repeated reconcile.
  2. Invoke reconcile twice; no duplicate resources and no irrelevant writes.
  3. Change image in CR; Deployment updates exactly once; status eventually matches generation.
  4. Remove a child Pod/Deployment; controller repairs target state.
  5. API write fails transiently; controller retries with backoff and meaningful condition.
  6. Controller restarts mid-reconcile; existing resources remain consistent.
  7. Delete CR; finalizer cleans external resources and completes safely.
  8. Invalid resource is rejected by schema or clearly reported in status.
  9. Unauthorized controller RBAC leads to visible, actionable errors.
  10. Concurrent spec change causes resourceVersion conflict; reconcile fetches latest state and retries safely.

Scoring: It is not enough to demonstrate creation of one child resource. Pass at least 8/10 tests with reproducible results, fix the remaining tests before presenting the project as production capable.

6. Go preparation mini-lab (offline standard library)

A basic retry algorithm with context is easy to test before introducing Kubernetes clients:

package main

import (
    "context"
    "errors"
    "fmt"
    "time"
)

func retry(ctx context.Context, max int, f func() error) error {
    var last error
    for i := 0; i < max; i++ {
        if err := ctx.Err(); err != nil { return err }
        if err := f(); err == nil { return nil } else { last = err }
        select {
        case <-ctx.Done(): return ctx.Err()
        case <-time.After(time.Duration(i+1) * 100 * time.Millisecond):
        }
    }
    if last == nil { return errors.New("no attempts") }
    return last
}

func main() {
    ctx, cancel := context.WithTimeout(context.Background(), time.Second)
    defer cancel()
    count := 0
    err := retry(ctx, 3, func() error {
        count++
        if count < 3 { return errors.New("temporary failure") }
        return nil
    })
    fmt.Printf("attempts=%d err=%v\n", count, err)
}

Save as retry.go, run go run retry.go on a host with Go installed. Expected behavior for this deterministic example is attempts=3 err=<nil> if the context deadline is not exceeded. A real controller should use established rate limiting and controller-runtime mechanisms; this is only a learning exercise in bounded retry/cancellation.

Six portfolio capstone projects — architecture, acceptance tests and presentation

Capstone 1 — Resilient multi-service application (Weeks 1–8)

Objective: Deploy API + worker + supporting data service to a disposable cluster using declarative configuration. Start with a small stateless API and choose a safe data-store topology; do not assume a single local database Pod provides HA.

Required implementation: Deployment, Service discovery, config separation, probes, resource requests/limits, graceful termination, rolling update, namespaces, least-privilege ServiceAccount, Helm or Kustomize packaging. Optionally write a small FastAPI/Go app for meaningful health endpoints.

Acceptance tests: (1) requests succeed through Service; (2) one app Pod disappears and replicas restore; (3) intentionally bad image revision is rolled back; (4) secret values do not appear in Git or standard logs; (5) observable shutdown/restart behavior; (6) all objects cleaned up.

Design questions: Why two replicas? How does a Service choose destinations? Which probe protects a slow start? How do you prevent connection drop during rollout?

Senior / Staff Kubernetes Engineering interview bank

72 questions with model answers. This is for recall, not memorization. For every question be ready to give: (a) a diagram, (b) a command or metric to verify, (c) one counterexample, and (d) an incident you actually experienced or a clearly labeled simulation.

Mock rules: 45 seconds for fundamentals; 2 minutes for incident answers; 10 minutes for architecture follow-ups. Award 0–4 per question: 0 absent, 1 jargon, 2 correct basics, 3 trade-offs/evidence, 4 deep failure handling and clear communication.

Foundations and APIs

Q1. What is the Kubernetes API server?

Answer: The authenticated/authorized API entry point through which clients and control loops read and mutate cluster objects; it is not the process launcher.

Q2. What is etcd?

Answer: A consistent, quorum-based key-value datastore commonly used to persist Kubernetes API state; backup and quorum health are operational concerns.

Q3. What is reconciliation?

Answer: Repeated comparison of desired and observed state followed by actions to converge safely; controllers must tolerate repeated and out-of-order observations.

Q4. Pod versus Deployment?

Answer: Pod is a group of containers sharing a lifecycle and network namespace; Deployment manages updates and ReplicaSets that maintain desired stateless Pods.

Q5. What is an OwnerReference?

Answer: Metadata connecting a dependent object to its owner, enabling garbage collection and controller relationships when configured correctly.

Q6. Spec vs status?

Answer: Spec is desired state; status is observed state. Controller-owned status may lag and should include conditions and generation tracking.

Q7. Who chooses a Pod node?

Answer: Scheduler binds eligible unscheduled Pods using feasibility and scoring; kubelet on the selected node executes them.

Q8. Why are labels important?

Answer: They form selectors for deployments, services, policies and operational grouping; errors can create unwanted matches or empty endpoints.

Q9. Is kube-proxy required on every modern cluster?

Answer: Service connectivity is required, but some deployments use an alternative dataplane (such as eBPF); kube-proxy is not universal.

Q10. How do you know a Deployment is healthy?

Answer: Check available/ready/updated replicas, conditions, Pod events, endpoint readiness and representative user-path requests, not apply success alone.

Q11. What changes after a manifest is accepted?

Answer: Controllers may create dependent objects and eventually move observed state; admission success does not guarantee readiness.

Q12. What is a CRD?

Answer: A schema-backed API extension that defines custom Kubernetes resource types; controllers may implement their desired behavior.

Networking and storage

Q13. Pod IP vs Service IP?

Answer: Pod IP is workload-instance addressing; Service IP is a stable virtual service abstraction routing to changing endpoints.

Q14. What is an EndpointSlice?

Answer: API object representing groups of network endpoints behind a Service, including address and readiness-related conditions.

Q15. Explain DNS failure triage.

Answer: Check Pod resolver config, Service/namespace names, CoreDNS health, network restrictions and direct Pod/Service IP connectivity.

Q16. Why does port-forward work but Service fail?

Answer: Port-forward uses a diagnostic tunnel and can bypass parts of normal in-cluster Service/data-plane path; inspect selectors, endpoints and dataplane.

Q17. NodePort vs LoadBalancer vs ClusterIP?

Answer: ClusterIP is internal Service VIP; NodePort exposes a port on eligible nodes; LoadBalancer asks provider integration to provision/attach external L4 exposure.

Q18. Ingress vs Gateway API?

Answer: Ingress is stable but frozen; Gateway API offers richer, role-oriented resources and routing. Either needs a compatible controller/implementation.

Q19. What is the role of CNI?

Answer: Configure Pod networking, IP assignment/routing depending on plugin, and optionally policy enforcement; capabilities vary.

Q20. Why can NetworkPolicy silently fail?

Answer: The API accepts objects even if installed CNI does not enforce them; verify plugin capability and actual traffic.

Q21. What causes connection tracking saturation?

Answer: Too many tracked flows can exhaust kernel tables, leading to dropped/new failed connections; inspect conntrack utilization and traffic patterns.

Q22. What is CSI?

Answer: Container Storage Interface by which storage drivers integrate volume provisioning/attach/mount with Kubernetes.

Q23. PV vs PVC vs StorageClass?

Answer: PV represents a resource, PVC is a claim/request, StorageClass specifies provisioning/characteristics; binding depends on class, topology and availability.

Q24. Is a StatefulSet a database backup?

Answer: No; stable network identity and storage relationships do not guarantee consistency, replication or recoverability.

Operations and failure diagnosis

Q25. ImagePullBackOff triage?

Answer: Describe Pod events; inspect image/tag/registry access, DNS/proxy, authorization, pull secrets and node pull capability.

Q26. CrashLoopBackOff triage?

Answer: Inspect prior container logs, exit code, signal/OOM indicators, probes, commands, config and dependencies.

Q27. Pending Pod triage?

Answer: Read scheduler Events; inspect resource requests, node selectors/affinity, taints, volume binding and quota.

Q28. OOMKilled versus CPU throttling?

Answer: OOMKilled is memory termination from exceeded constraints/pressure; CPU throttling delays execution but generally does not kill the process.

Q29. Readiness vs liveness?

Answer: Readiness decides traffic eligibility; liveness triggers restart on unrecoverable failure. Tuning them poorly can amplify outages.

Q30. Why a startup probe?

Answer: Allows slow boot to complete before liveness/readiness checks begin, avoiding unnecessary restarts.

Q31. What is a PDB?

Answer: A policy limiting voluntary disruptions through eviction API, not a guarantee against node failure or forced Pod deletion.

Q32. How do you safely drain?

Answer: Check capacity/PDBs, cordon and use drain/eviction, monitor workloads and reschedule; follow cluster/CLI version-specific runbooks.

Q33. What is version skew?

Answer: Kubernetes components and tooling have supported relative-version constraints; validate before upgrading API server, kubelets and add-ons.

Q34. How do you back up etcd?

Answer: Follow deployment-specific snapshot tooling using secured credentials/storage; prove restoration in a test environment and separately protect application data.

Q35. How many failures can a three-member etcd quorum withstand?

Answer: One member can fail while retaining two-member majority; two failed members cause loss of write quorum.

Q36. What is safe rollback?

Answer: Restore previous known-good desired configuration with validated health; do not assume rollback fixes irreversible database/schema mutations.

Security, cloud and supply chain

Q37. Authentication vs authorization?

Answer: Authn proves identity; authz checks whether that identity may perform requested verbs/actions on resources; admission can add separate policy decisions.

Q38. Role vs ClusterRole?

Answer: Role is namespace-scoped rule object; ClusterRole can express cluster-scoped or reusable namespace permissions, bound with RoleBinding/ClusterRoleBinding as appropriate.

Q39. What is a ServiceAccount?

Answer: Namespaced non-human workload/API identity used by Pods/controllers, subject to RBAC and token/security configuration.

Q40. What does Restricted Pod Security require?

Answer: A hardened policy restricting privilege escalation, user/capability/volume/host settings; use official version-specific requirements and exception process.

Q41. Why protect etcd?

Answer: It contains sensitive API state including Secrets unless external protection applies; restrict access, backups and encryption.

Q42. Secret best practices?

Answer: Least-privilege access, encryption at rest, external secret management when suitable, rotation, no logging/Git exposure and audit.

Q43. What is admission control?

Answer: Post-authn/authz policy/default/validation path on API writes; unsafe fail-closed webhooks can disrupt cluster operations.

Q44. What does image signing guarantee?

Answer: Provenance/integrity relative to trusted signatures; it does not guarantee absence of vulnerabilities.

Q45. EKS access entry significance?

Answer: EKS Cluster Access Management maps IAM principals via access entries; AWS recommends it for new access designs over deprecated aws-auth pattern.

Q46. EKS Pod Identity vs IRSA?

Answer: Both provide IAM to Pods; EKS Pod Identity is often simpler and recommended where supported; IRSA has different cross-account/dependency trade-offs.

Q47. Why prevent broad node role access?

Answer: Compromised Pods might exploit credential paths to access privileges unrelated to workload; isolate and scope role permissions.

Q48. How should CI deploy?

Answer: Short-lived least-privilege credentials, immutable image digests, scanned/signed artefacts, tested manifests, staged approval and observability gates.

Go, controllers and platform architecture

Q49. Why Go for Kubernetes engineers?

Answer: Kubernetes ecosystem libraries/controllers are heavily Go-based, enabling client tooling, concurrency and operator implementation.

Q50. What is context.Context?

Answer: A standard mechanism to propagate cancellation/deadlines and limited request-scoped data; do not retain contexts indefinitely.

Q51. What is an informer?

Answer: A shared watch/cache pattern supporting event handling with fewer API calls; it must tolerate relisting/watch disruption.

Q52. Idempotent reconcile?

Answer: Applying the same reconciliation repeatedly moves to the same intended state without duplicating side effects.

Q53. What is a finalizer?

Answer: Metadata requesting cleanup before deletion completion; bugs or unavailable dependencies can block deletion.

Q54. Status.observedGeneration?

Answer: Records which spec generation the controller has processed, helping clients distinguish current vs stale status.

Q55. Why use OwnerReferences?

Answer: Represent ownership and guide garbage collection; external resources still need explicit safe finalization.

Q56. What is controller-runtime?

Answer: Go libraries and conventions to construct Kubernetes controllers, caches, reconcile loops and tests.

Q57. How can a controller overload API servers?

Answer: Hot reconciliation loops, ineffective caching, unbounded list/watch or write conflicts generate excess API load.

Q58. How do you expose self-service Kubernetes?

Answer: Build constrained platform APIs/golden paths with RBAC, quotas, policy, reviews, observable workflows and documented ownership.

Q59. What is a fleet upgrade?

Answer: Coordinated rollout across clusters with canary groups, compatibility checks, soak time, failure gates and rollback policy.

Q60. Why is cluster-per-team not always ideal?

Answer: It creates management and cost overhead; select boundaries based on compliance, trust, workload and scale.

SRE, distributed systems and staff-level judgment

Q61. What is an SLI?

Answer: A measurable signal of service quality such as good responses divided by eligible requests over a defined window.

Q62. SLO versus SLA?

Answer: SLO is internal quantitative reliability objective; SLA is contractual customer-facing commitment and consequences.

Q63. Error budget for 99.9% availability in 30 days?

Answer: 0.1% of 30 days = 43.2 minutes of allowed unavailability, under the simplified all-or-nothing time-based metric.

Q64. Why can retries cause outages?

Answer: Unbounded retries multiply load on degraded dependencies; use timeouts, jitter, budgets and overload controls.

Q65. Is multi-cluster always more reliable?

Answer: No; shared failure domains, data consistency and added operational complexity can undermine gains.

Q66. What is blast radius?

Answer: The scope of systems/users that a failure or bad change can affect; limit via segmentation, safe rollouts and isolation.

Q67. How to choose RPO and RTO?

Answer: Tie acceptable data loss and restore duration to business impact, technical constraints and tested ability to recover.

Q68. What makes a good incident postmortem?

Answer: Grounded timeline, contributing conditions, impact metrics, counterfactuals, assigned preventive actions and verification; no unproven blame.

Q69. How to evaluate platform cost?

Answer: Optimize per useful unit of work while preserving SLOs, security and engineering throughput; count operational and failure costs.

Q70. What makes staff-level design different?

Answer: It resolves ambiguity, quantifies trade-offs, aligns stakeholders, designs for long-term evolution and creates org-wide leverage.

Q71. How would you push back on an unsafe launch?

Answer: State evidence, measurable risks, alternatives and reversible launch gates; escalate through appropriate ownership without misrepresenting certainty.

Q72. How do you justify ₹1 crore compensation?

Answer: With market-level fit and evidence of broad technical impact, difficult production judgment, engineering depth and leadership; a certificate alone is insufficient.

Your prior Linux + ELK + Python + Kubernetes/OpenShift work is a useful start. Work specifically on closing gaps such as custom controller coding, advanced networking, systems-design reasoning, AWS/EKS security architecture and senior-level technical communication.

Skills that command higher-level scope

  1. Engineering depth: Go, algorithms/data structures, networking, concurrency, Kubernetes API and controller-runtime, debugging with Linux tools.
  2. Platform design: secure multi-tenancy, abstractions and self-service APIs, GitOps/CI/CD, resource governance, fleet operations.
  3. Availability ownership: production incident response, SLOs, error budgets, HA/DR, canary rollouts, observability, upgrade strategy.
  4. Business impact: reduced deployment time, reduced infrastructure spend without worsened SLOs, lower incident rate, faster MTTR, better developer satisfaction.
  5. Leadership: mentor engineers, write ADRs, influence standards, prioritize risks, communicate outages and trade-offs.
