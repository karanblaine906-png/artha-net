Chapter 5 — Advanced PyTorch Internals

Course: PyTorch from Scratch to Production SOC Log Analysis
Audience: Python/Linux administrators, ML/MLOps engineers and security analysts
Goal: Understand tensor memory, automatic differentiation, mathematical gradients, custom modules, data pipelines and CPU/GPU optimization.

Learning outcomes

By the end, you should be able to explain PyTorch tensor storage and views, debug incorrect gradients, write a custom nn.Module, create a streaming dataset for Linux logs, profile training, and reason about performance bottlenecks. Examples use PyTorch 2.x APIs. Outputs are deterministic where explicitly indicated; device timings and performance vary.

5.1 Tensors: dimensions, shapes, strides, storage

A tensor is a typed, device-resident multidimensional array. Shape tells us how many entries exist per dimension. Stride gives the number of elements to move in underlying storage when an index increments by one. Storage is not necessarily laid out in the logical order of a view.

import torch
x = torch.tensor([[1., 2., 3.], [4., 5., 6.]])
print(x.shape)           # torch.Size([2, 3])
print(x.dtype)           # torch.float32
print(x.stride())        # (3, 1)
print(x.is_contiguous()) # True
y = x.transpose(0, 1)
print(y.shape)           # torch.Size([3, 2])
print(y.stride())        # (1, 3)
print(y.is_contiguous()) # False

Line by line: import torch imports the library. torch.tensor copies the nested values into a newly allocated tensor; floating-point literals produce the default floating dtype (normally float32). shape reports logical dimensions; dtype reports element representation; stride() returns offsets into storage; is_contiguous() checks the standard contiguous layout. transpose(0,1) swaps the two logical axes, typically without copying the underlying data. The transposed view therefore has different strides and is not contiguous.

Views vs copies

x = torch.arange(6).reshape(2, 3)
y = x[:, 1:]           # Basic slicing: view
z = x[:, [1, 2]]       # Advanced indexing: copy
x[0, 1] = 99
print(y[0, 0].item())  # 99
print(z[0, 0].item())  # 1

arange(6) constructs integer values 0–5. reshape(2,3) arranges them in two rows; reshape may return a view or copy depending on layout. x[:,1:] uses basic slicing, sharing storage. x[:,[1,2]] uses advanced indexing, producing a copy. Mutating x changes the view but not the copy. In-place mutations of tensors involved in Autograd can cause version-counter errors; prefer out-of-place operations when unsure.

Production scenario: A preprocessing pipeline transposes [batch, sequence, features] to [sequence, batch, features]. If a downstream operation requires contiguous layout, use tensor.contiguous() intentionally; do not insert copies everywhere because they consume bandwidth and memory.

Troubleshooting: If .view(...) fails on a noncontiguous tensor, use .reshape(...) when copying is acceptable or .contiguous().view(...) when you explicitly require a contiguous buffer.

5.2 Matrix multiplication and shape contracts

X = torch.randn(4, 6)   # 4 samples, 6 features
W = torch.randn(6, 16)  # 6 inputs, 16 outputs
b = torch.zeros(16)     # 16 biases
H = X @ W + b
print(H.shape)          # torch.Size([4, 16])

randn draws random normal values. @ performs matrix multiplication; inner dimensions must match (6 and 6). Addition broadcasts the 16-element bias across four samples. H is a batch of 16-dimensional pre-activations. For our SSH detector, 6 is the number of engineered security features.

Interview: Why does nn.Linear(6,16) have 112 parameters? Its weight has 16 × 6 = 96 elements and bias has 16 elements, totaling 112. Internally the layer computes X @ weight.T + bias.

5.3 Autograd: dynamic computation graphs

w = torch.tensor(2.0, requires_grad=True)
x = torch.tensor(3.0)
y = w * x
loss = (y - 10) ** 2
loss.backward()
print(w.grad)  # tensor(-24.)

Line by line: w is a leaf tensor for which PyTorch will accumulate gradients. x is a constant input. Multiplication creates y and records a differentiable operation. Squaring the prediction error produces scalar loss. Calling backward() traverses the graph in reverse, applying derivatives and accumulating results in w.grad.

Mathematically, L = (wx - 10)^2. Therefore dL/dw = 2(wx - 10)x; substituting w=2, x=3 yields 2(6-10)3 = -24. A gradient tells us the local direction of steepest increase; gradient descent subtracts a scaled gradient.

Why gradients accumulate

w = torch.tensor(2.0, requires_grad=True)
for step in range(2):
    loss = (w * 3 - 10) ** 2
    loss.backward()
    print(step, w.grad.item())
# 0 -24.0
# 1 -48.0

Each iteration creates a fresh graph, but leaf gradients are accumulated. In a real training loop, call optimizer.zero_grad() (often with set_to_none=True) before backward unless intentional gradient accumulation is required.

no_grad vs inference_mode vs eval

  • model.eval() changes Dropout and BatchNorm behavior; it does not disable gradient tracking.
  • torch.no_grad() stops recording gradient operations within its scope; useful for validation and parameter updates.
  • torch.inference_mode() additionally disables some Autograd bookkeeping and can improve inference performance; tensors created there have restrictions when reused in gradient-tracked computations.
model.eval()
with torch.inference_mode():
    logits = model(batch)
    probabilities = torch.sigmoid(logits)

eval() sets the model's training flag to false. inference_mode() disables Autograd-related work for the block. model(batch) runs a forward pass, and sigmoid converts binary logits to values between zero and one. These probabilities are not necessarily calibrated.

5.4 Deriving backpropagation for a linear layer

Let Z = XW + b, A = ReLU(Z) and scalar loss L. The chain rule yields dL/dW = Xᵀ (dL/dZ), dL/db = sum_batch(dL/dZ) and dL/dX = (dL/dZ)Wᵀ. For ReLU, dA/dZ is 1 where Z > 0 and 0 where Z < 0 (PyTorch chooses 0 at exactly 0). With mean reduction, upstream gradients already contain the relevant averaging factor.

x = torch.tensor([[2.0, -1.0]])
layer = torch.nn.Linear(2, 1, bias=False)
with torch.no_grad():
    layer.weight.copy_(torch.tensor([[0.5, 0.25]]))
output = layer(x)
loss = output.square().mean()
loss.backward()
print(output.item())           # 0.75
print(layer.weight.grad)       # tensor([[ 3.0000, -1.5000]])

Linear(2,1,bias=False) defines one linear neuron with two weights. no_grad ensures the initialization assignment is not recorded in the computation graph. copy_ replaces the parameter values. The output is 2(0.5) + (-1)(0.25) = 0.75; loss is 0.75². Derivative dL/dw = 2(output)x = 1.5[2,-1] = [3,-1.5].

Interview: Does backward() update parameters? No. It computes gradients. An optimizer such as SGD or Adam uses those gradients to update parameters.

5.5 Gradient checking with finite differences

import torch
w = torch.tensor(2.0, dtype=torch.float64, requires_grad=True)
f = lambda v: (3 * v - 10) ** 2
f(w).backward()
eps = 1e-5
with torch.no_grad():
    numerical = (f(w + eps) - f(w - eps)) / (2 * eps)
print(round(w.grad.item(), 5))   # -24.0
print(round(numerical.item(), 5)) # -24.0

float64 reduces rounding error for numerical checks. The central-difference formula approximates the derivative by evaluating the loss at nearby weights. no_grad prevents the check from constructing another graph. Finite differences are slow for large models but valuable for testing custom derivatives. PyTorch also offers torch.autograd.gradcheck for suitable differentiable functions.

5.6 Custom PyTorch module for log classification

import torch
from torch import nn

class LogMLP(nn.Module):
    def __init__(self, input_features=6, hidden=32):
        super().__init__()
        self.layers = nn.Sequential(
            nn.Linear(input_features, hidden),
            nn.ReLU(),
            nn.Linear(hidden, 16),
            nn.ReLU(),
            nn.Linear(16, 1)
        )

    def forward(self, features):
        if features.ndim != 2 or features.shape[1] != 6:
            raise ValueError('Expected [batch, 6] features')
        return self.layers(features)

model = LogMLP()
print(sum(p.numel() for p in model.parameters())) # 769

nn.Module provides parameter registration and integration with optimizers and serialization. super().__init__() initializes its base state. nn.Sequential applies layers in sequence. The forward shape check catches malformed API inputs before matrix multiplication. numel() counts tensor elements; parameter count is (6×32+32)+(32×16+16)+(16×1+1)=769.

Production consideration: Input shape validation is not enough: enforce numeric ranges, correct feature order, and the exact fitted scaler and aggregation window used during training.

5.7 Dataset and DataLoader for windowed log features

import torch
from torch.utils.data import Dataset, DataLoader

class LogWindowDataset(Dataset):
    def __init__(self, features, labels):
        self.features = torch.as_tensor(features, dtype=torch.float32)
        self.labels = torch.as_tensor(labels, dtype=torch.float32).reshape(-1, 1)
        if self.features.ndim != 2 or self.features.shape[1] != 6:
            raise ValueError('features must have shape [N,6]')
        if len(self.features) != len(self.labels):
            raise ValueError('feature/label count mismatch')

    def __len__(self):
        return len(self.labels)

    def __getitem__(self, index):
        return self.features[index], self.labels[index]

features = torch.randn(100, 6)
labels = torch.randint(0, 2, (100, 1))
loader = DataLoader(LogWindowDataset(features, labels),
                    batch_size=16, shuffle=True, num_workers=0)
for batch_x, batch_y in loader:
    print(batch_x.shape, batch_y.shape)
    break
# torch.Size([16, 6]) torch.Size([16, 1])

Line by line: Dataset defines how to access one example; DataLoader batches examples and optionally shuffles or parallelizes fetching. as_tensor converts input arrays into tensors, potentially sharing memory when compatible. reshape(-1,1) ensures binary labels have shape [N,1]. __len__ reports dataset size; __getitem__ returns one feature/label pair. batch_size=16 requests 16 examples per batch. shuffle=True randomizes example order; it does not prevent temporal leakage. num_workers=0 performs loading in the main process, a good starting point for small datasets and debugging. The loop reads the first batch only.

Time-aware splitting for security logs

Do not randomly mix highly overlapping SSH time windows from the same host/source IP across training and testing: this leaks near-duplicate information. Prefer chronological train/validation/test splits, and consider grouping by host or source entity depending on your deployment goal. Fit scalers only on training data. Validate on a later period and test on a final untouched period.

Iterable datasets for live logs

IterableDataset can stream records, but each worker must shard its input to avoid duplicate events. Handle file rotation, checkpoints, backpressure, event-time ordering and at-least-once delivery explicitly. A real-time detector should aggregate events into fixed or sliding windows before inference; individual failed-login lines lack necessary context.

5.8 Stable training loop with validation

import torch
from torch import nn

device = torch.device('cuda' if torch.cuda.is_available() else 'cpu')
model = LogMLP().to(device)
criterion = nn.BCEWithLogitsLoss()
optimizer = torch.optim.AdamW(model.parameters(), lr=1e-3, weight_decay=1e-2)

for epoch in range(5):
    model.train()
    total_loss = 0.0
    for xb, yb in loader:
        xb, yb = xb.to(device), yb.to(device)
        optimizer.zero_grad(set_to_none=True)
        logits = model(xb)
        loss = criterion(logits, yb)
        loss.backward()
        torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
        optimizer.step()
        total_loss += loss.item() * xb.shape[0]
    print(f'Epoch {epoch+1}: loss={total_loss/len(loader.dataset):.4f}')

device selects a CUDA GPU if available, otherwise CPU. model.to(device) moves model parameters. BCEWithLogitsLoss accepts raw logits and combines sigmoid with binary cross-entropy stably. AdamW uses decoupled weight decay. train() enables training behavior. Each batch is transferred to the model device. zero_grad(set_to_none=True) clears old gradients. The forward pass computes logits; loss compares them with labels; backward computes gradients; clipping bounds the global gradient norm; step() updates weights. Multiplying mean batch loss by batch size and dividing by dataset length produces a sample-weighted epoch mean.

Important: This demo uses random features and random labels, so loss reduction does not imply security detection capability. Use meaningful labeled datasets and separate validation/test loaders before making performance claims.

5.9 CPU, CUDA and mixed precision

print(torch.cuda.is_available())
print(torch.cuda.device_count())
if torch.cuda.is_available():
    print(torch.cuda.get_device_name(0))

cuda.is_available() tests whether a supported CUDA runtime/device is available. device_count() reports visible CUDA devices. get_device_name(0) identifies the first visible GPU. On a CPU-only Debian laptop, CUDA availability is typically False.

For CUDA training, mixed precision can reduce memory use and accelerate supported operations:

scaler = torch.amp.GradScaler('cuda', enabled=(device.type == 'cuda'))
for xb, yb in loader:
    xb, yb = xb.to(device), yb.to(device)
    optimizer.zero_grad(set_to_none=True)
    with torch.autocast(device_type=device.type,
                        enabled=(device.type == 'cuda')):
        loss = criterion(model(xb), yb)
    scaler.scale(loss).backward()
    scaler.unscale_(optimizer)
    torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)
    scaler.step(optimizer)
    scaler.update()

autocast selects lower-precision operations where appropriate. GradScaler scales the loss to reduce float16 gradient underflow; unscale_ restores gradients before clipping. scaler.step skips unsafe updates if nonfinite gradients are detected; update adjusts the scale. On CPU this example disables scaling and autocast, so it behaves like ordinary training. Mixed precision is not automatically faster for every model/device.

5.10 Profiling and bottleneck diagnosis

from torch.profiler import profile, ProfilerActivity

model.eval()
example = torch.randn(64, 6, device=device)
activities = [ProfilerActivity.CPU]
if device.type == 'cuda':
    activities.append(ProfilerActivity.CUDA)
with profile(activities=activities, record_shapes=True) as prof:
    with torch.inference_mode():
        for _ in range(10):
            model(example)
print(prof.key_averages().table(sort_by='self_cpu_time_total', row_limit=10))

The profiler records selected CPU/GPU operations. record_shapes helps identify unexpectedly large tensors. key_averages() aggregates measurements, and the table sorts by CPU self time. Profiling adds overhead, so do not treat its times as unbiased production latency. Warm up the model before benchmarking, synchronize CUDA around manual timings, and report batch size, device and percentile latency.

Security-analytics performance scenario: If parsing syslog lines consumes more CPU than neural inference, adding a GPU will not fix the bottleneck. Profile parsing, aggregation, feature scaling and inference separately. Consider batch inference, compiled regexes, streaming aggregation and caching only after measurements.

5.11 Production reliability and security

  1. Model artifacts: Prefer trusted, versioned state_dict artifacts; use torch.load(..., weights_only=True, map_location='cpu'), verify artifact integrity and match the architecture.
  2. Input contract: Version feature schema, scaler parameters, aggregation duration, timezone assumptions and missing-value behavior together with model weights.
  3. Data privacy: Minimize raw usernames and source IPs in stored training datasets; apply retention and access controls.
  4. Alert quality: Optimize precision, recall and false alerts per host/day, not only accuracy. Class imbalance makes accuracy misleading.
  5. Drift: Track changes in feature distributions and false-positive feedback. Retraining requires evaluation and approval, not automatic trust in new data.
  6. Failure modes: Have a rule-based fallback or queue/retry path if inference is unavailable. Decide explicitly whether the pipeline should fail open or closed.
  7. Adversarial behavior: Attackers can adapt to detection thresholds. Use layered detections, analyst review and careful testing rather than treating neural predictions as proof of compromise.

5.13 Interview questions and answers

Q1. What is a tensor stride? Number of storage elements traversed when an index increments along an axis; views can change stride without copying storage.

Q2. Why can view() fail after transpose? A transposed tensor often has noncontiguous strides that cannot be represented by the requested view; reshape may copy.

Q3. What is a leaf tensor? A user-created tensor not produced by a recorded differentiable operation; leaf tensors with requires_grad=True accumulate gradients in .grad.

Q4. Why does PyTorch accumulate gradients? It supports contributions from multiple backward calls, including gradient accumulation across minibatches.

Q5. Explain the chain rule in backpropagation. Derivatives of composed operations multiply along paths, and contributions from multiple paths sum.

Q6. Difference between eval() and inference_mode()? The former changes module behavior; the latter disables gradient-related bookkeeping.

Q7. What does BCEWithLogitsLoss expect? Raw logits, not probabilities; it applies a numerically stable combination of sigmoid and binary cross-entropy.

Q8. Why prefer AdamW over naive L2 regularization in Adam? AdamW decouples weight decay from adaptive gradient updates.

Q9. Why might a GPU not accelerate a small MLP? Kernel-launch and transfer overhead can dominate tiny workloads; parsing and preprocessing may be the bottleneck.

Q10. How do you avoid data leakage in SSH detection? Use time-aware and possibly entity-aware splits, fit transformations only on training data, and isolate overlapping windows.

Q11. What is gradient clipping? Bounding gradient magnitude/norm to reduce extreme updates; it does not fix fundamentally bad labels or architectures.

Q12. What is the role of a DataLoader worker? It loads/transforms dataset samples in a separate process; multiprocessing overhead can exceed benefits for small datasets.

Q13. How do you diagnose an OOM? Measure batch shapes and allocated memory, inspect stored tensors with attached graphs, and adjust batch size/model or accumulation.

Q14. Why isn't classification accuracy enough for SOC alerts? With rare attacks, predicting normal for everything can have high accuracy but zero recall; alert volume and precision matter.

Q15. How would you validate a deployed detector? Evaluate on unseen future periods, monitor precision/recall and false-alert burden, shadow-test against rules, and establish rollback criteria.

5.14 Practical labs

Lab A — Tensor layout: Run the transpose and indexing examples. Print data_ptr(), stride() and is_contiguous() before/after; explain when a copy occurs.

Lab B — Gradient audit: Derive dL/dw manually for three different w values and compare with Autograd and central finite differences.

Lab C — Model contracts: Change input features from six to five and observe the validation error; restore six features and count trainable parameters.

Lab D — Training pipeline: Train on a properly labeled synthetic SSH-window dataset with a chronological holdout. Report confusion matrix, precision, recall, PR-AUC and alerts per 1,000 windows. Document that synthetic metrics do not establish real-world efficacy.

Lab E — Performance: Benchmark batch sizes 1, 16, 64 and 256 on CPU. Compare end-to-end latency including feature creation to model-only latency, and explain the difference.
